# DramaIP 现代微服务全栈开发流程

## 0. 文档定位

本文回答的核心问题是：

> DramaIP 的一个产品需求，如何从想法开始，经过产品设计、架构设计、契约设计、前后端开发、自动化测试、CI/CD、Kubernetes 部署，最终安全上线并持续运营。

本文不是单纯的技术栈清单，也不是目录结构说明，而是一套完整的软件交付流程。

DramaIP 的整体交付链路为：

```text
产品需求
  ↓
用户场景与验收标准
  ↓
领域建模与服务边界确认
  ↓
API、gRPC、事件契约设计
  ↓
数据库与分布式一致性设计
  ↓
任务拆分与迭代计划
  ↓
桌面端、Web、移动端、后端并行开发
  ↓
单元测试、集成测试、契约测试、E2E
  ↓
代码评审与质量门禁
  ↓
CI 构建、扫描、生成制品
  ↓
测试环境与预发布环境验证
  ↓
灰度发布到 Kubernetes
  ↓
指标、日志、链路追踪与业务监控
  ↓
故障处理、对账、复盘和用户反馈
  ↓
进入下一轮迭代
```

# 一、DramaIP 的整体产品与系统边界

## 1.1 产品入口

DramaIP 包含四类客户端：

```text
DramaIP
├── Desktop：专业、本地优先的创作工作台
├── Web：官网、登录、订阅购买和账号中心
├── Mobile：灵感记录和轻量创作
└── Admin：运营、对账、异常处理和审计后台
```

四类客户端通过不同方式使用系统能力。

### Desktop

桌面端是完整创作工作的主要入口：

* 本地 SQLite 是创作数据的可信写入源；
* 支持长文本、人物设定、项目管理和复杂 AI 工作流；
* 可以使用用户自己的 API Key；
* 也可以登录 DramaIP Cloud，使用平台套餐和 token 额度；
* 云端不可用时不能影响本地项目继续编辑。

### Web

Web 主要负责：

* 产品官网；
* 定价和下载；
* 注册、登录和邮箱验证；
* 账号中心；
* 套餐购买；
* 订单、订阅和 token 用量查询。

### Mobile

移动端只做轻量创作：

* 登录；
* 灵感记录；
* 短文本草稿；
* AI 快速扩写；
* 查看套餐和余额；
* 将草稿交接给桌面端。

移动端不复制完整桌面工作台。

### Admin

管理后台负责：

* 管理员登录；
* 用户和账号状态查询；
* 订单、订阅和支付状态查看；
* token 用量和 AI 成本分析；
* outbox、MQ、支付 webhook 异常排查；
* 报表和审计日志；
* 高权限操作确认。

Admin 使用独立认证体系，不复用普通用户 JWT。

---

## 1.2 仓库边界

DramaIP 使用两个业务仓库：

```text
dramaIp/
├── docs/
│   ├── 产品设计
│   ├── 技术架构
│   ├── ADR
│   ├── 开发流程
│   ├── 发布流程
│   └── 差异演进
│
├── dramaip-desktop/
│   └── 本地优先桌面端，可在未来开源
│
└── dramaip-platform/
    ├── Web
    ├── Mobile
    ├── Admin
    ├── Go 微服务
    ├── 部署配置
    └── 闭源商业能力
```

必须保持以下边界：

```text
可公开：
Electron、React、本地 SQLite、基础 AI Provider、导出能力

必须闭源：
支付、订阅、额度账本、平台 API Key、AI 成本控制、
风控、生产环境配置、管理后台和商业 Prompt
```

桌面端通过公开且版本化的 API 使用云端能力，不能包含云端服务实现和平台密钥。

# 二、流程总原则

DramaIP 的开发流程遵循十项原则。

## 2.1 架构文档优先

代码实现要向目标架构收敛。

出现以下情况时，应先写 ADR：

* 增加新的微服务；
* 改变服务数据所有权；
* 改变认证方式；
* 改变支付或额度状态机；
* 改变事件格式；
* 引入新的基础设施；
* 修改开源与闭源边界。

流程为：

```text
发现现有架构不适用
  ↓
编写 ADR
  ↓
评审技术影响和迁移方案
  ↓
更新目标架构
  ↓
修改代码
```

禁止先改代码，最后再用文档解释已经发生的架构漂移。

---

## 2.2 契约优先

在全面开发前先确定：

* HTTP API；
* gRPC API；
* RabbitMQ 事件；
* 错误码；
* 幂等规则；
* 身份传播方式；
* 超时和重试规则；
* SDK 数据模型。

契约确认后，桌面端、Web、Mobile 和后端才能并行开发。

---

## 2.3 本地优先

桌面端的创作项目默认只保存在本地。

云端能力只能在用户明确操作时使用：

* 用户主动调用云端 AI；
* 用户主动同步草稿；
* 用户主动分享项目；
* 用户主动使用云端套餐。

云端异常不得导致：

* 本地项目无法打开；
* 本地编辑内容丢失；
* 本地 BYOK 模型无法使用；
* 云端数据覆盖本地正文。

---

## 2.4 数据自治

每个领域服务只能读写自己的 PostgreSQL Schema。

```text
auth-service       → auth schema
user-service       → user schema
billing-service    → billing schema
quota-service      → quota schema
ai-gateway-service → ai_gateway schema
notification       → notification schema
reporting          → reporting schema
admin              → admin schema
```

禁止：

```sql
SELECT *
FROM billing.orders
JOIN quota.token_accounts ...
```

跨领域数据只能通过：

* gRPC；
* 领域事件；
* reporting read-model；
* BFF 内存聚合。

每个服务使用独立数据库角色，从数据库权限层面阻止跨 Schema 访问。

---

## 2.5 同步链路只完成必要结果

同步链路负责用户必须立即看到的结果。

例如支付成功后的同步链路：

```text
支付回调验签成功
  ↓
billing 记录支付成功
  ↓
billing 同步调用 quota 创建额度账户
  ↓
订阅变为 active
  ↓
用户立即可以使用云端 AI
```

异步链路负责：

* 通知；
* 报表；
* 用量聚合；
* 邮件；
* 对账；
* 补偿；
* 运营统计。

---

## 2.6 关键写操作必须幂等

以下接口必须支持幂等：

* 创建订单；
* 支付 webhook；
* 创建订阅周期；
* 创建 token account；
* AI 请求；
* token 预扣；
* token 结算；
* 移动端离线草稿提交；
* MQ 消费；
* 管理员高权限操作。

幂等不能只依靠 Redis，必须有数据库唯一约束或持久化幂等记录。

---

## 2.7 同一制品逐级发布

同一版本的镜像依次进入：

```text
开发验证
  ↓
测试环境
  ↓
预发布环境
  ↓
生产灰度
  ↓
生产全量
```

禁止每个环境重新构建一遍镜像。

例如：

```text
harbor.example.com/dramaip/auth-service:git-a82d913
```

该镜像应原样从测试环境推进到生产环境。

---

## 2.8 可观测性从服务创建第一天接入

每个新服务创建时必须同时具备：

* 结构化日志；
* Trace ID；
* OpenTelemetry；
* Prometheus 指标；
* 健康检查；
* 请求耗时；
* 错误分类；
* 下游调用指标。

不能等生产出故障后才补日志和监控。

---

## 2.9 安全贯穿整个流程

安全不只是上线前做一次扫描，而是贯穿：

```text
需求 → 威胁建模
设计 → 权限和数据边界
开发 → 安全编码
提交 → Secret 和依赖扫描
构建 → 镜像扫描和 SBOM
部署 → mTLS、NetworkPolicy、Secret 挂载
运行 → 风控、审计、异常告警
```

---

## 2.10 主分支持续可发布

采用短生命周期功能分支：

```text
main
├── feat/desktop-cloud-ai
├── feat/billing-checkout
├── feat/mobile-draft
└── fix/quota-settlement
```

功能分支应尽量在数天内合并，不长期维护大型分支。

未完成能力通过以下方式隔离：

* Feature Flag；
* 未开放的 Kong Route；
* 内部配置开关；
* 仅测试环境启用；
* 新 API 暂不被客户端调用。

# 三、阶段一：需求发现与产品设计

## 3.1 需求来源

DramaIP 的需求可能来自：

* 用户反馈；
* 产品路线；
* 运营数据；
* 支付和模型成本；
* 技术债务；
* 安全问题；
* 故障复盘；
* 平台能力建设。

需求进入开发前，必须先形成明确的问题定义。

错误示例：

```text
增加一个 AI 功能。
```

正确示例：

```text
桌面端已登录 Pro 用户可以选择 DramaIP Cloud 模型，
提交当前选中章节的有限上下文进行续写，
请求必须经过额度预扣和真实 usage 结算，
网络失败不能影响本地项目数据。
```

---

## 3.2 用户故事

用户故事应描述用户价值：

```text
作为一名购买 Pro 套餐的桌面端用户，
我希望不填写自己的 API Key 就能使用云端模型，
以便快速完成章节扩写。
```

---

## 3.3 验收标准

验收标准必须可测试。

例如桌面端 Cloud AI：

1. 未登录时不能调用云端模型。
2. 套餐无效时返回明确提示。
3. 余额不足时不能调用模型。
4. 每次请求必须生成唯一幂等键。
5. 同一幂等键重复提交不能重复调用模型。
6. 请求上下文不能超过规定字符数。
7. 预检接口不能上传创作正文。
8. 模型调用前必须成功预扣额度。
9. 模型调用完成后必须按真实 usage 结算。
10. 客户端断开后，已经产生的模型成本仍需结算。
11. 云端失败不能修改本地项目。
12. Prompt、Token 和平台 API Key 不能进入日志。

---

## 3.4 非功能需求

每个核心需求还要明确：

* 性能；
* 可用性；
* 并发；
* 安全；
* 数据保留；
* 隐私；
* 成本；
* 容灾；
* 可观测性；
* 灰度和回滚。

AI 功能还必须明确：

```text
最大上下文
最大输出长度
支持模型
请求超时
流式还是非流式
预扣估算方法
usage 缺失时的结算方法
单用户 RPM
单用户成本上限
Provider 失败策略
Prompt 是否保存
```

---

## 3.5 需求产出物

进入技术设计前，应至少形成：

```text
PRD
用户故事
验收标准
页面原型
业务流程图
权限矩阵
数据和隐私说明
成本模型
发布和回滚要求
```

达到以上条件后，需求才进入技术设计阶段。

# 四、阶段二：领域建模与技术设计

## 4.1 确认所属领域

先判断需求属于哪个领域，而不是立即创建新服务。

DramaIP 的主要领域包括：

```text
认证领域          auth
用户资料领域      user
计费订阅领域      billing
额度账本领域      quota
模型代理领域      ai-gateway
通知领域          notification
轻量草稿领域      inspiration
报表投影领域      reporting
管理安全领域      admin
```

例如：

```text
“用户修改昵称”               → user
“验证支付回调”               → billing
“预扣本月 token”             → quota
“调用 DeepSeek 或 OpenAI”    → ai-gateway
“支付成功发送站内信”         → notification
“移动端提交灵感草稿”         → inspiration
“运营查看本月订单”           → reporting
```

---

## 4.2 判断是否需要新服务

只有同时满足以下一项或多项，才考虑新建微服务：

* 有独立的数据所有权；
* 有独立安全边界；
* 有明显不同的扩缩容节奏；
* 有独立部署需求；
* 有独立故障隔离需求；
* 有独立领域规则；
* 有不同的出站调用特征。

例如 `quota-service` 和 `ai-gateway-service` 分开是合理的：

```text
quota-service
├── 强一致账本
├── 数据库并发控制
└── 低延迟额度操作

ai-gateway-service
├── 高耗时模型调用
├── Provider 熔断
├── 独立并发舱壁
└── 成本风控
```

不能因为代码较多就创建新服务。

---

## 4.3 确定调用方式

每次跨服务交互必须明确属于哪一种。

### 同步 HTTP

用于：

* 外部客户端访问；
* 第三方支付 webhook；
* Kong 到 BFF。

### 内部 gRPC

用于：

* BFF 调领域服务；
* billing 调 quota；
* ai-gateway 调 quota；
* Admin BFF 调 reporting；
* Desktop BFF 调 inspiration。

### RabbitMQ 事件

用于：

* 通知；
* 报表；
* 用量聚合；
* 续期；
* 邮件；
* 异步补偿；
* 非关键副作用。

判断原则：

```text
用户必须立即获得结果吗？
├── 是 → 优先同步调用
└── 否 → 优先异步事件
```

---

## 4.4 设计 BFF 边界

DramaIP 使用四个独立 BFF：

```text
bff/web/interface
bff/desktop/interface
bff/mobile/interface
admin/interface
```

每个 BFF 只负责对应客户端的：

* 视图聚合；
* 字段裁剪；
* 下游服务编排；
* 协议转换；
* 客户端差异适配。

禁止 BFF：

* 持有订单业务规则；
* 直接扣减 token；
* 直接访问领域数据库；
* 直接更新订阅；
* 保存业务权威数据；
* 变成万能业务服务。

---

## 4.5 编写 ADR

涉及重要技术决策时，新增 ADR：

```text
docs/adr/
├── ADR-001-采用独立Desktop-BFF.md
├── ADR-002-AI请求采用预扣结算.md
├── ADR-003-Web使用HttpOnly-Cookie.md
└── ADR-004-支付额度采用Saga.md
```

ADR 至少包括：

```text
背景
问题
候选方案
最终决策
优点
代价
安全影响
迁移方案
回滚方案
```

# 六、阶段四：契约优先设计

## 6.1 契约分类

DramaIP 有三类核心契约。

### 外部 HTTP 契约

客户端统一调用：

```http
/v1/...
```

例如：

```http
POST /v1/auth/login
GET  /v1/me/dashboard
POST /v1/subscription/checkout
POST /v1/desktop/ai/chat
POST /v1/mobile/drafts
```

### 内部 gRPC 契约

放置在：

```text
services/api/<领域>/<类型>/v1/
```

例如：

```text
services/api/quota/service/v1/quota.proto
services/api/ai_gateway/service/v1/ai.proto
services/api/bff/desktop/interface/v1/bff.proto
```

### 事件契约

放置在：

```text
services/events/<领域>/v1/
```

例如：

```text
payment_succeeded.proto
subscription_activated.proto
token_usage_recorded.proto
```

---

## 6.2 契约设计顺序

推荐顺序：

```text
业务流程
  ↓
请求与响应模型
  ↓
错误模型
  ↓
身份和权限
  ↓
幂等要求
  ↓
超时和重试
  ↓
API / Proto / Event Schema
  ↓
契约评审
  ↓
生成代码和 SDK
  ↓
客户端与服务端并行开发
```

---

## 6.3 通用字段

关键请求应包含：

```text
request_id
idempotency_key
trace_id
user_id 或 account_id
客户端版本
必要的资源版本
```

事件 Envelope 至少包含：

```text
event_id
event_type
event_version
occurred_at
producer
trace_id
aggregate_id
payload
```

---

## 6.4 错误码设计

错误必须区分：

```text
认证失败
权限不足
资源不存在
参数错误
状态冲突
幂等冲突
余额不足
限流
服务暂时不可用
Provider 超时
内部错误
```

不能把所有错误都返回：

```json
{
  "code": 500,
  "message": "操作失败"
}
```

例如：

```json
{
  "code": "QUOTA_INSUFFICIENT",
  "message": "本周期剩余额度不足",
  "trace_id": "..."
}
```

## 6.5 API 兼容性

允许在 `/v1` 中进行：

* 新增可选字段；
* 新增接口；
* 新增可选参数；
* 扩展枚举但保持旧客户端可处理。

以下变化必须升级到 `/v2`：

* 删除字段；
* 修改字段语义；
* 修改必填规则；
* 修改响应结构；
* 改变状态机含义；
* 改变错误语义。

旧版本进入废弃期时返回：

```http

Sunset: <date>
```

# 七、阶段五：数据模型和一致性设计

## 7.1 确定数据所有权

新增一张表前必须回答：

```text
哪个领域拥有这张表？
哪个服务可以写？
哪些服务可以读？
是否是权威事实？
是否需要历史审计？
是否需要唯一约束？
是否需要事件投影？
```

例如：

```text
订单事实         → billing
额度账户         → quota
AI 请求成本      → ai-gateway
运营订单视图     → reporting
通知已读状态     → notification
管理员审计       → admin
```

---

## 7.2 数据库迁移

迁移文件放在：

```text
services/migrations/<领域>/
```

数据库变更必须：

1. 使用版本化迁移；
2. 先在本地 Compose 验证；
3. 在 CI 创建空数据库验证全量迁移；
4. 验证旧版本升级；
5. 验证回滚或修复方案；
6. 通过 one-shot migration job 执行。

生产环境禁止人工直接修改表结构。

---

## 7.3 数据库兼容升级

数据库变更采用：

```text
Expand
  ↓
Migrate
  ↓
Contract
```

例如字段重命名：

```text
第一版：新增新字段，旧字段保留
第二版：应用同时兼容新旧字段
第三版：迁移历史数据
第四版：所有服务停止读取旧字段
第五版：删除旧字段
```

禁止在新版本上线时直接删除旧字段，导致旧 Pod 运行失败。

---

## 7.4 关键写路径

以下操作必须使用原生 SQL 或明确锁机制：

* token 预扣；
* token 结算；
* token 回滚；
* 订单状态迁移；
* 支付状态迁移；
* outbox 批量锁定；
* 并发冲突判断；
* 依赖 `rows affected` 的更新。

简单 CRUD 可以使用 GORM。

---

## 7.5 Outbox 与 Inbox

生产者在业务事务中同时写入：

```text
业务表
outbox_events
```

事务提交后，relay 将事件发送到 RabbitMQ。

消费者先写入或锁定：

```text
event_inbox
```

处理完成后标记成功。

完整流程：

```text
领域事务
  ├── 更新业务状态
  └── 写 outbox
        ↓
Outbox Relay
        ↓
RabbitMQ
        ↓
Consumer Inbox 去重
        ↓
执行业务副作用
```

该模式保证：

* 数据库提交后事件最终可发送；
* relay 重启后可以续传；
* MQ 重复投递不会重复生效；
* 失败事件可以重试和进入 DLQ。

---

## 7.6 支付、订阅和额度 Saga

核心状态流：

```text
用户创建订单
  ↓
billing 创建 pending order
  ↓
用户完成微信或支付宝支付
  ↓
支付平台调用 webhook
  ↓
billing 验签和幂等检查
  ↓
本地事务：
├── order = paid
├── payment = succeeded
├── subscription = quota_pending
└── outbox 写 payment.succeeded.v1
  ↓
事务提交
  ↓
billing 同步、幂等调用 quota
  ↓
创建当期 token_account
  ├── 成功
  │    ↓
  │  subscription = active
  │    ↓
  │  写 subscription.activated.v1
  │
  └── 失败
       ↓
     subscription = activation_failed
       ↓
     补偿任务重试
       ↓
     长期失败则人工处理或退款
```

任何一步都必须可查询、可重试、可审计。

---

## 7.7 AI 预扣与结算

AI 请求流程：

```text
客户端生成 X-Idempotency-Key
  ↓
Kong 鉴权和限流
  ↓
对应 BFF
  ↓
ai-gateway 持久化请求审计
  ↓
quota 申请预扣
  ↓
调用模型 Provider
  ↓
获取真实 usage
  ↓
quota 多退少补
  ↓
记录 Provider 成本
  ↓
返回响应
```

异常处理：

```text
预扣失败
→ 不调用模型

Provider 调用失败且未产生成本
→ 取消预扣

Provider 已产生成本但结算失败
→ settlement_pending
→ 后台补偿

客户端中途断开
→ 继续完成审计和结算

重复幂等键、相同请求
→ 返回原结果

重复幂等键、不同请求
→ 返回 409
```

## 9.5 Desktop 开发

Desktop 分为：

```text
renderer
→ React UI

electron
→ IPC、本地数据库、文件、Keychain、安全策略、AI 调用
```

重要规则：

* Renderer 不能直接持有 refresh token；
* Renderer 不能直接调用带身份凭据的 Cloud AI Endpoint；
* 云端调用由 Electron 主进程发起；
* refresh token 存系统 Keychain；
* access token 只放内存；
* 本地 SQLite 只保存不可认证的凭据引用；
* 长耗时任务不能阻塞 Electron 主进程；
* 云端错误不能修改本地项目状态。

## 9.6 Mobile 开发

```text

  ↓

  ↓

  ↓
有网络时提交 Mobile BFF
  ↓
服务端按 client_id 幂等写入
  ↓
提交成功后更新本地同步状态
```

refresh token 放 SecureStore，access token 只在运行时内存保存。

网络失败不能删除本地草稿。

## 9.7 Admin 开发

Admin 必须：

* 使用独立管理员登录；
* 使用独立 Admin BFF；
* 每个操作进行 RBAC 校验；
* 敏感操作要求一次性确认；
* 写入不可变审计日志；
* 不直接连接领域数据库；
* 报表数据从 reporting-service 获取。

管理员“处理异常”只能修改运营投影状态，不能直接改写支付、订阅和额度权威事实。

```text
auth-service:1.3.0
auth-service:git-a82d913
```

禁止生产使用：

```text
auth-service:latest
```

```text
第三方 Provider
支付商户配置
域名

日志等级
Feature Flag
```

不能维护不同环境的代码分支。

## 13.3 Kubernetes 部署对象

每个服务通常包括：

```text
Deployment
Service
ServiceAccount
ConfigMap
Secret
HPA
PodDisruptionBudget
NetworkPolicy
ServiceMonitor
```

一次性数据库迁移使用：

```text
Job
```

定时任务或异步消费者按领域独立部署。

## 13.4 部署顺序

推荐顺序：

```text
基础设施和外部依赖
  ↓
数据库 Migration Job
  ↓
领域服务
  ↓
领域 Job / Consumer
  ↓
Reporting
  ↓
各端 BFF
  ↓
Kong Route
  ↓

```

新接口在后端未全部就绪前，不能提前开放 Kong Route。

---

## 13.5 GitOps

生产部署建议使用独立部署仓库：

```text
dramaip-deploy/
├── environments/dev
├── environments/test
├── environments/staging
└── environments/prod
```

CI 只负责生成制品并更新镜像版本。

Argo CD 或同类 GitOps 控制器负责：

```text
读取 Git 期望状态
  ↓
同步 Kubernetes
  ↓
持续检测漂移
  ↓
恢复到声明状态
```

生产环境不应依赖开发人员手动执行大量 `kubectl apply`。

---

## 13.6 灰度发布

普通内部服务可以使用 RollingUpdate。

关键服务使用金丝雀：

```text
新版本 5%
  ↓
观察错误率、延迟和业务指标
  ↓
扩大到 20%
  ↓
扩大到 50%
  ↓
全量
```

适合灰度的服务：

* auth；
* billing；
* quota；
* ai-gateway；
* Web/Desktop/Mobile BFF；
* Kong 配置。

---

## 13.7 数据库发布策略

数据库 Migration 必须先于应用代码部署，并向后兼容旧版本。

正确：

```text
先新增字段
  ↓
新旧版本均可运行
  ↓
发布新应用
  ↓
迁移历史数据
  ↓
停止旧字段使用
  ↓
后续版本删除旧字段
```

错误：

```text
先删除旧字段
  ↓
旧 Pod 立即报错
```

---

## 13.8 回滚策略

回滚分为：

### 应用回滚

恢复上一版本镜像。

### 配置回滚

恢复上一版 Helm/Kong 配置。

### 功能回滚

关闭 Feature Flag。

### 数据修复

通过补偿任务或修复 Migration 完成，不能盲目反向迁移关键账本。

对于支付、订阅和额度数据，原则是：

> 优先追加纠正记录，而不是删除或覆盖历史事实。

# 十六、阶段十四：故障处理与恢复

## 16.1 标准故障流程

```text
告警触发
  ↓
判断用户影响
  ↓
确定受影响服务和版本
  ↓
止损
  ↓
恢复核心业务
  ↓
数据对账和补偿
  ↓
定位根因
  ↓
编写复盘
  ↓
补充测试、监控或架构措施
```

---

## 16.2 常用止损措施

* 回滚版本；
* 关闭 Feature Flag；
* 暂停新订单；
* 暂停某个 AI Provider；
* 降低单用户 RPM；
* 打开熔断；
* 扩容 Consumer；
* 暂停异常任务；
* 将流量切回旧版本；
* 关闭有问题的 Kong Route。

---

## 16.3 支付故障

支付故障优先保护：

* webhook 原始数据；
* 支付平台事件 ID；
* 订单状态；
* 支付状态；
* 订阅状态；
* Outbox；
* Trace ID。

恢复后通过对账任务比较：

```text
支付平台
billing
quota
```

禁止仅根据客户端“支付成功页面”人工修改订阅。

---

## 16.4 额度故障

出现额度不一致时检查：

```text
token_account
token_reservation
token_usage_log
AI request audit
Provider usage
Outbox / Inbox
```

修复时追加：

* 调整记录；
* 补结算记录；
* 补偿事件；
* 审计原因。

不能直接修改 `used_tokens` 后不留历史。

---

## 16.5 AI 成本异常

发生成本突增时：

1. 按 Provider 和模型查看成本；
2. 查看单用户和单 IP 请求；
3. 检查账号是否被盗；
4. 降低 RPM；
5. 暂停高成本模型；
6. 打开用户或 Provider 熔断；
7. 检查重复幂等请求；
8. 检查结算和重试逻辑；
9. 对异常账号撤销会话。

---

## 16.6 故障复盘

复盘至少回答：

* 用户受到什么影响；
* 故障持续多久；
* 如何发现；
* 为什么发生；
* 为什么测试没有发现；
* 为什么监控没有提前发现；
* 为什么恢复耗时；
* 是否产生数据差异；
* 如何补偿；
* 如何防止再次发生。

复盘重点是改进系统，不是追责个人。

# 十八、一个完整功能的实际开发示例

下面以“桌面端使用 DramaIP Cloud 续写章节”为例，串联整套流程。

## 第一步：产品定义

目标：

```text
已登录且有有效套餐的桌面用户，
可以选择 DramaIP Cloud 模型，
使用当前章节的有限上下文进行续写。
```

验收标准包括：

* 不上传整个项目；
* 余额不足不能调用；
* 同一请求不能重复扣费；
* 网络失败不影响本地正文；
* 用户确认后才将结果写入本地项目。

---

## 第二步：技术设计

涉及组件：

```text
dramaip-desktop
Kong
Desktop BFF
auth-service
billing-service
quota-service
ai-gateway-service
PostgreSQL
Redis
OpenTelemetry
```

不需要新增微服务。

---

## 第三步：契约设计

新增或确认：

```http
GET  /v1/desktop/ai/models
POST /v1/desktop/ai/preflight
POST /v1/desktop/ai/chat
```

内部 gRPC：

```text
Desktop BFF → AI Gateway
AI Gateway → Quota Reserve
AI Gateway → Quota Settle
```

---

## 第四步：数据库设计

新增或确认：

```text
ai_gateway.request_audits
ai_gateway.provider_cost_logs
quota.token_reservations
quota.token_usage_logs
```

唯一约束：

```text
user_id + idempotency_key
user_id + request_id
```

---

## 第五步：后端实现

1. Desktop BFF 验证 access token。
2. Desktop BFF 限制上下文大小。
3. AI Gateway 创建持久化请求审计。
4. Quota 原子预扣。
5. AI Gateway 调用 Provider。
6. 获取或估算 usage。
7. Quota 完成结算。
8. 写成本记录。
9. 返回结果。
10. 结算失败进入补偿流程。

---

## 第六步：桌面端实现

1. Renderer 显示模型列表。
2. Renderer 请求主进程执行 Cloud AI。
3. 主进程从本地项目构造有限上下文。
4. 主进程生成 request_id 和 idempotency_key。
5. 主进程调用 Desktop BFF。
6. 返回内容先显示为候选结果。
7. 用户点击采用后才写入 SQLite。
8. 失败只显示错误，不修改原正文。

---

## 第七步：测试

必须覆盖：

* 未登录；
* 套餐失效；
* 余额不足；
* 重复请求；
* 不同 Payload 使用同一幂等键；
* Provider 超时；
* Provider 不返回 usage；
* 结算失败；
* 客户端中断；
* 云端返回成功但用户不采用；
* 本地数据库写入失败；
* Prompt 不进入日志。

---

## 第八步：CI

流水线执行：

```text
Proto 检查
SDK 生成
Go 测试
Desktop 测试
数据库集成测试
E2E
Secret 扫描
镜像扫描
构建服务镜像
构建桌面测试包
```

---

## 第九步：预发布

在 Staging：

1. 使用 AI Test Provider；
2. 验证预扣和结算；
3. 验证真实 Provider 沙箱；
4. 验证 Trace；
5. 验证 Grafana Dashboard；
6. 验证成本告警；
7. 验证回滚。

---

## 第十步：生产灰度

```text
内部账号
  ↓
5% Desktop Cloud 用户
  ↓
20%
  ↓
50%
  ↓
全量
```

观察：

* AI 成功率；
* Provider 延迟；
* 额度结算；
* settlement_pending；
* 成本；
* 用户错误反馈；
* Desktop 崩溃率。

指标异常立即停止扩大流量。

# 二十、Definition of Done

一个功能只有同时满足以下条件才算完成。

## 产品

* 验收标准全部通过；
* 异常提示明确；
* 用户文档已更新。

## 架构

* 服务边界正确；
* ADR 已补充；
* 没有跨 Schema；
* BFF 没有承载领域逻辑。

## 契约

* API 和事件已版本化；
* SDK 已重新生成；
* Breaking Change 检查通过；
* 幂等规则明确。

## 数据

* Migration 已测试；
* 唯一约束和并发保护存在；
* Outbox/Inbox 正确；
* 审计历史完整；
* 对账方式明确。

## 安全

* 权限和资源归属已验证；
* Secret 扫描通过；
* 日志无敏感信息；
* Token 存储符合客户端安全要求；
* Admin 权限独立。

## 测试

* 单元测试通过；
* 集成测试通过；
* 契约测试通过；
* E2E 通过；
* 核心并发测试通过；
* 故障场景已验证。

## 运维

* 健康检查存在；
* Dashboard 存在；
* 告警存在；
* Trace 可贯通；
* 回滚方案可执行；
* Runbook 已更新。

## 发布

* 同一制品逐级推进；
* Staging 验收通过；
* 灰度指标正常；
* Smoke Test 通过。

# 二十二、最终流程总结

DramaIP 的现代微服务全栈开发流程可以压缩为八条主线：

```text
产品线
需求 → 用户故事 → 验收 → 用户反馈

架构线
领域建模 → 服务边界 → ADR → 架构演进

契约线
HTTP → gRPC → Event → SDK → 兼容性管理

开发线
本地环境 → 并行开发 → PR → 代码评审

数据线
数据自治 → Migration → Saga → Outbox/Inbox → 对账

质量线
单元测试 → 集成测试 → E2E → 并发 → 故障注入

交付线
CI → 镜像 → 测试 → Staging → 灰度 → 生产

运行线
Metrics → Logs → Traces → 告警 → 恢复 → 复盘
```

最终形成的完整闭环为：

```text
用户需求
  ↓
产品和架构设计
  ↓
版本化契约
  ↓
客户端与微服务并行开发
  ↓
自动化测试和安全门禁
  ↓
生成不可变制品
  ↓
GitOps 部署 Kubernetes
  ↓
灰度发布
  ↓
业务和技术可观测性
  ↓
对账、故障处理和用户反馈
  ↓
进入下一轮迭代
```

这套流程的最终目标不是“部署很多微服务”，而是让 DramaIP 在保持桌面端本地优先的同时，安全、稳定、可审计地提供账号、支付、订阅、额度和云端 AI 能力。
