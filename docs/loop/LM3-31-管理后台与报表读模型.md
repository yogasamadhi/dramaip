# LM3-31 管理后台与报表读模型

## 交付边界

- `clients/apps/admin` 是独立 React + Vite 应用，不挂载在 C 端 Next/Web 路由。
- Admin 登录使用独立 JWT issuer/audience 与短时服务端 session；浏览器 token 只保留在当前页面内存。
- `admin-bff` 只持有 `admin` schema；它通过 mTLS gRPC 调用 `reporting-service`，不直接读取任一领域表或 `reporting` 表。
- `reporting-job` 消费独立 RabbitMQ queue，持久化公共 envelope 后投影 checkout、支付成功、订阅激活与 token 用量。`source_events` 为重建来源，`user_summaries`、`order_summaries`、`subscription_summaries` 与 `projection_exceptions` 均为可丢弃派生数据。
- 本 loop 不发起真实付款、支付 provider、AI provider 或任何财务账本写入。

## 受控重建

先停止或扩缩容到零个 `reporting-job` consumer，避免与重放并发；`reporting-service` 可以继续提供上一次稳定投影。随后仅为一个 job 实例设置：

```sh
REPORTING_REBUILD_ON_START=true
```

该实例会在开始消费前清空派生表，并按 `reporting.source_events` 的接收顺序重放。成功日志包含 `reporting_read_model_rebuilt`；完成后移除该环境变量、恢复普通 consumer，并检查：

- `GET /v1/admin/reporting/overview` 的 `last_event_at` 与 source event 最新时间一致；
- `GET /v1/admin/reporting/exceptions` 没有新的 open exception；
- job `/healthz` 同时通过 PostgreSQL 与 RabbitMQ 检查。

不要删除 `source_events`，不要把重建命令用于领域库，也不要以重建替代 billing/quota/AI 的事实修复。

## 异常分诊

`projection_exceptions` 表示报表 consumer 无法理解或投影某个已持久化公共事件。运营人员应先用 `event_id`、`event_type` 与 `trace_id` 在领域日志、outbox relay、DLQ 或补偿任务中完成根因修复。后台“确认已处理”流程为：

1. 具备 `reporting.write` 的管理员填写处置说明；
2. Admin BFF 创建五分钟一次性 `reporting.exception.resolve` 确认并审计；
3. 同一管理员消费确认，Admin BFF 调 reporting gRPC 把异常标为 `resolved`；
4. 此动作只关闭投影告警，绝不改变订单、订阅、额度、退款、webhook、outbox 或成本账本。

如果 reporting 下游不可用，确认消费审计会保留为 `admin.reporting.exception.resolve.requested`；恢复服务后应重新发起一次确认，不能绕过确认直接改表。

## 生产 smoke

在健康、隔离环境中，用离线创建的最小权限测试管理员：

1. 从独立 Admin origin 登录，确认刷新页面后需要再次登录；
2. 用 C 端 JWT 请求 `/v1/admin/me`，期望 `401`；
3. 查看 overview、用户、订单、订阅、异常与 audit，确认没有跨 schema 数据库凭据；
4. 对测试投影异常执行一次确认关闭，审计中应有 confirmation created/consumed/requested；
5. 执行一次受控重建，确认重复事件不会重复累计 token。

生产必须使用 operator-managed Admin keyset、mTLS Secret 与独立 `POSTGRES_REPORTING_PASSWORD`；仓库不创建默认管理员，也不保存真实密码、token、私钥或支付凭据。
