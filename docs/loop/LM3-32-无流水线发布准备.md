# LM3-32 无流水线发布准备

本项目按维护者要求不启用 Gitee 托管流水线。发布由经批准的运维人员在受控工作站执行；脚本不保存凭据、不默认推镜像，也不会自动访问集群。

`preflight.sh` 默认只接受已同步、无改动的 `main`。开发者验证脚本本身时可临时设置
`DRAMAIP_PREFLIGHT_ALLOW_DIRTY=1`，该绕过不得用于任何 staging 或生产发布。

## 顺序

1. 在干净、已同步的 `main` 执行 `bash deploy/release/preflight.sh`；
2. 由平台团队预先创建 staging namespace、Kong Ingress Controller（`IngressClass=kong` 与 `KongPlugin` CRD）、外部 PostgreSQL/Redis/RabbitMQ/OTel，以及 HTTPS 可达的 OCI registry。该准备不是应用发布脚本的隐式副作用；
3. 由 Secret Manager/External Secrets 创建 staging runtime、auth JWT、admin JWT、internal mTLS 四个 Secret，以及 `kubernetes.io/dockerconfigjson` registry pull、`kubernetes.io/tls` Ingress TLS Secret；不要把 Secret 值写入 Helm values；
4. 如需在另一台受控构建/发布主机上操作，执行 `DRAMAIP_WORKSPACE_SYNC_AUTHORIZED=1 DRAMAIP_RELEASE_HOST=<operator@release-host> bash deploy/release/sync-release-workspace.sh`。它只同步 `dramaip-platform` 源码并记录 Git commit，明确排除 `.env`、私钥、`docker-data`、依赖缓存和构建产物；目标目录仅供该脚本管理，会以 `--delete-excluded` 移除这些文件，不能存放 kubeconfig 或任何凭据；
5. 在受控工作站设置 `IMAGE_REGISTRY=<approved-registry/project>` 后执行 `bash deploy/release/staging-prerequisites.sh staging`。它只读检查 namespace、发布权限、Kong、六类 Secret 的存在和类型、以及 registry 的 HTTPS `/v2/` 可达性；401 代表仓库可达且需要已登录操作员，不会在此步骤使用凭据；
6. 用不可变 Git SHA 设置 `IMAGE_TAG`，由已登录的镜像仓库操作员执行 `bash deploy/release/build-images.sh`；只有显式 `PUSH_IMAGES=1` 才会推送；
7. 在扫描工作站以同一不可变 tag 执行 `bash deploy/release/scan-images.sh`；高危或严重漏洞（不含已无修复版本的条目）必须为零；
8. 在受控工作站设置环境专属基础设施地址、精确 Web/Admin Origin、不可变镜像 tag（生产还必须显式指定全部 Secret 名）后，执行 `DRAMAIP_RELEASE_AUTHORIZED=1 IMAGE_REGISTRY=<approved-registry/project> IMAGE_TAG=<immutable-git-sha> DRAMAIP_POSTGRES_HOST=<host> DRAMAIP_REDIS_ADDR=<addr> DRAMAIP_RABBITMQ_HOST=<host> DRAMAIP_RABBITMQ_PORT=<port> DRAMAIP_OTEL_ENDPOINT=<url> DRAMAIP_PUBLIC_INGRESS_HOST=<host> DRAMAIP_WEB_ORIGIN=<https-origin> DRAMAIP_ADMIN_ORIGIN=<https-origin> bash deploy/release/helm-release.sh staging apply`；脚本会只读确认 runtime、JWT、mTLS、registry pull 和 TLS Secret 均已由 Secret Manager/External Secrets 提供；
9. 变更单批准限流探测的请求量后，执行 `DRAMAIP_SMOKE_AUTHORIZED=1 SMOKE_BASE_URL=<staging-api-base-url> SMOKE_RATE_LIMIT_TEST=1 SMOKE_RATE_LIMIT_ATTEMPTS=<limit-plus-one> bash deploy/release/staging-smoke.sh staging`，验证 Helm/migration 成功、Deployment rollout、mTLS Secret 挂载、公开健康和 Kong 限流。真实支付仍被跳过；
10. 出现错误时以已审计的 Helm revision 执行 `DRAMAIP_RELEASE_AUTHORIZED=1 bash deploy/release/helm-release.sh staging rollback <revision>`。应用回滚不回滚已成功执行的向后兼容 migration。

生产使用相同流程，但必须先通过 staging smoke、使用 operator-managed production Secrets，并由独立变更单批准。
`helm-release.sh production apply` 还要求显式提供 `DRAMAIP_RUNTIME_SECRET`、
`DRAMAIP_AUTH_JWT_SECRET`、`DRAMAIP_ADMIN_JWT_SECRET`、`DRAMAIP_INTERNAL_MTLS_SECRET`、
`DRAMAIP_IMAGE_PULL_SECRET` 和 `DRAMAIP_INGRESS_TLS_SECRET`，因此不会回退到 chart 内的占位值。

## 经授权的临时隔离 staging

当常规 staging 的外部依赖、Secret Manager 或 OCI registry 尚未就绪时，可以在**受维护者
单次明确授权**后使用 `temporary-staging.sh` 完成一次私有 LAN 验收。它不是生产路径，也不
会修改普通 staging 的 values：仅允许 `dramaip-staging*` 命名空间、`dramaip-staging.local`
本地镜像标签、短期随机凭据/证书、`emptyDir` 依赖和 worker 节点选择；支付对接与账单对账
开关保持关闭，AI Provider 指向不可路由本地地址。

该流程必须在受控构建主机运行，且将 Kong Chart 固定为已核验的 `ingress-0.24.0.tgz`
（SHA-256 `670053e7ae58f0b09951f9edc3ab4dea6cab59c970efb6080b3082f63b4fc1f2`）。若目标
主机 DNS 不能解析 Chart 仓库，只能从已核验工作站同步该归档；禁止通过改 DNS、关闭 TLS
验证或替换为未核验 Chart 来绕过问题。

临时流程依次为：`bootstrap` 创建专属 namespace 和 2 天有效的临时 Secret；`install-kong`
只在 worker 上安装 Kong 并使用经检查未占用的 32080/32443 NodePort；构建后的 17 个应用
镜像用 `archive-images` 打包；`preload-images` 通过一个在 `192.168.2.0/24` 私有 LAN 上短暂
存在、SHA-256 校验的 HTTP 服务加载到每台 worker 的 Docker 缓存，随后立即删除带 Docker
socket 的 DaemonSet。预加载的 marker 与 `IMAGE_TAG` 必须匹配，`staging-prerequisites.sh`
才会放行。该 loader 是唯一使用 host Docker socket 的对象，限定在专属 namespace 和 worker
selector，且不执行全局 image prune。

临时发布需同时设置：

```bash
export DRAMAIP_TEMPORARY_STAGING_AUTHORIZED=1
export DRAMAIP_TEMPORARY_STAGING_INFRA=1
export IMAGE_REGISTRY=dramaip-staging.local
export IMAGE_TAG=<immutable-git-sha>
# 目标主机将 Helm 安装在用户目录而非默认 PATH 时：
export DRAMAIP_HELM_BIN="$HOME/.local/bin/helm"
```

再以 `DRAMAIP_RELEASE_AUTHORIZED=1` 调用 `helm-release.sh staging apply`。若入口 DNS 不存在，
`staging-smoke.sh` 支持 `SMOKE_CA_FILE=<temporary-ingress-cert>` 和
`SMOKE_CURL_RESOLVE=api.staging.internal:32443:<node-ip>`，仍执行 CA 验证，禁止用 `-k`。
验收、回滚演练完成后先 `helm-release.sh staging rollback <revision>`，再依次执行
`remove-images` 和 `teardown`（均要求 `DRAMAIP_TEMPORARY_STAGING_CLEANUP_AUTHORIZED=1`），并
删除构建主机的 Docker archive。应用精确标签会被移除，但不会运行可能影响其他工作负载的
全局 Docker prune；Kong CRD 保留到运维人员确认没有其他 Kong 使用方后再单独处理。

## 渐进发布边界

`helm-release.sh apply` 是带健康等待和 `--atomic` 的标准滚动发布，不把它描述为流量灰度。
真正的灰度必须由集群团队预先提供 Kong Gateway 的受控流量分割能力，并在变更单中记录：
候选 revision、流量比例、观测窗口、错误率/延迟阈值、扩大或回退的负责人。没有该能力时，
只能执行标准滚动发布，不能声称完成 canary 验收。

应用回退使用已审计的 Helm revision；已成功执行的向后兼容 migration 不回退。任何破坏性
migration 均须等待 LM3-33 的备份恢复验证后再另行审批。

`staging-smoke.sh` 对每个当前工作负载检查其挂载的 mTLS Secret 名称，并要求实际观察到
Kong 的 HTTP 429。它不替代服务间 TLS 握手的人工证据：运维人员仍须在隔离 staging 中
保留一次“无客户端证书被拒绝、正确工作负载证书被接受”的 gRPC 记录及 trace ID。
