# LM3-10 数据库角色验证与回滚

LM3-10 以一个 DDL migration identity 和六个无 DDL 权限的运行 identity
收敛 PostgreSQL 权限。运行 identity 不拥有 schema 或表，只获得自己的 schema
上的 `USAGE` 和 DML/sequence 权限；跨域数据只能经 API、事件或 read-model 流转。

| 领域 workload | PostgreSQL login | 唯一可访问 schema |
| --- | --- | --- |
| auth | `dramaip_auth` | `auth` |
| user | `dramaip_user` | `user_profile` |
| billing、billing-job | `dramaip_billing` | `billing` |
| quota、quota-job | `dramaip_quota` | `quota` |
| ai-gateway | `dramaip_ai_gateway` | `ai_gateway` |
| notification、notification-job | `dramaip_notification` | `notification` |
| migration job | `POSTGRES_USER` | 所有 schema（DDL only） |
| web-bff | 无 database login | 无 |

## 部署约束

- migration job 的 `POSTGRES_USER` 必须是受控 DDL 身份。首次自动创建/轮换运行
  role 时，该身份需要 `CREATEROLE`；已经由 DBA 预创建 role 时，将
  `DB_ROLE_BOOTSTRAP=false`（Compose）或 `migrations.bootstrapRuntimeRoles=false`
  （Helm）。
- 生产环境为六个 `POSTGRES_*_PASSWORD` 分别提供不同密码。Helm 的 runtime
  Deployment 不再通过 `envFrom` 获取完整数据库 Secret，而是只引用自己的密码键。
- `POSTGRES_DSN` 如被使用，必须是 `postgres://` 或 `postgresql://` URL；运行时会
  以领域 role 覆盖其中的 user/password。关键值格式会被拒绝，避免悄然退回 DDL 身份。
- 普通服务启动时执行 role 自检：当前 user 必须与领域 role 相同，自己的 schema
  必须可 `USAGE`，所有其他领域 schema 必须不可 `USAGE`。检查失败即拒绝启动。

## 验证

无需流水线。常规 Gitee 提交前，在一个一次性、隔离的 PostgreSQL 测试实例执行：

```bash
cd dramaip-platform/services
POSTGRES_ROLE_TEST_DSN='postgres://ddl_user:password@localhost:5432/dramaip_role_test?sslmode=disable' \
  make db-role-matrix
```

该测试会运行全部 migration、创建/轮换六个共享 login，并让每个 login 实际查询一个
外域表；外域查询必须失败。因为 login 是 PostgreSQL cluster 级对象，测试实例必须
独立或明确允许 role 密码被测试轮换；不能指向生产库或多人共用开发实例。DDL 用户
还必须拥有 `CREATEROLE`。基础回归仍使用：

```bash
GOCACHE=/tmp/dramaip-go-build go test ./...
docker compose --env-file services/.env -f deploy/docker-drama/docker-compose.yaml config --quiet
helm template dramaip-platform deploy/helm/dramaip-platform \
  -f deploy/helm/dramaip-platform/values-dev.yaml \
  --set devInfra.persistence.hostPathBase=/tmp/dramaip-helm >/dev/null
```

## 回滚边界

本 migration 只添加运行 login 并收紧权限，不删除业务数据、schema 或表。服务镜像和
部署配置可以整体回退：旧版本继续使用每个 workload 已覆盖的 `POSTGRES_USER`/
`POSTGRES_PASSWORD`，仍只能访问本领域 schema；Web BFF 没有直连数据库的回退依赖。

若必须临时撤销权限变更，先停止受影响 workload，再由 DDL 身份基于受控变更单显式
`GRANT` 所需 schema/table 权限并记录审批；禁止把 runtime role 提升为 superuser 或
把 DDL 密码注入普通服务。恢复时重新执行 `018_database_role_isolation.up.sql` 的 revoke
与 grant 矩阵，随后运行上述 role-matrix 测试。
