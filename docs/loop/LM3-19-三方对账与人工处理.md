# LM3-19 三方对账与人工处理

## 账本边界和对账范围

对账由 `billing-job` 定时执行，默认每小时扫描至多 100 个已支付订单，并以持久 cursor 轮转已支付
账本，避免每轮只覆盖最新或最旧订单。它比对 billing
领域中的 `orders`、`payments`、`subscriptions`、已验证的渠道 webhook 证据，以及 quota
领域中同一订阅、同一起始周期的 token account。billing-job 不读取 quota schema；它只通过
`QuotaService.GetPeriodAccount` 读取精确自然键。生产启用 mTLS 时，该 RPC 额外限制为
`billing-job` 证书主体，不能被一般 BFF 调用。

下列差异会作为 case 记录：支付记录缺失或重复、支付渠道/金额/币种不一致、缺订阅、异常订阅
状态、真实渠道缺少本地已验签/主动查询证据、quota 查询失败、缺周期账户、账户快照不一致和已激活
订阅对应的非 active quota 账户。发现过程不会修改订单、支付或订阅。

`billing.reconciliation_runs` 保存运行汇总；`reconciliation_items` 保存当前待办 case；每次发现
都向 `reconciliation_observations` 追加不可变快照，故重跑不会覆盖历史差异事实。人工操作只写入
不可变 `reconciliation_actions`，并要求操作者、原因和幂等键。

## 人工处置接口

接口仅绑定 billing-job 的内网 HTTP 端口：Compose 为容器内部端口，Helm 不为 job 创建 Service 或
Ingress。设置 `RECONCILIATION_OPERATOR_TOKEN` 前，所有接口返回 `503`，不会因空配置开放。设置后须以
`Authorization: Bearer <operator-token>` 访问，所有 JSON 响应均为 `Cache-Control: no-store`。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/internal/reconciliation/runs` | 手动运行；body 必须含 `requested_by`。 |
| `GET` | `/internal/reconciliation/runs/latest` | 读取最近一次运行汇总。 |
| `GET` | `/internal/reconciliation/items?status=open&limit=100` | 读取按严重级排序的 case。 |
| `POST` | `/internal/reconciliation/items/{item_id}/actions` | 提交受控操作。 |
| `GET` | `/internal/reconciliation/metrics` | 读取本进程运行数、发现数和失败数。 |

操作 body：

```json
{
  "action": "retry_quota_provision",
  "actor": "ops@example.com",
  "reason": "paid order has no period entitlement",
  "idempotency_key": "reconcile-20260713-001"
}
```

允许的 action 和效果：

- `retry_quota_provision` 仅适用于 `missing_quota_account`。它按 subscription + period 的自然键调用现有
  幂等 quota 创建 API；如订阅仍在 `quota_pending` / `activation_failed`，再复用已有 Saga 激活事务。
- `manual_confirm` 只确认操作者已完成外部核验并关闭 case；不伪造 payment、退款或渠道成功状态。
- `request_refund` 与 `freeze_entitlement` 只将 case 放入 `manual_review` 并追加审计。它们不会发起真实
  渠道退款或静默变更额度，必须通过后续受控运营流程处理。

这一区分是故意的：对账 job 没有被授予自行修正财务账本的权限，且没有阈值/开关时禁止自动金融动作。

## 配置、回滚和核验

```bash
# 关闭定时扫描；已有审计和人工接口不会删除。
BILLING_RECONCILIATION_ENABLED=false

# 默认值；按吞吐调整，但保持有限批次。
BILLING_RECONCILIATION_INTERVAL=1h
BILLING_RECONCILIATION_BATCH_SIZE=100

# 仅在运维网络、Secret 或受控终端配置，绝不提交。
RECONCILIATION_OPERATOR_TOKEN=...
```

Helm 使用 `config.billingJob.reconciliationEnabled`、`reconciliationInterval` 和
`reconciliationBatchSize`；操作令牌来自 chart 的现有 Secret 中
`RECONCILIATION_OPERATOR_TOKEN` 键。回滚时可先关闭 scheduler 或回滚 billing-job/ quota-service 镜像；
迁移 `027_billing_reconciliation` 是纯追加的，不删除支付、订阅、额度或审计历史。

自动化验证：

```bash
cd dramaip-platform/services

GOCACHE=/tmp/dramaip-go-build go test ./pkg/platform ./app/quota/service/... ./app/billing/job/...

# 需要新的隔离 PostgreSQL（DDL 身份需能创建运行时 role）。
POSTGRES_BILLING_RECONCILIATION_TEST_DSN='postgres://ddl_user:password@localhost:5432/dramaip_billing_reconciliation?sslmode=disable' \
  make billing-reconciliation-integration
```

集成夹具验证缺额度、重复支付、金额不符、重跑不重复建 case、每次 observation 留痕、人工退款请求
不静默改权益，以及缺额度补偿的幂等路径。quota state-machine 集成测试还验证 exact period lookup。

## 渠道账单限制

2026-07-13，项目所有者明确要求跳过真实付款后继续。因此本 loop 没有也不会伪造微信/支付宝商户
账单下载、真实退款或公网回调证据。对真实渠道，当前周期性检查使用已保存的验签 webhook 与主动查询
证据；缺证据会形成 `provider_evidence_missing` case。未来启用真实商户凭据时，必须补充官方渠道账单
拉取适配器并完成真实沙箱 E2E，才能把它作为真实渠道结算或生产支付开通证据。
