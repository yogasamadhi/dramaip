# Loop Engineering Rules

本文档定义一套面向 Git 远端协作项目的 Loop Engineering 执行规则。适用于功能开发、
迁移、重构、验证补齐、文档收口、发布准备和其他可切片工程任务。

Loop Engineering 的核心价值是可以无人值守地持续推进整张 LOOPMAP，直至所有 loop
真正完成。单个 loop 的一次执行未成功，不是整批任务停住的理由：执行器必须保存可
审计现场、记录未完成点和明确的再进入动作，快速收束本次尝试并继续后续 loop；完成
一轮遍历后，再自动回到未完成项继续推进。

本规则默认项目使用 Git 分支、远端同步和远端推送记录工程结果。若项目不使用 Git，
必须先在项目本地规则中定义等价的分支隔离、变更记录、远端同步、远端发布和清理
流程；在等价流程明确前，不应套用本标准流程宣告 loop 完成。

项目可以在本规则之外补充本地目录约束、验证命令、分支策略和发布流程；这些补充
应放在项目自己的 LOOPMAP、CONTRIBUTING、README 或执行说明中，不应写成本通用
规则的前提。

## 1. 核心定义

Loop Engineering 是一种小闭环工程方法。一个 loop 是围绕单一可验收结果形成的、
可审查、可验证、可提交、可回滚的最小独立工程单元。这里的“最小”指最小的独立
验收结果或需要隔离的风险边界，不是最小的文件修改、实现步骤或测试动作。若拆分后
的子块不能各自形成可独立验收且可安全保留的结果，并且没有命中第 3.3.3 节任一拆分
条件，就应把它们保留为同一 loop 的内部 checklist。

在满足审查、验证和回滚要求的前提下，应避免没有独立验收结果或风险边界的微型
loop。默认优先选择较完整的端到端能力块，减少重复读取上下文、创建分支、运行相同
验证、提交、合并和记录完成状态的成本。

每个 loop 必须满足：

1. 只服务一个明确目标。
2. 有清晰范围、验收标准和验证方式。
3. 完成后审查 diff，并运行与风险匹配的验证。
4. 使用版本控制记录结果；完成前必须同步远程并推送远端。
5. 一次尝试未完成时保留可审计、可恢复的现场，记录未完成点、证据和下一次动作。
6. 无论本次结果是 `done` 还是 `partial`，都必须有限时地收束尝试，不等待人工输入，
   并把调度权交还给整批执行器。

一个 loop 的交付物可以是一个功能点、一个迁移切片、一个验证入口、一个文档闭环
或一个发布关卡。验证入口或文档只有在本身能独立交付和验收时才单独成 loop；同一
结果所需的代码、测试、配置、接线和文档通常应在同一个 loop 中收口，即使它们跨越
多个目录、模块或技术层。不要把多个无关目标混进同一个 loop。

多个 loop 默认按顺序逐个尝试，禁止把多个 loop 混在同一个分支或 diff 中一次性实现。
这里的顺序约束针对“尝试边界”，不要求前一个 loop 必须 `done` 才能开始下一个：前一
个 loop 成功时走完合并、推送和清理流程；未成功时走完第 2.13 节的未完成收束流程，
状态记为 `partial`，然后立即调度下一个可推进的 loop。整批执行器必须持续遍历并重试
`todo` / `partial` 项，不能把任一单次失败升级为整批任务的停止条件。

已经具有独立交付、独立验收或独立风险边界的多个 loop，不应为了减少数量而批量
合并：这会让范围失控，使审查、验证和回滚失去清晰边界。反过来，也不应把同一
验收链路中的实现步骤预先拆成多个微型 loop。平衡原则是：在一次聚焦 review 能够
理解、一次完整验收能够判断、一次回滚能够撤销的范围内，优先保留较大的能力闭环；
命中第 3.3.3 节任一拆分条件时，应在相应边界拆分。

## 2. 标准 Loop 流程

每次 loop 尝试严格按以下顺序执行。同一时刻只在一个 loop 的隔离分支或 worktree 中
产生改动；当前尝试已成功闭环或按第 2.13 节完成未完成收束后，立刻开始下一个可推进
项。`partial` 是可重试状态，不是暂停状态，也不存在 `blocked` 终态。

### 2.0 首次 loop 启动 Gate：先发布项目已有代码

本节只在整张 LOOPMAP 启动、首次 loop 开始前执行一次。后续 loop、`partial` 收束、
sweep 重试和恢复执行都不得再次进入本 Gate，也不得因本节增加任何等待或阻塞条件。

首次 loop 开始前，检查项目是否存在尚未 add、commit 或 push 的既有变更，包括已跟踪
修改、应纳入版本控制的未跟踪文件、暂存区内容和本地尚未推送的 commit。代码、测试、
配置、迁移和文档都在检查范围内。

若存在既有变更，必须先审查其 diff、补齐当前代码所需实现和验证、排除凭据与生成物，
再按真实目标完成 `add`、`commit`、远端同步和 `push`。这次提交属于首次 loop 之前的
基线收口，不计入任何 loop，也不得与首次 loop 的改动混为同一提交。

启动检查至少包括：

```bash
git status --short --branch
git diff
git diff --cached
git log --oneline @{upstream}..HEAD
```

发现待发布代码后，按项目实际范围执行：

```bash
git add <existing-change-files>
git diff --cached --check
git diff --cached
git commit -m "<describe existing completed work>"
git fetch origin
# 按项目规则安全合并或变基远端新提交，并重新验证
git push origin <current-branch>
git status --short --branch
```

只有首次基线代码已经提交、推送，且工作区无未解释改动后，才开始首次 loop。不得用
`git stash`、临时挪走文件或把既有改动夹带进首次 loop 来伪造干净基线；也不得提交
凭据、缓存、构建产物或明确属于其他人的未授权改动。

首次 loop 一旦开始，本 Gate 永久通过。此后严格恢复第 2.1 至 2.14 节的标准流程：某个
loop 验证、同步或推送失败时，按第 2.13 节快速收束为 `partial` 并继续下一个可推进项，
绝不能以“重新满足首次发布 Gate”为由停住后续 loop。

### 2.1 明确本轮目标

开始前写清楚：

- 本 loop 要完成什么。
- 哪些文件、模块、接口或文档在范围内。
- 哪些内容明确不在范围内。
- 为完成同一结果需要哪些内部 checklist 项。
- 如何判断完成。
- 要运行哪些验证命令或人工检查。
- 本次未完成时如何保全现场、判断无进展并快速退出尝试。
- 下一次尝试可直接执行的动作、所需证据和自动降级方案。

如果范围包含多个可独立交付、独立验收或独立回滚的结果，或者无法在一次聚焦 review
中理解，应先按第 3.3 节拆分。不要仅因为跨文件、跨模块、跨前后端，或同时需要代码、
测试和文档，就创建多个 loop。

### 2.2 检查工作区并同步目标分支

开始前检查当前状态，并记录当前所选分支为本 loop 的目标分支：

```bash
git status --short --branch
git branch --show-current
```

如果工作区已有未提交变更，先判断它们是否属于当前 loop。不要覆盖、回退或整理
他人的未完成改动，除非得到明确授权。

开始前必须同步目标分支的远程状态，并让目标分支处在远端最新提交上：

```bash
git fetch origin
git merge --ff-only origin/<target-branch>
git status --short --branch
```

如果无法快进，说明本地和远端可能已经分叉，应按项目约定合并或变基并重新验证。
禁止用会丢失他人提交的方式推进，例如未经明确授权的 `git reset --hard`、强推或
覆盖远端历史。如果在本次尝试内不能安全解决，按第 2.13 节记录分叉证据和再进入
命令，收束当前尝试并继续整批任务，不得停在交互式 Git 命令或等待维护者回复。

### 2.3 创建 loop 开发分支

从已同步的目标分支新建一个专用开发分支：

```bash
git switch -c loop/<loop-id>-<short-topic>
```

后续开发、验证、审查和提交都在该 loop 开发分支上完成。不要直接在目标分支上开发
本 loop，除非项目本地规则明确要求或维护者明确授权。

loop 分支在预计能一次闭环时可作为本地临时分支，不必单独推送。若一次尝试成为
`partial`，必须保留该分支；有可用远端时应推送同名分支或项目约定的 checkpoint
引用，避免挂机进程或机器退出后丢失现场。每个 loop 的完成记录仍以目标分支推送成功
为准，checkpoint 推送不得伪装成完成。

重试 `partial` loop 时应复用其原分支或 worktree，并从执行记录中的 `Next attempt`
继续，不要重复创建同名分支或从头重做已经验证可信的工作。

如果创建开发分支前发现目标分支状态不干净，应先按 2.2 的规则处理工作区，不要把
无关未提交变更带入新分支。

### 2.4 执行单个 loop

执行时必须控制范围：

- 只改本 loop 所需文件。
- 可以按内部 checklist 分步实现，但只有整体验收通过后才把 loop 标记为完成。
- 不顺手做无关重构。
- 不引入与目标无关的依赖、格式化风格或目录结构变化。
- 不提交缓存、构建产物、本地虚拟环境、密钥或临时文件。
- 对兼容层、旧目录、公共协议和共享工具保持额外谨慎；除非本 loop 明确覆盖，
  不扩大它们的行为面。
- 连续动作不再产生新证据或进展时，停止在本次尝试中重复相同命令；记录结果，选择
  可自动执行的替代路径，或按第 2.13 节收束后留待下一轮重试。

### 2.5 本地验证

每个 loop 至少运行与变更直接相关的最小验证。验证命令由项目技术栈决定，常见
示例包括：

```bash
git diff --check
npm test
npm run typecheck
pnpm test
pnpm run typecheck
pytest
python3 -m compileall <package>
cargo test
mvn test
```

验证范围按风险扩大：

- 文档-only loop：至少检查 diff、链接、命令和路径是否可信。
- 单模块 loop：运行该模块测试、编译检查或类型检查。
- 共享库、公共协议、迁移边界、认证、数据写入或并发逻辑：运行相关集成测试和
  回归测试。
- 普通跨模块能力块：覆盖受影响模块、接口边界和端到端验收链路；不要仅因跨模块就
  自动运行无关的全项目回归。
- 发布、升级、兼容层，或改变共享基础设施、关键公共路径的跨模块 loop：运行项目
  约定的完整回归或发布前检查。

如果某项验证失败或无法运行，必须记录命令、关键输出、原因、影响范围、替代检查和
下一次动作。能在当前尝试内快速修复则继续；否则将本 loop 收束为 `partial` 并调度
后续 loop，不能让测试进程、人工 smoke 或问题调查无限占用整批执行器。

包含多个内部 checklist 项时，开发过程中优先运行直接受影响的最小测试；到达整体验收
点后再运行本 loop 的完整验证包。除非内部步骤改变了共享协议、安全边界、测试基础
设施或已经暴露回归，不要为每个机械步骤重复运行相同的完整回归。

### 2.6 审查 diff

成功提交或保存未完成 checkpoint 前必须审查：

```bash
git status --short
git diff --check
git diff
```

如果 loop 分支已经包含内部检查点 commit，还必须审查它相对本轮目标分支的累计 diff；
不能只看最后一段未提交改动：

```bash
git diff --check <target-branch>...HEAD
git diff <target-branch>...HEAD
```

确认：

- 没有未预期文件。
- 没有凭据、token、密码、cookie、私钥或真实 `.env`。
- 没有误提交 `.venv`、`node_modules`、`__pycache__`、`.DS_Store`、构建产物或缓存。
- 没有误改用户、队友或远端合入的无关内容。
- 文档中的路径、命令、配置项和验收条件能对应真实项目状态。

### 2.7 提交

每个 loop 的开发分支默认使用一个功能 commit。较大的能力块如需保留可审查的内部
检查点，可以使用少量、顺序清晰的功能 commit；不要仅为了维持“一 loop 一 commit”
而把同一验收链路拆成多个 loop。提交信息应说明本 loop 的目标或动作：

```bash
git add <files>
git commit -m "loop: add health check smoke test"
```

提交应满足：

- 开发分支上的一个或一组紧密相关的功能 commit 对应一个可解释的 loop。
- 每个 commit 边界清晰，整个 loop 可作为一个单元审查、验证和回滚。
- 不把“未完成”状态提交成完成状态。

本次尝试不能完成但存在值得保留的安全改动时，可以在 loop 分支创建明确标识为
checkpoint 的 commit，例如 `loop(<loop-id>): checkpoint <unfinished-topic>`，并优先
推送 loop 分支。checkpoint 不得合并到目标分支，不计作 loop 完成；执行记录必须列出
已完成部分、未完成部分、验证结果和下一次入口。若改动不安全、不可编译或没有保留
价值，应保持在隔离 worktree 中或按项目规则仅撤销本 loop 自己的改动，不得污染目标
分支，也不得删除他人改动。

如果后续使用 `git merge --no-ff` 合并，目标分支会额外产生一个 merge commit。这个
merge commit 只用于记录本 loop 分支的合入边界，不应混入新的功能改动。

非 Git 项目必须先按本文开头定义等价流程；否则不能把 loop 标记为 `done`。

### 2.8 同步目标分支

loop 开发分支完成提交、满足验收并通过审查后，必须先切回本 loop 开始时记录的目标
分支，并再次同步远程最新状态：

```bash
git switch <target-branch>
git fetch origin
git merge --ff-only origin/<target-branch>
git status --short --branch
```

如果目标分支无法快进，说明 loop 执行期间远端和本地目标分支已经分叉。必须按项目
约定解决分叉并重新运行受影响验证，不能直接覆盖远端历史。若不能在本次尝试安全
解决，则不得合并；转入第 2.13 节收束并继续下一项。

### 2.9 合并回目标分支

确认目标分支已经同步到远端最新后，把 loop 开发分支合并回来：

```bash
git merge --no-ff <loop-branch>
```

若出现冲突，只解决本 loop 范围内的问题；冲突解决后必须重新运行受影响验证。合并
完成前，不应宣告本 loop 完成。无法安全解决的冲突应中止本次合并、保全 loop 分支，
按第 2.13 节记录后继续整批任务；不要停在等待输入的冲突状态。

如果项目采用 squash merge、rebase merge 或其他合并策略，应遵循项目本地规则，但
仍必须满足：本 loop 在专用分支开发，完成后回到开始时的目标分支，并把结果合入该
目标分支。

squash merge 或 rebase merge 可能让 Git 无法识别 loop 分支已经被普通合并。采用
这类策略时，必须在完成记录中说明合并策略，并在清理分支前确认 loop 分支内容已经
等价进入目标分支。

### 2.10 验证合并结果

合并回目标分支后，必须检查目标分支状态和最终 diff：

```bash
git status --short --branch
git diff --check origin/<target-branch>...HEAD
git diff origin/<target-branch>...HEAD
```

同时重新运行受影响验证。若远端变更与当前 loop 无关，至少重新运行本 loop 的最小
验证；若涉及共享模块、测试基础设施或发布流程，运行更大范围回归。

若合并结果验证失败，不得推送，也不得让失败结果留在目标分支后直接开始下一 loop。
应先确认本次 merge commit 和目标分支基线，使用项目批准的非破坏性回滚方式撤销本次
合并（普通 merge 默认可创建对应的 revert commit），验证目标分支已恢复，再保留 loop
分支并按第 2.13 节收束。不得借此撤销远端新提交、他人提交或其他 loop 的结果。

### 2.11 推送远程

合并回目标分支并验证通过后，必须把目标分支推送到远端：

```bash
git push origin <target-branch>
```

推送后确认本地与远端对齐：

```bash
git status --short --branch
```

目标状态应无未解释的 ahead/behind。若无法推送，本 loop 不能标记为完成；必须记录
原因、当前 commit、远端状态和下一步处理方式，状态转为 `partial`，收束当前尝试后
继续下一项。后续 sweep 必须重试推送，不能因为代码已经在本地合并就跳过该 loop。

### 2.12 清理 loop 分支

目标分支推送成功，并确认本地与远端对齐后，必须删除本地 loop 分支。默认使用安全
删除：

```bash
git branch -d <loop-branch>
```

如果 loop 分支曾推送到远端，且不再需要远端 review、排查或续做，也必须删除远端
loop 分支：

```bash
git push origin --delete <loop-branch>
```

不要用 `git branch -D` 强删尚未合并的 loop 分支，除非维护者明确确认该分支已经
不需要保留。

如果因 squash merge、rebase merge 或其他非普通合并策略导致 `git branch -d`
拒绝删除，但已经确认 loop 分支内容等价进入目标分支，可以按项目规则清理该分支；
清理记录必须说明 `-d` 不适用的原因、采用的合并策略和确认方式。

如果确实需要临时保留 loop 分支用于 review、排查或补丁续做，必须记录保留原因、
保留位置和后续清理责任。

`partial` loop 的分支属于恢复入口，不执行本节的成功清理；应按第 2.13 节记录并保留。
后续完成并合入目标分支后，再执行安全删除。不能为了切换到下一 loop 而用 `-D` 丢弃
尚未等价进入目标分支的工作。

### 2.13 未完成尝试的快速收束

任何实现、验证、同步、合并、推送、环境或依赖问题，只要未能在本次尝试内完成，都
按以下流程收束。该流程结束的是“本次尝试”，不是 loop，也不是整批任务：

1. 停止无进展的重复操作，并终止会持续等待输入、锁或网络的交互式进程。
2. 退出未完成的 merge / rebase / cherry-pick 等中间状态；只使用不会丢失已有工作的
   安全方式恢复到可切换、可审计状态。
3. 运行 `git status --short --branch` 和适用的 `git diff --check`，排除凭据、缓存和
   非本 loop 改动；记录失败命令及足够定位问题的脱敏输出。
4. 将有保留价值的工作留在隔离的 loop 分支或 worktree；可安全提交时创建 checkpoint，
   有远端时推送恢复引用。不得把未验收结果合入目标分支。
5. 将状态写为 `partial`，追加本次执行记录，至少列出 `Completed`、`Unfinished`、
   `Evidence`、`Next attempt` 和分支 / worktree 位置。`Next attempt` 必须是下一轮可直接
   执行的具体动作，不能只写“待处理”“等回复”或“稍后重试”。
6. 回到干净的目标分支或切换到下一个隔离 worktree，把调度权交还给整批执行器。

未完成原因只能作为事实记录和下次调度输入，不能转成 `blocked` 状态、等待人工回复
的会话或整批停止信号。若某项动作需要当前执行器没有的权限、凭据、网络、设备或破坏
性授权，应记录约束并继续其他 loop；同时自动选择 fixture、mock、只读检查、兼容实现
或其他安全替代路径。LOOPMAP 不应把无法无人值守满足的外部动作设计成 loop 的唯一
完成条件，具体要求见第 3.7 节。

### 2.14 整批 sweep 与自动重试

整张 LOOPMAP 以 sweep 方式运行：

1. 按依赖和建议顺序扫描所有非 `done` loop，优先执行依赖已满足且能直接产生进展的项。
2. 某项依赖未满足时，不等待；记录本次 skip 和缺失依赖，继续扫描其他项。依赖 loop
   在本 sweep 后续完成时，可在同一 sweep 重新入队；否则进入下一 sweep。
3. 每个 loop 尝试成功后标记 `done`；未成功则按第 2.13 节记为 `partial`，继续扫描。
4. 扫描到末尾后，只要仍有 `todo` 或 `partial`，立即开始下一 sweep。重试时先读取上次
   `Evidence` 和 `Next attempt`，不得原样重复已经证明无效的动作。
5. 如果一整个 sweep 没有任何 loop 取得进展，执行器必须自动做恢复分析：重排依赖、
   缩小失败面、补诊断、拆出可独立验收结果、选择安全替代实现，并把这些动作写入下一
   次尝试；“零进展”本身不是停止条件。
6. 只有所有 loop 都为 `done` 且第 7.2 节的整批验收成立，整批任务才可结束并宣告完成。

调度器可以对单次命令和单次尝试设置超时，以避免假死；不得把单次重试次数、单次
失败、一个 sweep 结束或等待人工输入作为整批任务的正常终止条件。若运行环境被外部
强制终止，必须留下可自动恢复的游标和执行记录，下次启动从非 `done` 项继续。

## 3. LOOPMAP 编写规范

LOOPMAP 是把本规则落到具体项目、迁移或长周期任务上的执行地图。它必须能回答：
为什么做、按什么基线做、分成哪些 loop、每个 loop 如何验收、完成后如何证明已经
闭环，以及单次尝试未完成后如何自动恢复并继续跑完整张地图。

LOOPMAP 不替代实际执行记录。计划中的 loop 默认只能是 `todo`；只有满足第 7.1 节的
完成定义后，才能标记为 `done`。

### 3.1 必备结构

迁移、复杂开发、多人协作或长周期任务应维护 LOOPMAP 类文档，至少包含：

- 目标与范围：说明本地图要完成的总体目标、参考源、目标端和明确不覆盖的内容。
- 当前基线：记录当前系统状态、已知差异、已通过的检查和仍不可信的检查。
- 兼容与安全约束：列出不得回退的认证、安全、数据、兼容或发布约束。
- 粒度策略：说明本地图采用的端到端能力块、合并判断和必须拆分的风险边界。
- 执行约定：声明执行时遵循本 LOOPRULE；项目本地补充可以具体化规则，或在安全
  底线内调整粒度，但不得削弱可审查、可验证、可回滚、完成定义和高风险验证要求。
- Loop 表：列出每个 loop 的编号、负责人、状态、目标、范围、内部 checklist、验收和验证。
- 建议执行顺序：说明 loop 之间的先后关系、依赖关系、依赖未满足时可继续推进的项和
  自动降级路径。
- 执行记录区：每次尝试结束都追加记录；成功和未完成记录都不覆盖历史。
- 挂机策略：定义命令超时、checkpoint 保存、sweep 游标、重试顺序和零进展恢复方式。

### 3.2 Loop 表字段

每个 loop 至少包含以下字段：

| 字段           | 含义                                           |
| -------------- | ---------------------------------------------- |
| Loop           | 稳定编号，如 `L2-14`、`LMWX-05`                |
| Owner          | 负责人、角色或执行 agent                       |
| 状态           | `todo`、`doing`、`partial`、`done`             |
| 目标           | 本 loop 要完成的单一目标                       |
| 主要范围       | 涉及目录、模块、接口、页面或文档               |
| 内部 checklist | 完成同一结果所需的紧密相关步骤；可在表格外展开 |
| 验收           | 可验证的完成标准                               |
| 验证           | 本 loop 必须运行或人工执行的检查               |
| 未完成收束     | 分支 / worktree 保全方式和必须写入的诊断证据   |
| 下一次动作     | 本次未完成后可由执行器直接运行的恢复或降级动作 |

推荐额外字段：

- `优先级`: 如 `P0`、`P1`、`P2`，用于说明执行顺序和风险。
- `不在范围`: 明确本 loop 不处理的内容，防止顺手扩大范围。
- `依赖`: 本 loop 取得最终结果前需要的其他 loop、接口或环境条件；它影响调度优先级，
  不代表整批执行器要原地等待。
- `尝试次数` / `最后进展`: 帮助下一 sweep 判断是否需要换方案，不用于达到上限后停止。
- `风险`: 标注共享模块、数据写入、认证、发布、兼容层等高风险点。
- `回滚边界`: 说明失败时应整体撤销什么，以及是否存在可独立保留的部分；高风险
  loop 必填。

### 3.3 Loop 平衡粒度规则

生成 LOOPMAP 的目标不是把工作拆到最细，而是在可审查、可验证、可回滚的约束内，
形成粒度平衡的独立闭环，避免没有独立验收结果或风险边界的微型 loop。默认粒度是
“端到端能力块”：围绕一个用户可见结果、协议能力、迁移 Gate 或发布关卡，把必要的
实现、测试、配置、接线和文档放进同一个 loop。

#### 3.3.1 生成顺序

生成 LOOPMAP 时按以下顺序确定粒度：

1. 先从总体目标和 Gate 提取可验收结果，不从目录树、文件清单或技术层开始切块。
2. 为每个结果收集完成它所需的实现、测试、配置、接线和文档，作为内部 checklist。
3. 用第 3.3.2 节的合并条件和第 3.3.3 节的拆分条件确定 loop 边界。
4. 初稿完成后执行第 3.3.4 节的反碎片化复核，再输出最终 Loop 表。

不得预设 loop 数量，也不得按目录、文件数量、前端/后端或开发步骤平均切块。没有
独立验收结果或风险边界的步骤应合并；命中第 3.3.3 节任一条件时必须拆分。

#### 3.3.2 默认合并条件

若一组工作共同服务同一验收结果，合并后仍能整体审查、验证和回滚，并且没有命中
第 3.3.3 节的拆分条件，默认放在同一个 loop 中。以下特征说明它们适合合并：

- 服务于同一个用户可见结果、协议能力、迁移 Gate 或发布关卡。
- 共享同一批核心文件、背景上下文或设计决策。
- 能用一条端到端验收链路判断整体通过或失败。
- 失败时应作为一个整体回滚，不存在有价值且安全的半成品交付。
- 其中的测试、配置、接线和文档只是同一结果的必要组成部分。

一个平衡的 loop 通常包含 2-6 个紧密耦合的内部 checklist 项。这只是帮助识别微型
loop 的启发式，不是硬性上下限：不得为了凑数量强行合并，也不得因为超过 6 项就
机械拆分。只有一个机械步骤的 loop 应优先与相邻 loop 合并，除非它本身就是独立的
可验收 Gate，或存在必须隔离的风险或回滚边界。

若项目没有自己的尺度约定，可把“能在一个短生命周期执行周期内闭环，reviewer 能在
一次约 30-60 分钟的聚焦 review 中理解”作为目标区间。超出该区间只触发重新评估，
不自动按目录或步骤拆分；实际 diff 复杂度、风险和验收边界优先于时间估算。

模块数量、文件数量、编程语言和“前端/后端”标签本身都不是拆分理由。基础设施、
测试框架、文档、接线或发布说明如果不能形成独立验收结果或守住一个 Gate，应作为
能力 loop 的内部 checklist，而不是单独建 loop。

#### 3.3.3 必须拆分条件

出现下列任一情况时，应在对应边界拆分：

- 包含两个可独立验收且可安全保留的结果，或存在必须隔离的上线或回滚边界。
- 同时跨越彼此独立的安全、数据持久化、公共协议或兼容性决策边界。
- 一部分暂时缺少外部依赖，而另一部分可以形成独立可验收结果。
- 预计 diff 已大到无法在一次聚焦 review 中理解，或失败后难以定位责任和回滚范围。
- 验证链路彼此独立且成本很高，合并后会反复运行大量无关回归。
- Owner、发布窗口或环境条件不同，无法在一个短生命周期分支内闭环。

高风险本身不自动要求按实现步骤拆分。共享协议、认证、支付、订单、数据写入或发布
流程必须扩大 review 和验证范围，并在 `风险`、`验收`、`验证` 和 `回滚边界` 中
写明；是否拆分仍按本节列出的条件判断。

#### 3.3.4 反碎片化与过大复核

输出 LOOPMAP 前必须逐个检查相邻或强依赖的 loop：

- 是否重复读取同一上下文、修改同一核心文件或运行同一套验证。
- 是否把实现、测试、配置、接线或文档人为拆成前后多个 loop。
- 是否共享同一验收结果，后一个 loop 单独完成时没有独立价值。
- 合并后是否仍能用一句话描述目标、一条链路验收、一个边界回滚。

如果以上答案表明边界相同，应合并并改写为一个能力 loop 的内部 checklist。同时检查
是否合并过度：若目标必须用两个互不依赖的结果描述、任一半都能独立交付，或 diff
无法在一次聚焦 review 中理解，则按第 3.3.3 节拆分。

最终 LOOPMAP 应减少没有独立验收结果的流程开销：同一 loop 只建立一个分支生命周期
和一条完成记录，内部 checklist 不单独创建分支或重复走合并、推送、清理等完整闭环。
这不减少第 2.6、2.10 节要求的累计 diff 审查、同步后检查和合并后验证。测试和文档应
跟随能力一起收口，避免后置的“补测试 loop”和“补文档 loop”。

执行中一旦确认范围无法审查、验证或回滚，应立即按第 3.3.3 节调整边界，而不是等到
多个 loop 失败，也不是按目录平均切块。

### 3.4 状态规则

状态只能表达真实执行进度，不表达愿望或计划优先级：

- `todo`: 尚未开始。
- `doing`: 当前正在执行，且已有明确目标分支和 loop 分支。
- `partial`: 本次尝试已安全收束，但 loop 尚未满足验收、验证、提交、推送或分支清理
  要求；执行记录中已有证据和可自动执行的 `Next attempt`，等待整批调度器再次入队。
- `done`: 已实现、验证、审查、提交、合并回目标分支、推送远端，并清理 loop 分支；
  如需保留 loop 分支，已记录原因、位置和清理责任。

代码已提交但未推送时不应视为完整闭环，只能算 `partial`。loop 分支未清理且未记录
保留原因时，也不应视为完整闭环。规划、审计或调研记录不得伪装成已完成的实现
loop。状态集合中禁止增加 `blocked`、`waiting-human`、`failed-final` 等会让调度器永久
跳过未完成项的终态。

`doing` 只允许用于当前正在占用执行权的尝试。正常让出调度权前必须转成 `done` 或
`partial`；执行器异常退出后，恢复程序应把遗留 `doing` 视为待审计的 `partial`，先
检查分支 / worktree 现场再重新入队。

### 3.5 验收与验证写法

验收和验证必须具体到执行者可以直接照着检查：

- 验收写结果，不写动作。例如写“订单列表按 `status` 请求并展示 5 条分页”，不要只
  写“对齐订单列表”。
- 验证写命令、页面路径、接口路径、截图对象或手工路径。
- 手工 smoke 应说明入口、关键操作和通过标准。
- 截图比对应说明参考页面、目标页面和需要比对的状态。
- 无法自动化的检查必须说明可由执行器采集的替代证据；人工检查可以作为附加 review，
  不能成为挂机 loop 唯一的完成信号。确实必须由人或外部系统裁决的事项应在执行前
  改写为可自动判定的代理标准，或移出无人值守 LOOPMAP。

### 3.6 执行记录模板

每次 loop 尝试结束都应在 LOOPMAP 的执行记录区追加一条记录。`done` 和 `partial`
使用同一模板，至少包含：

```text
Loop:
Attempt:
Outcome: done | partial
Target branch:
Loop branch:
Commit(s):
Merge commit:
Verification:
Diff review:
Remote sync:
Push:
Loop branch cleanup:
Current branch/worktree:
Completed:
Unfinished:
Evidence:
Next attempt:
Sweep cursor:
Notes:
```

字段含义：

- `Target branch`: 本 loop 开始时记录的目标分支。
- `Attempt`: 该 loop 单调递增的尝试编号。
- `Outcome`: 本次尝试结果；只有满足第 7.1 节才可写 `done`，否则统一写 `partial`。
- `Loop branch`: 本 loop 使用的开发分支。
- `Commit(s)`: loop 分支上的一个或多个功能 commit。
- `Merge commit`: 合并回目标分支产生的 commit；如使用 squash/rebase merge，说明策略。
- `Verification`: 实际运行的验证命令和人工检查结果。
- `Diff review`: 是否执行 `git diff --check` 和最终 diff 审查。
- `Remote sync`: 开始前和合并前是否同步远端，如何处理远端新提交。
- `Push`: 目标分支是否已推送成功。
- `Loop branch cleanup`: loop 分支是否已删除；`partial` 时说明保留位置和恢复方式，
  `done` 时说明清理结果或保留责任。
- `Current branch/worktree`: 本次尝试收束时所在分支和工作区状态。
- `Completed`: 本次已经实现且证据可信的部分；没有则明确写 `none`。
- `Unfinished`: 尚未满足的验收项或缺失条件，必须具体且可检查。
- `Evidence`: 失败命令、脱敏输出、日志 / 测试位置、commit 和环境事实。
- `Next attempt`: 下一轮能直接执行的首个动作以及失败时的自动替代方案。
- `Sweep cursor`: 整批执行器接下来要尝试的 loop，供异常退出后恢复。
- `Notes`: 跳过项、风险、回滚说明或后续 loop 依赖。

### 3.7 挂机可执行性审查

LOOPMAP 在进入执行前必须通过挂机可执行性审查。每个 loop 都必须满足：

- 所需输入、fixture、命令、路径、验收信号和超时策略明确，执行器无需临场追问。
- 依赖未满足、网络不可用、Provider 失败、测试失败、Git 分叉和推送失败都有自动收束
  与下一次动作。
- 需要选择方案时，已写明安全默认值、决策优先级或可回滚的试验方法；不能写成“询问
  用户后继续”。
- 需要凭据、审批、付费资源、真实设备或特定发布窗口时，已经预置合法能力，或提供能
  完成同一验收结果的本地 fixture、mock、延迟发布 / 本地交付路径。不能把等待外部动作
  设为 loop 的唯一完成路径。
- 验收由命令退出码、结构化输出、页面 / 接口状态、产物校验或其他机器可采集证据判定；
  人工 review 只能附加，不能卡住调度。
- `partial` 分支、checkpoint、执行记录和 sweep 游标能让新进程从现场恢复，而不是依赖
  上一次会话记忆。

不满足以上条件的条目不能以“执行时再等待”的方式进入 LOOPMAP。应先重写验收、补
fixture / 自动化、拆出当前环境可完成的结果，或明确移出本次整批任务；LOOPMAP 一旦
进入执行，其表内所有 loop 都必须存在无需人工介入的完成路径。

## 4. 远程协作规则

多人或多 agent 协作时：

- 每个 loop 尝试开始和成功结束都要同步远程状态；同步失败时按第 2.13 节收束，不等待。
- 推送前必须处理远端新提交，禁止覆盖别人提交。
- 如果远端频繁变化，以“先同步、再测、再推”为准。
- 同步远端后，相关测试必须重跑。
- 推送成功后再宣告 loop 完成。
- 一个 loop 的同步、review 或推送问题不能阻止其他隔离 loop 被尝试；整批执行器在后续
  sweep 中回来重试该项。

推荐最终确认：

```bash
git log --oneline --decorate --max-count=8
git status --short --branch
```

## 5. 迁移与兼容规则

适用于任何新旧系统并存、目录迁移、API 替换或兼容层维护的任务。

- 新能力优先进入目标架构或目标目录。
- 旧入口如需保留，应尽量只承担兼容、转发、说明或极薄包装职责。
- 删除旧入口前必须有替代路径、验证方式、回滚方案和发布说明。
- 对外部用户、下游系统或自动化脚本可见的行为变更，必须记录兼容影响。
- 如果项目有冻结目录或禁止修改区域，必须使用项目本地规则和检查命令验证。

## 6. 安全与凭据规则

- 不把密码、token、cookie、私钥写入文件或 commit。
- 不把密码放进 shell 命令参数。
- 无人值守 loop 不得在运行中等待交互式凭据输入。凭据必须在执行前通过项目批准的
  secret 机制提供；缺失时记录约束，选择不泄露凭据的本地替代路径并继续其他 loop。
- 在有人值守且确实必须临时输入凭据时，只通过交互式提示输入。
- 凭据一旦出现在聊天、日志或终端记录中，应尽快轮换。
- `.env` 只允许提交模板文件，例如 `.env.example`。

## 7. 完成定义

### 7.1 单个 loop 完成

一个 loop 只有同时满足以下条件，才算完成：

1. 目标实现。
2. 文档状态按需更新。
3. 本地验证通过；原验证无法运行时，验收预先定义的等价替代检查已经通过。
4. diff 审查通过。
5. 变更已按项目版本控制流程记录。
6. 已同步远程最新状态。
7. 同步后必要测试通过。
8. 已推送到远程分支。
9. loop 开发分支已清理；如需保留，已记录原因、位置和清理责任。
10. 工作区和分支状态无未解释的残留问题。

未满足以上任一条件时，本次结果只能是 `partial`。记录原因和替代检查不会自动把 loop
变成 `done`；它们用于安全收束与下一次重试。尤其是“验证无法运行但已记录”只证明
现场可审计，除非验收事先明确定义的等价替代检查已经通过，否则仍需后续 sweep 补齐。

### 7.2 整批任务完成

整批 LOOPMAP 只有同时满足以下条件才可结束并宣告完成：

1. Loop 表中的所有条目均为 `done`，不存在 `todo`、`doing` 或 `partial`。
2. 所有 Gate loop 通过，跨 loop 的最终验收和必要回归通过。
3. 所有 checkpoint 已合入、确认无须保留或按记录安全清理；没有遗失的隔离 worktree。
4. 目标分支已经同步并推送，远端包含全部完成结果。
5. 执行记录覆盖每个 loop 的最终成功尝试，历史未完成记录均能对应到后续解决证据。
6. 当前分支、工作区和远端状态没有未解释残留。

完成一轮 sweep、写下未完成原因、用尽某次重试、遇到外部依赖或暂时没有进展，都不
等于整批任务完成。执行器必须按第 2.14 节继续调度，直到所有 loop 真正闭环。外部运行
环境强制中断时只能报告“执行中断、可恢复”，不得报告任务完成；下次运行必须从记录的
sweep 游标和非 `done` 项自动续跑。

最终完成总结必须说明：

- 完成了哪些 loop。
- 运行了哪些验证。
- 是否已提交、同步和推送。
- loop 分支是否已清理，或为什么需要保留。
- 当前分支和工作区状态。
- 历史 `partial` 尝试如何在后续 sweep 中解决。

如果仍有未完成、跳过或无法验证的事项，只能输出 sweep / 中断进度记录并继续执行，
不能输出最终完成总结。
