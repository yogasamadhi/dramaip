# LM3-11 套餐与权益快照验证

从 migration 019 起，`billing.orders`、`billing.subscriptions` 与
`quota.token_accounts` 都保存购买/续期时的完整套餐权益，不再通过可变的
`billing.plans` 行重建历史。

| 记录 | 快照字段 |
| --- | --- |
| order | code、name、billing period、plan price、currency、月额度、RPM、上下文上限、model level、来源、时间 |
| subscription | 与 order 相同；支付确认直接复制 order snapshot |
| token account | 与 subscription 相同；`quota_tokens` 就是该周期的额度 snapshot |

`billing.plans` 只用于展示当前可售套餐和创建新的 checkout。支付确认、订单/订阅
查询、失败重试、quota provision 与周期续账只读取已经写入的 snapshot。相同
`subscription_id + period_start` 的重试不会改写已有 quota account 快照。

## 旧数据和部署

迁移会从当时仍存在的 `plan_id` 关联回填历史 order/subscription；无法关联的行明确标记
为 `legacy_unknown`，全部回填记录使用 `plan_snapshot_source=legacy_backfill`。历史上早于
迁移且套餐已经变更的数据不伪装成原始购买值，运营对账应以该来源标识区分。

新服务写入 `checkout` source；quota 周期续账复制前一周期的权益并标记为
`period_renewal`。新增列保留默认值以兼容 migration 先于应用滚动升级的窗口；新路径的
quota API 强制要求完整 snapshot，避免后续服务重新依赖 `billing.plans`。该兼容窗口中
旧 billing 镜像漏写的新字段会由 billing trigger 以 `legacy_compat` 填充；旧 quota RPC
调用同样由 quota trigger 保存受限的 `legacy_compat` snapshot，而不会使新服务回查
billing schema。

## 验证

不使用流水线。请在一个全新、隔离的 PostgreSQL 数据库上运行：

```bash
cd dramaip-platform/services
POSTGRES_SNAPSHOT_TEST_DSN='postgres://ddl_user:password@localhost:5432/dramaip_snapshot_test?sslmode=disable' \
  make plan-snapshot-integration
```

该测试先回放 001–018，写入旧结构的 order、subscription 与 quota account，再应用 019
验证历史回填；随后创建 basic checkout，故意修改 basic 的价格、名称、额度、RPM、上下文和
model level，再确认支付。历史记录以及新订单、订阅和 quota account 的快照都必须仍等于
各自创建时的值。测试检测到已有 migration 记录时会拒绝运行，避免误用非空数据库。

由于全量 migration 会创建 runtime role，测试实例必须独立，DDL user 必须有
`CREATEROLE`；不得指向生产库或多人共用实例。补充检查：

```bash
GOCACHE=/tmp/dramaip-go-build go test ./...
make event-contracts
rg 'JOIN billing\.plans|billing\.plans' app/billing app/quota --glob '*.go'
```

最后一项只应保留 billing 的当前套餐读取、checkout snapshot 捕获和本验证测试；quota
目录不应命中 `billing.plans`。

## 回滚边界

迁移只增加字段和回填快照，不删除 `plans`、订单、订阅或 quota 记录。回滚应用版本时，
旧代码仍可依赖保留的既有列运行；不得删除已经写入的 snapshot。后续收紧列默认值或
删除旧 `plan_id` 依赖，必须在另一个兼容窗口结束后的 migration 中执行。
