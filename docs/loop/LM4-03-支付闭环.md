# LM4-03：正式支付渠道与订单体验闭环

状态：本地实现和自动化回归通过；正式渠道发布仍受外部沙箱证据阻断。

## 交付

- 移除 Web 端 `production` 伪渠道：模拟模式只传 `simulated`；非模拟模式只允许用户从公开部署配置中选择
  `wechat_pay` 或 `alipay`。Billing 对伪渠道返回明确的参数错误，且仍以服务端 merchant 配置为唯一授权来源。
- Checkout 下单后立即跳转认证订单页。订单页展示支付地址、有效期、服务端 `pending/paid/failed/expired` 状态，
  每 3 秒轮询 pending 状态，并为 expired/failed 提供重新创建订单动作。
- 浏览器不会以跳转或点击确认权益：正式渠道只能由已验证并主动核验的 webhook 激活；模拟确认按钮严格限于
  `simulated` provider 和模拟模式。
- 新增 Billing migration `036_billing_checkout_delivery`：持久化 provider 返回的支付地址和过期时间；查询时将
  已到期的 pending 订单原子标记为 `expired`。微信 native 下单携带 `time_expire`，支付宝 precreate 携带
  `timeout_express`，两者均由 `BILLING_CHECKOUT_TTL`（默认 30 分钟）统一推导。
- SDK、protobuf、Web BFF 和订单读取契约新增 `expires_at`，使重新打开订单页仍能恢复同一支付入口。

## 验证

- `cd dramaip-platform && make test`：通过（Go 全量、客户端类型检查、Web route smoke）。
- `cd dramaip-platform/clients && pnpm lint && pnpm build:web`：通过。
- `cd dramaip-platform/services && buf generate`：生成契约后 Go 回归通过。
- 本地 Docker 健康栈使用新 Billing/Web BFF 镜像并运行 migration 036 后，`make platform-e2e` 通过；E2E 额外断言
  checkout 初始为 pending、保留 simulated 支付入口，随后只经服务端模拟确认变为 paid。
- 微信/支付宝适配器签名 fixture 覆盖 `time_expire` / `timeout_express`；BFF HTTP 测试验证明确 provider 与
  `expires_at` 不丢失；Billing 测试验证 `production` 永远不会进入 repository。

## 已记录阻断与边界

1. `make billing-wechat-webhook-integration` 和 `make billing-alipay-webhook-integration` 需要专用、空白且拥有
   DDL 权限的 PostgreSQL DSN。当前健康栈的 PostgreSQL 被运行中服务共享，而这些测试会重置集群级运行角色密码；
   为避免破坏健康栈，没有在共享实例运行。临时创建的两个本地测试数据库已删除。
2. 未提供微信/支付宝官方沙箱 merchant 凭据及回调可达环境，因此没有启用任一真实 provider，也不宣称真实支付可用。
   在获得隔离 DSN 和官方沙箱证据前，渠道 Feature Flag 必须保持关闭。
3. 浏览器访问既有 `localhost:3009` 前端时只确认了未登录套餐页壳；该已有前端进程未完成公开套餐加载，虽然
   `GET /v1/plans` 和其 CORS 响应正常。它不作为本 Loop 的正向支付 UI 验收证据；自动化 build/route/BFF/E2E
   结果仍完整保留，LM4-04 需复查这一环境级现象。
