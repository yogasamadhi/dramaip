# DramaIP 技术架构

本文记录 DramaIP 的目标技术设计。目标仓库边界采用一个父目录管理两个项目：

- `dramaip-desktop`：桌面端项目，未来可能开源。
- `dramaip-platform`：官网、移动端和云端服务，保持闭源。

通用产品、架构、路线与流程文档放在父级 `docs/` 下。

## 0. 文档定位

本文只描述 DramaIP 的**目标技术架构与工程约束**，不是代码实现状态的复述。代码、目录、部署脚本和测试应以本文为目标收敛；实现差异、阶段性偏离和迁移路径统一记录在 `docs/差异演进.md`。

本文中的“必须 / 禁止 / 只能”视为架构红线；“建议 / 后续可”视为演进建议。若工程实现需要改变红线，应先更新本文或新增 ADR（Architecture Decision Record），再改代码，避免架构漂移。

## 1. 架构目标

DramaIP 的产品形态分为三类入口：

1. 桌面端：专业创作工作台，本地优先，适合长文本、复杂项目、AI 工作流、导出交付。
2. Web 官网：产品官网、定价页、下载页、登录注册、订阅购买、账号中心。
3. 移动端：轻量创作入口，用于随手记录灵感、创建草稿、查看套餐和 token 余额。

云端服务负责：

1. 用户登录与账号体系。
2. 月费套餐订阅。
3. 每月 token 额度和用量账本。
4. 用户无需填写 API Key 的 AI 代理调用。
5. 支付回调、订阅续期、异步任务和运营后台能力。

核心原则：

- 登录只证明“用户是谁”。
- 订阅和额度决定“用户能用多少”。
- 桌面端保持本地优先，不把云端作为创作数据的唯一可信源。
- 支付状态以后端支付回调为准，不信任客户端支付成功提示。
- token 扣减必须可审计、可幂等、可追踪。
- 云端采用微服务架构。服务边界沿有界上下文和扩展性差异切分；切完之后的正确性靠数据自治、Saga、可观测性保证，而不是靠"多拆几个进程"。
- 架构文档优先；实现若需要改变目标红线，应先更新本文或新增 ADR。

### 2.1 dramaip-desktop

`dramaip-desktop` 是本地优先的 Electron 桌面端项目。

```txt

  apps/
    desktop/
      electron/         Electron main / preload / IPC / 本地运行时
      renderer/         React UI

  packages/
    core/               TS 类型、Zod schema、常量
```

注意：`apps/desktop` 不是纯前端。`renderer` 是前端 UI，`electron` 更像本地后端，负责 IPC、数据库、密钥、文件、安全策略和 AI 调用。

#### 目录约定（判断结构是否合理的五条标准）

1. **契约与实现分离，路径镜像**：`api/<领域>/<类型>/v1/*.proto` 与 `app/<领域>/<类型>/` 一一对应，改契约能立刻定位到服务；MQ 事件契约放 `events/<领域>/vN/`，与 HTTP/gRPC 契约同等版本化。
2. **按 `<领域>/<类型>` 切，不是 `<类型>/<领域>`**：`billing/job` 正确，`job/billing` 错误。`service` / `job` / `interface` 是**类型**，按触发方式区分——`service` = 同步领域服务（被其它服务 gRPC 调用）、`job` = 异步任务（定时器 / MQ 触发）、`interface` = 面向前端的 BFF 聚合层；它们不是领域，提到顶层会造成 worker 大杂烩。
3. **每个 `app/<领域>/<类型>/` 内部遵循 kratos-layout**：`cmd/server/{main.go, wire.go}` + `configs/` + `internal/{conf, server, service, biz, data}` 五层。
4. **共享代码沉到 `pkg/`，但只沉项目特有的**：Kratos 自带的 `log / tracing / validator / middleware` 不在 `pkg/` 里重新包一层；`pkg/` 放 token 解析、业务中间件、outbox relay 等**加值**代码。
5. **基础设施与代码分离**：Kong、k8s、Docker 配置放 `deploy/`，不和服务源码混。

#### Kong 在结构中的位置

网关用 Kong，**不要再造一个 Kratos 的 gateway 服务**——Kong 就是网关。流量分工：

```txt
外部客户端（web / mobile / desktop / admin）
    │  HTTPS
    ▼
Kong   ── TLS / 路由 / JWT 校验 / 限流 / CORS      ← 外部入口，配置在 deploy/kong/
    │  HTTP（按 Host / Path 路由到对应 BFF）
    ▼
┌─────────────────────────────────────────────────────────────┐
│  bff/web/interface    bff/desktop/interface                   │
│  bff/mobile/interface admin/interface                        │
│  （每个端独立 BFF，聚合多服务，按需裁剪视图）                    │
└─────────────────────────────────────────────────────────────┘
    │  gRPC（内部直连，不经 Kong）
    ▼
auth / user / billing / quota / ai-gateway / notification
```

- 外部流量过 Kong，Kong 负责鉴权前置和限流，并按请求特征路由到对应端 BFF。
- **每个端有独立的 BFF**：Web/Desktop/Mobile 三端面向 C 端用户，但视图粒度、数据量级、鉴权路径不同，各自独立部署；Admin 是管理后台，独立鉴权体系（管理员认证 + RBAC + 审计日志）。
- 内部服务间 gRPC **直连，不走 Kong**（Kong 是外部入口，不是内部总线）；内部靠 K8s DNS / 服务发现 + mTLS。
- BFF 只做各自端的聚合，鉴权 / 限流交给 Kong，不在 BFF 里重写。
- Kong 必须剥离所有来自客户端的内部身份头（如 `X-User-Id`、`X-User-Role`、`X-Plan`），JWT 验签通过后再注入可信身份上下文；BFF 和下游服务只信任来自 Kong/BFF 的内部身份上下文，不信任客户端直传头。
- Kong 配置（路由、插件、consumer）放 `deploy/kong/`，用 decK 或 `kong.yml` 声明式管理。

### 2.3 开源与闭源边界

推荐以仓库边界控制开源风险：

```txt
public:
  dramaip-desktop

private:
  dramaip-platform

optional:
  API contracts / SDK，可公开也可随 desktop 发布
```

桌面端可开源的内容：

- Electron + React 桌面应用。
- 本地 SQLite 数据层。
- 基础 AI provider 接口和本地工作流。
- 导出能力。
- 桌面端文档、测试和脚本。

不建议开源的内容：

- 用户、订阅、支付、token 账本服务实现。
- 微信支付、支付宝的商户配置和回调处理。
- 平台级模型代理、风控、成本控制。
- 商业 prompt、资源市场审核规则、运营后台。
- 生产环境部署、Kong、数据库、队列和密钥配置。

桌面端如需使用云端套餐，通过公开 API 调用闭源服务，不直接包含服务端实现。

契约（proto / OpenAPI / 事件 schema）建议作为**独立版本化产物**管理，跨 `dramaip-desktop` 与 `dramaip-platform` 两个仓库引用同一版本，避免契约漂移。SDK 版本与契约版本绑定。

### 2.4 开发阶段与部署阶段

开发与部署采用不同的基础设施策略，两者的服务镜像通过同一个 `services/Dockerfile.service` + `build.args.TARGET` 构建，保证二进制同源。

#### 开发阶段

以 `deploy/docker-drama/docker-compose.yaml` 为目标运行基线。所有基础设施（PostgreSQL、Redis、RabbitMQ、Kong）和核心 Go 服务在单机 Compose 内编排，配合完整可观测性栈（OpenTelemetry Collector、Prometheus、Jaeger、Fluent Bit、OpenSearch、OpenSearch Dashboards、Grafana）。用 `make platform-up` 一键启动，`make platform-e2e` 验证完整链路。详见 `docs/LOCAL_DEVELOPMENT.md`。

开发阶段最低目标能力：

- 全栈服务编排（基础设施 + 核心微服务 + Kong）
- 数据库 migration（one-shot 容器，在全部服务启动前执行完毕）
- E2E 自动化验证（注册 → 购买 → AI 调用 → 额度扣减完整链路）
- 模拟支付（dev/test 环境，用于不依赖真实支付渠道的端到端测试）
- 可观测性三支柱（指标/链路/日志）本地可用
- AI test provider（不依赖真实 API Key 即可验证预扣 + 结算逻辑）
- 健康检查与依赖拓扑（`depends_on` + `healthcheck` 保证启动顺序正确）

#### 部署阶段

以 `deploy/k8s/` 和 `deploy/helm/` 为目标。部署阶段才引入的生产能力：

- CI/CD 流水线（构建、测试、镜像推送）
- 灰度/金丝雀发布
- 自动扩缩容（HPA）
- k8s 调度、服务发现、mTLS
- 生产级密钥管理（Vault / K8s Secrets，不依赖环境变量明文）
- 生产级 PostgreSQL（高可用、定期备份、PITR 恢复）
- 真实支付渠道（微信支付/支付宝）的 webhook 接入
- 生产级 Kong（TLS 证书、生产限流策略、监控告警）

本地开发不依赖 k8s，`deploy/k8s/` 和 `deploy/helm/` 目录与 docker-compose 并存，由部署流水线按需选用。

配置管理分层：各服务的 `configs/config.yaml` 提供默认值，敏感值（JWT 私钥、支付密钥、API Key、数据库密码）通过环境变量或受控文件挂载覆盖。分层策略：

- `config.yaml`：非敏感默认值（端口、超时、日志级别）。
- 环境变量：环境差异值（dev/staging/prod 的数据库地址、第三方配置）和不适合文件挂载的敏感值。
- 生产环境：JWT 私钥以仅 auth-service 可读的 K8s Secret 文件挂载；公共 JWKS 也从受控挂载读取。数据库密码等可通过 `envFrom` 注入，不与 config.yaml 一起提交到仓库。
- 严格禁止将任何密钥（JWT 私钥、支付密钥、API Key）写入 config.yaml 或提交到 Git；生产 access token 不使用共享 HMAC secret。

## 3. 应用技术栈

### 3.1 桌面端

桌面端目标技术基线：

```txt
Electron 38
electron-vite
React 19
Vite
TypeScript
Tailwind CSS
shadcn/ui
Zustand
SQLite + better-sqlite3
Drizzle ORM
Zod
TipTap
LangGraph.js
OpenAI-compatible API
pnpm workspace
```

桌面端定位：

- 专业创作工作台。
- 本地项目数据库为可信写入源。
- 复杂 AI 工作流和长上下文控制优先在桌面完成。
- 后续可接入云端账号、订阅和 AI 网关，但不强制依赖云端。

线程模型注意：`better-sqlite3` 是同步接口，运行在 Electron 主进程。长耗时 AI 工作流不能阻塞主进程和 UI；DB 写入对 SQLite 而言足够快，但大批量导入、导出、向量化等重活应放到 Worker 线程或渲染进程，避免拖垮 IPC 与窗口响应。

桌面端云端模式认证：桌面端使用云端套餐时，不走内嵌 WebView 登录（安全风险：Electron WebView 无法保证用户看到的是真实登录页）。推荐采用 **OAuth 2.1 Authorization Code + PKCE** 风格流程，即使后端不是完整 OAuth Provider，也按同等安全语义实现：

1. 桌面端生成 `code_verifier / code_challenge / state`，打开系统浏览器（`shell.openExternal`）跳转 Web 登录页。
2. 用户完成登录/注册后，Web 端只把一次性 `authorization_code` 和 `state` 回调给桌面端（localhost 临时 HTTP server 接收，或自定义协议 `dramaip://auth/callback?code=...&state=...`）。
3. 桌面端校验 `state` 后，用 `authorization_code + code_verifier` 通过后端 token endpoint 换取 refresh token / access token。
4. 后端保证 authorization code 单次使用、短 TTL（建议 60 秒）、绑定 `code_challenge`，并记录换取审计。
5. 桌面端将 `refresh_token` 存入系统 Keychain，access token 存内存。后续所有 API 请求经 Kong → BFF → 下游服务。
6. 桌面端不持有平台 API Key，只持有用户身份凭据。

禁止把 refresh token、access token 或平台 API Key 放入 URL query、日志、崩溃上报、renderer 明文状态或本地项目数据库。自定义协议回调只传一次性 code，不传长期凭据。

### 4.1 弹性策略（熔断 / 降级 / 重试）

服务间 gRPC 调用必须配置合理的弹性策略，防止级联故障：

**超时**：所有应用 gRPC client/server 由共享 interceptor 强制 deadline；`GRPC_REQUEST_TIMEOUT` 默认 10 秒，`AI_RPC_TIMEOUT` 默认 95 秒，且绝不扩大调用方已经提供的较短 deadline。Provider HTTP 再受 `AI_PROVIDER_TIMEOUT`（默认 90 秒）约束，避免模型调用耗尽整个请求预算。

**重试**：仅在 `Get*` / `List*` / `Validate*` 查询 RPC 上对 `Unavailable` / `DeadlineExceeded` 重试，最多 3 次，采用指数退避加小抖动。有副作用的操作（扣减 token、创建订单、支付确认）绝不自动重试，交由幂等键、Saga、outbox 与补偿处理。outbox relay 的失败投递保留原事件 ID，按 5 秒指数退避且上限 5 分钟。

**熔断**：每个下游 gRPC target、每个 Provider/model 均使用独立熔断器。默认连续 3 次瞬态传输失败后打开，15 秒后只允许一个半开探测；业务拒绝说明下游可达，不会打开熔断。BFF 与服务 data 层通过 gRPC interceptor 统一接入，AI Provider 在 data 层接入。

**降级**：关键路径的降级策略需提前定义：

| 场景 | 降级行为 |
|------|---------|
| quota-service 不可达 | ai-gateway 直接拒绝请求，返回"服务暂时不可用"；不绕过额度检查 |
| billing-service 不可达 | Web BFF 只对已成功获取且不超过 5 分钟的套餐列表使用只读内存快照；订单、订阅、支付和写操作不降级 |
| auth-service 不可达 | BFF 返回 `503 + Retry-After: 2`，前端提示用户稍后重试；不影响已登录用户的 JWT 校验（Kong 仍用公钥本地验签）|
| MQ 不可达 | outbox relay 释放租约并保留事件，按有界指数退避后重试（不丢消息）；同步链路（支付回调 → 创建 token_account）不受影响 |

**舱壁**：ai-gateway 对每个 `Provider + model` 使用独立并发舱壁（`AI_PROVIDER_MAX_CONCURRENCY` 默认 8）、超时和熔断；单个模型慢响应或饱和时快速返回 `503 + Retry-After`，不拖垮其它模型。`Unavailable` 映射为 `503 + Retry-After: 2`，`DeadlineExceeded` 映射为 `504 + Retry-After: 1`。实现、故障注入和处置方法见 [LM3-23 弹性运行手册](./loop/LM3-23-弹性与降级.md)。

### 4.2 ORM 使用约束

选用 GORM 作为 ORM，但关键路径必须规避 GORM 的隐式行为：

**必须使用原生 SQL 的场景**：
- token 账户的预扣、结算和回滚（可用单条 `UPDATE ... WHERE used_tokens + ? <= quota_tokens`，也可在事务内 `SELECT ... FOR UPDATE` 锁定账户后检查并更新；禁止无锁先查后写）
- 订单/支付状态变更
- 任何依赖 `rows affected = 0` 判断并发冲突的场景
- outbox 事件的批量插入与标记

**GORM 适用场景**：
- 简单 CRUD（创建用户资料、查询套餐列表）
- 非关键路径的关联查询
- migration 工具生成的表结构操作

**代码规范**：
- GORM 更新必须显式指定 `Select()`，禁止 `Updates()` 自动忽略零值字段
- 禁止使用 GORM 的 `Save()` 做 upsert（并发不安全）
- 所有写操作必须使用事务包裹

## 5. 服务拆分

### 5.0 数据自治与服务边界原则

微服务的正确性建立在数据自治上，不是建立在"拆了多少个进程"上。所有服务拆分遵循以下硬约束：

- **数据自治**：每个服务独占自己的数据。基础形态采用**每服务独立 schema、共享同一 PostgreSQL 实例**；后续按负载再独立 DB。任何服务不得直连、JOIN 别服务的表，跨服务数据需求只走 API 或事件。一旦出现跨服务表 JOIN，服务边界即名存实亡，未来拆库、换库、重构都会被锁死。
- **数据库权限强制边界**：每个服务使用独立 DB role，只授予自己 schema 的读写权限；migration/job 使用单独迁移角色执行 DDL。普通运行服务不得持有跨 schema 权限，BFF 不持久化业务数据、不直连领域表。需要跨域视图时走 BFF 编排、领域 API、事件投影或独立 reporting/read-model schema。
- **边界沿有界上下文 + 扩展性差异切分**：`quota` 和 `ai-gateway` 单独拆出来是因为它们在 AI 热路径、扩缩容节奏、出站调用特征上与其它服务不同，这是正确的拆分理由。
- **部署粒度不等于领域边界**：服务可以按成本、负载和运维成熟度选择部署粒度，但 API 契约、数据所有权、DB role、事件 schema 和可观测性字段必须按领域边界设计。可以合并部署，不得合并账本和权限边界。
- **服务内部状态可独立演进**：服务的表结构、缓存策略、内部实现变更不应对其它服务可见。
- **跨服务一致性见 §5.8**，不依赖分布式事务（无 2PC）。
- **每个 `app/<领域>/<类型>/` 内部遵循 kratos-layout**：`cmd/server/{main.go, wire.go}` + `configs/` + `internal/{conf, server, service, biz, data}` 五层（目录约定详见 §2.2）。

### 5.1 auth-service

职责：

- 注册。
- 登录。
- 密码校验。
- 邮箱验证与密码找回的一次性验证码。
- JWT access token 签发。
- refresh token 签发、轮换、撤销。
- 登出。
- 设备会话管理。
- 登录失败限流。

核心表：

```sql
users (
  id,
  email,
  phone,
  password_hash,
  status,
  email_verified_at,
  phone_verified_at,
  session_invalidated_at,
  created_at,
  updated_at
);

email_actions (
  id,
  user_id,
  purpose,        -- verify_email / reset_password
  token_hash,
  expires_at,
  consumed_at,
  created_at
);

user_identities (
  id,
  user_id,
  provider,
  provider_user_id,
  created_at
);

refresh_tokens (
  id,
  user_id,
  token_hash,
  device_id,
  family_id,
  parent_id,
  replaced_by,
  expires_at,
  revoked_at,
  revoked_reason,
  last_used_at,
  created_at
);
```

认证策略：

- `access_token`：短期有效，用于 API 请求。
- `refresh_token`：长期有效，用于换取新 token。
- 服务端只保存 refresh token 哈希。
- Web BFF 将 access 与 refresh token 分别置于 `HttpOnly + SameSite=Lax` Cookie；生产环境必须设置 `Secure`，refresh Cookie 路径限定为认证接口。优先同源部署并保持 host-only；若 Web/API 使用不同受控子域，才可配置其共同父域，且不得覆盖任何不受信任子域。浏览器 JavaScript 不读取这两类 token，登录/刷新 JSON 只返回用户视图。
- Web 的 Cookie 状态变更使用双提交 CSRF（可读 CSRF Cookie + 请求 header）；凭据型 CORS 只允许精确的 Web origin，禁止 `*` 与 credentials 组合。
- access token 以 RS256 签发，携带 `kid`、issuer、audience 和过期时间；auth-service 在 `/.well-known/jwks.json` 发布当前和保留验证公钥。
- 客户端在登录、刷新和登出请求附带稳定的非秘密 `X-Device-Id`；支持主动登出、踢设备、异常会话撤销。
- 密码使用 `bcrypt`。
- 邮箱验证和密码恢复使用 15 分钟、一次性的站外验证码；数据库只保存验证码哈希，验证码、token、密码不得出现在 URL、日志或 trace。邮件由受控服务端 HTTPS 投递网关发送（生产拒绝非 HTTPS endpoint），不能以客户端回传或前端“已验证”状态替代。
- 未验证邮箱的 Web 账号可浏览套餐，但 BFF 必须拒绝创建或确认付款订单。密码重置需撤销 refresh token 并使已有 access session 立即失效。

Refresh token 轮换策略：每次用 refresh token 换取新 access token 时，同时签发新的 refresh token 并撤销旧的（rotation），用 `family_id`、`parent_id` 和 `replaced_by` 保留审计链。如果已被标记为 rotation 的旧 refresh token 被重复使用（reuse detection），说明 token 可能被盗，auth-service 应立即撤销该用户所有仍有效的 refresh token，并以 `reuse_detected` 记录原因；按设备登出使用 `device_logout` 原因。refresh token 的 TTL 建议 30 天，与 access token 的 15 分钟形成合理的"短凭据 + 长轮换"组合。

### 5.2 user-service

职责：

- 用户资料。
- 账号状态。
- 用户偏好。
- 与订阅、额度、设备绑定的基础信息。

`user` 与 `auth` 分开的原因：身份凭证（密码、token、会话）变更频率和安全等级，与资料/偏好不同，分属不同有界上下文。`user` 的资料会被多个服务读取，应通过 JWT claims + 短期缓存满足，避免每次请求都同步回查 user-service（详见 §13 身份传播）。

`auth` 与 `user` 的数据边界：

- **auth-service 的 `users` 表是"认证身份表"**：最小字段（id、email、phone、password_hash、身份状态如 active/disabled），`user_id` 的主源和发放者。
- **user-service 持有"业务 profile"**：昵称、头像、偏好、扩展资料等，通过 `user_id` 关联 auth 身份。
- 注册流程：auth 创建 `users` 行 → 同步调用 user-service 创建对应 profile（或通过 `user.registered.v1` 事件异步创建，允许短暂不一致）。auth 负责发放 `user_id`，user-service 持有该 `user_id` 下的全部业务资料。两边的 `status` 字段语义不同：auth.status = 认证状态（能否登录），user.status = 业务状态（是否被冻结/封禁），二者可独立变化。

职责：

- 管理用户每月 token 额度。

- 扣减 token。
- 记录用量。
- 支持套餐升级、降级后的额度调整。

核心表：

```sql

  id,
  user_id,
  subscription_id,
  plan_code,
  period_start,
  period_end,
  quota_tokens,
  used_tokens,       -- 已结算 + 已预留的当前占用；结算/取消/过期会调平
  status,
  created_at,
  updated_at
);

  id,
  user_id,
  subscription_id,
  token_account_id,
  request_id,
  model,
  prompt_tokens,
  completion_tokens,
  total_tokens,
  cost_amount,
  status,
  error,
  created_at
);
```

并发扣减必须使用原生 SQL 做原子保护，允许两种实现：

1. 单条条件更新：

```sql
UPDATE token_accounts
SET used_tokens = used_tokens + ?
WHERE id = ?
  AND used_tokens + ? <= quota_tokens;
```

2. 事务内 `SELECT ... FOR UPDATE` 锁定当期 `token_account`，检查剩余额度后更新。

如果条件更新行数为 0，或锁定后检查失败，说明额度不足。禁止用“先查询余额、再无锁更新”的实现。

云端 AI 上线前必须具备预扣表：

```sql
token_reservations (
  id,
  user_id,
  token_account_id,
  request_id,
  reserved_tokens,
  actual_tokens,
  status,
  expires_at,
  created_at,
  updated_at
);
```

`token_reservations` 的 `request_id` 必须具备幂等唯一性。推荐使用 `user_id + request_id` 唯一约束；若采用全局唯一 `request_id`，客户端和 BFF 必须保证它是全局 UUID。重复请求若 payload 相同，应返回已有 reservation / usage 结果；payload 不同则返回冲突，不得重复扣减。

预扣状态机建议至少包含：`reserved`、`settled`、`over_quota_settled`、`cancelled`、`expired`、`settlement_pending`。`reserved` 过期只能释放尚未确认产生成本的占用；如果模型侧已经产生费用但结算失败，必须进入 `settlement_pending` 或人工对账路径，不能简单过期回滚。

扣减策略演进：

1. 早期"后扣费"：请求前检查余额大于 0，模型调用完成后按真实 usage 扣费。注意并发窗口——多个请求同时通过"余额>0"检查会形成超扣，早期可接受，需配合 max_rpm 限流收敛风险。
2. "预扣 + 结算"：请求开始按估算上限预扣到 `token_reservations`，调用完成后用真实 usage 结算差额。ai-gateway 热路径必须采用此模式（见 §5.5）；若没有预扣能力，不得开放平台 API Key 托管的云端 AI。

usage 未知的处理：流式响应的 usage 在末尾才到，个别 provider 可能不返回或返回估算值。必须约定 fallback——按输入 token 估算上限预扣，usage 回填后多退少补；不得因为"usage 未知"而放行不计量。

周期账户创建：当期 `token_account` 由 billing 支付链路在本地事务提交后**同步、幂等**创建（自然键 `subscription_id + period_start`，唯一约束兜底重投递），不放入普通异步队列。若创建失败，订阅进入 `quota_pending / activation_failed` 并由补偿任务重试。月度重置同理：worker 创建新周期账户，旧账户保留供对账（见 §5.7、§5.8）。

### 5.5 ai-gateway-service

职责：

- 替用户调用模型。
- 统一保管平台 API Key。
- 用户无需自己填写 API Key。
- 模型路由。
- 请求限流。
- token 用量计量。
- 失败重试和审计。
- 对接 quota-service 扣减额度。

请求流程（预扣 + 结算，保证额度保护与账本准确）：

```txt
用户请求 AI 接口
  |
  v
Kong 鉴权 / 限流
  |
  v
ai-gateway-service
  |
  +-- 校验用户身份
  +-- 调 quota-service 申请一次"预扣租约"（按估算上限，单次 RPC）
  +-- 调 OpenAI-compatible / 其他模型 API
  +-- 获取真实 usage
  +-- 结算：调 quota-service 用真实 usage 多退少补
  +-- 返回结果给用户
```

把"检查 + 扣减"合并为一次预扣 RPC，既保护热路径延迟，又对短时间突发并发有额度保护。模型调用完成后的结算应遵循：

- 非流式接口：成功响应返回前完成结算；若结算失败，返回明确错误并记录 `settlement_pending`，由补偿任务重试。
- 流式接口：开始流式输出前完成预扣；流结束后结算。若客户端中途断开，但模型侧已产生成本，ai-gateway 必须保留审计记录并进入后台结算补偿。
- 租约必须有超时回收机制，防止模型调用失败后额度长期占用。已确认产生模型成本的请求不得被简单过期回收，必须进入结算或人工对账路径。

桌面端未来有两种模型模式：

1. 本地自带模式：用户自己配置 API Key，所有调用在桌面本地完成。
2. 云端套餐模式：用户登录后走 `ai-gateway-service`，使用平台 API Key 和套餐额度。

成本风控：平台 API Key 托管意味着账号被盗会直接烧平台预算。除 max_rpm 外，ai-gateway 还需单用户/单 IP 的短窗口成本上限和异常突增告警，超限直接熔断。

AI 请求审计表最低字段：

```sql
request_audits (
  id,
  user_id,
  request_id,
  request_hash,
  provider,
  model,
  reservation_id,
  prompt_tokens,
  completion_tokens,
  total_tokens,
  remaining_tokens,
  status,
  error,
  response_payload,   -- 只允许存摘要或产品明确允许保留的最小响应
  started_at,
  finished_at,
  created_at,
  updated_at
);
```

若需要成本核算，应在 ai-gateway 或独立 billing/reporting 模块记录 provider 计费快照：`provider / model / prompt_tokens / completion_tokens / input_unit_price / output_unit_price / currency / exchange_rate / cost_amount / priced_at`。成本账本用于运营和对账，不能反向替代用户侧 quota 账本。

AI Chat 幂等性：`POST /v1/ai/chat` 不是天然幂等操作，客户端超时重试可能导致重复扣减额度和重复模型成本。客户端必须为每次 AI 请求生成 `X-Idempotency-Key` header；ai-gateway 以 `user_id + idempotency_key` 为唯一键写入持久化请求审计表，记录请求 hash、reservation_id、状态、usage、响应摘要和错误。Redis 只能作为短期快速缓存（TTL 5 分钟），不能作为唯一幂等源。重复请求的处理规则：

- 请求 hash 相同且已成功：返回已缓存或已持久化的结果，不重复调用模型，不重复扣减额度。
- 请求 hash 不同：返回 409，提示 idempotency key 已被不同 payload 使用。
- 原请求仍在处理中：返回 202 / 409 或可轮询状态，禁止并发重复调用模型。
- Redis 不可达：走持久化表判断；若持久化表不可达，保守拒绝请求，而不是放行烧平台预算。

### 5.6 notification-service

`notification-service` 独占通知列表、已读状态和 BFF 触发的同步写入；Web BFF 仅通过
内部 gRPC 调用它，不直接读取或更新 `notification.notifications`。`notification-job`
消费自己的 RabbitMQ topic 订阅（payment、subscription、quota 与显式 notification
request），并与同步服务复用 notification 领域 repository；其它领域仍不直接写通知表。

职责：

- 用户站内通知查询。
- 通知已读 / 未读状态管理。
- 邮件、短信、站内信等通知渠道抽象。
- 从 billing、quota、ai-gateway 等领域事件生成用户可见通知。
- 通知投递幂等和失败重试。

核心表：

```sql
notifications (
  id,
  user_id,
  type,
  title,
  body,
  source_event_id,
  read_at,
  created_at,
  updated_at
);

event_inbox (
  id,
  event_id,
  event_type,
  trace_id,
  processing_at,
  attempts,
  last_error,
  processed_at,
  raw_payload,
  created_at,
  updated_at
);

delivery_attempts (
  id,
  event_id,
  notification_id,
  channel,
  status,
  failure,
  attempted_at
);
```

消费端先持久化/租约 `event_inbox`，成功后标记 `processed_at`；失败会释放租约后按
`x-retry-count` 重投，超过上限才进入专属 DLQ。通知行以 `(user_id, source_event_id)`
唯一去重，因此 worker 重启或 MQ 至少一次投递不会生成重复站内信；每次渠道结果写入
`delivery_attempts`。当前启用 `in_app` adapter，邮件/SMS 通过同一接口后续接入，不能
仅改环境变量假装已投递。

通知服务不得成为“所有事件副作用”的垃圾桶：用户可见通知归 notification，账单、额度、对账、报表等领域副作用仍归原领域 job。

### 5.7 worker

worker 不是"按消费 MQ 切出来的单一服务"，而是**按领域组织消费者**的统称。每个领域服务自带属于自己的异步消费者，或按领域独立队列、独立部署：

- `app/billing/job/`：订阅续期检查、退款补偿、账单报表。
- `app/quota/job/`：新周期 token_account 维护、用量聚合、对账。
- `app/notification/job/`：独占 notification topic queue，处理用户可见站内信和渠道投递审计；不执行账单、额度或报表副作用。

不把所有领域的异步逻辑塞进同一个可部署单元——否则它会成为耦合磁铁（billing 改续期逻辑要重启整个 worker，连带 quota 聚合一起受影响）和部署瓶颈。

职责（按领域分布）：

- RabbitMQ 消费。
- 支付成功后的下游异步处理（通知、统计、对账）。注意：额度账户创建走同步链路，不在此处。
- 订阅续期检查。
- 失败补偿。
- 用量统计聚合。
- 邮件、站内通知、运营报表。

典型事件（schema 见 §11 版本化约定）：

```txt
subscription.activated.v1
subscription.renewed.v1
subscription.canceled.v1
payment.succeeded.v1
payment.failed.v1
token.usage.recorded.v1
quota.exhausted.v1
```

跨服务查询与报表：微服务 + 独立 schema 的架构下，管理后台的跨服务查询（如"用户列表 + 订阅状态 + 本月用量"）走两种路径：

1. **异步聚合**（实时性要求低）：quota-job / billing-job 定时（如每小时）从各服务拉数据，写入聚合表或物化视图。管理后台查聚合表而非直接 JOIN 各服务。典型场景：运营报表、用量排行、月度对账。
2. **BFF 并行编排**（实时性要求高）：BFF 并行调用多个服务的 gRPC 接口，在内存中合并结果后返回。典型场景：Web BFF 的用户详情页（user + subscription + token_balance）、Desktop BFF 的上下文预检（user + subscription + usage_trend）。单次请求的并行调用数不超过 3 个服务，任一失败不阻塞其他返回（部分降级）。

管理后台作为内部工具，不复用 C 端 BFF，也不让浏览器直接访问内部领域服务。目标形态是独立的 `admin/interface`（或 admin BFF）经 Kong / 内网入口暴露，使用独立管理员认证、RBAC、审计日志和更严格的操作确认。admin-interface 可以编排各领域服务的内部 API 或查询 reporting/read-model，但不得绕过服务边界直接 JOIN 领域表。

### 5.8 跨服务一致性与 Saga

支付 → 订阅 → 额度 是跨三个服务的链路，是本系统最关键的分布式事务场景。必须按 saga 设计，不能靠"发一次事件就完事"。

原则：

- 不依赖跨服务事务（无 2PC）。
- 写库与发事件通过 **outbox 原子化**。
- 消费端必须幂等。
- 失败要有补偿或可兜底的兜底路径。
- 用户可见结果走同步链路，副作用走异步链路。

Outbox 模式（避免 dual-write）：

billing-service 在更新 `orders / payments / subscriptions` 的**同一 DB 事务**里写 `outbox_events`，由独立 relay 进程投递到 RabbitMQ。这样保证"DB 提交即事件最终发出"，不会出现"付了钱但事件丢失"或"DB 回滚但幽灵事件已发出"。

幂等消费：

每个事件带全局唯一 `event_id` + 领域自然键（如 `subscription_id + period_start`）。消费端用去重表或唯一约束保证重投递只生效一次。`webhook_events` 是同一思路在入口侧的应用，内部事件消费同样要求。

补偿：

若额度账户创建最终失败（例如长时间不可达），saga 不能"乐观成功"了事：标记订阅异常 → 通知运营 → 进入退款或人工处理流程。每一步都要可追溯，不留脏状态。

同步与异步的边界：

- 同步：支付回调成功 → billing 本地事务记录支付成功和订阅待激活 → 事务提交后同步、幂等创建当期 token_account（billing 直连 quota gRPC）→ 标记订阅 active。用户付完钱应尽快可用，但不能通过跨服务事务伪装强一致。
- 异步：通知发送、统计聚合、续期、报表。
- 判断准则见 §11：同步链路只做必要的用户可见结果，耗时或可补偿动作进队列。

最终一致性窗口：

同步激活后用户立即可用；但前端展示的"用量趋势/历史"如果来自异步聚合，可能有短暂延迟。前端对"刚付完是否能用"应查询权威接口（quota-service），不查异步聚合表。

trace 上下文：

saga 链路横跨同步 RPC 与异步事件，必须全程透传 `trace_id`（见 §12），否则链路失败时无法定位是哪一跳。

## 6. 套餐与 token 额度模型

套餐不是简单的会员状态，而是“月费订阅 + 每月 token 额度”。

示例套餐：

```txt
Free       每月 10,000 tokens
Basic      每月 500,000 tokens
Pro        每月 2,000,000 tokens
Premium    每月 10,000,000 tokens
```

额度校准（重要）：token 额度必须按真实单次上下文规模校准，不能拍脑袋。长篇小说生成单次即可达数十万 token，Free 档 10,000 tokens 实际上**一次请求就会用尽甚至不足**，名义存在却不可用。各档 `monthly_token_quota` 必须与 `max_context_tokens`、`max_rpm`、典型工作流步数联合对账后再定。示例数字仅作量级参考，上线前需用真实 prompt 链路重算。

套餐维度：

- 月度 token 额度。
- 每分钟请求限制。
- 单次最大上下文。
- 可用模型等级。
- 是否支持高级工作流。
- 是否支持视频相关能力。

额度账本与成本账本分开：

- 用户侧展示和限额使用 `quota_tokens / used_tokens / remaining_tokens`，保证产品规则简单可解释。
- 平台侧成本使用 `provider / model / prompt_tokens / completion_tokens / unit_price / cost_amount / currency / exchange_rate` 记录真实成本，用于毛利、风控和对账。
- 不同模型输入/输出价格不同，不能只用 `total_tokens` 粗略估算平台成本；套餐定价必须同时参考用户额度、模型路由比例和真实 provider 成本。
- 成本账本不可作为用户扣费唯一依据，用户扣费以 quota-service 的额度账本为准；成本账本用于运营分析、异常检测和财务对账。

订阅周期：

```txt
用户购买套餐
  |
  v
billing-service 创建订单
  |
  v
微信支付 / 支付宝完成扣款
  |
  v
billing-service 接收并验证支付回调
  |
  v
本地事务：更新 order / payment / subscription(quota_pending) + 写 payment.succeeded.v1 outbox
  |
  v
事务提交后：同步、幂等创建当期 token_account（billing 直连 quota gRPC）
  |
  v
创建结果
  ├─ 成功：本地事务标记 subscription active + 写 subscription.activated.v1 outbox
  └─ 失败：标记 activation_failed，等待补偿任务重试或人工处理
  |
  v
relay 投递 payment.succeeded.v1 / subscription.activated.v1（outbox → MQ，供下游异步消费）
  |
  v
worker 消费：通知 / 统计 / 聚合
```

月度重置不应清空旧账户，而是创建新的周期账户：

```txt
subscription: Basic
period: 2026-07-01 ~ 2026-08-01
quota_tokens: 500000
used_tokens: 0
```

这样便于查账、统计、排错和对账。

## 7. 套餐升级与降级

建议规则：

升级：

- 立即生效。
- 可补差价。
- 当前周期额度按新套餐补齐或按比例增加。
- 升级产生的额度调整必须写入独立账本记录（如 `quota_adjustments`），不能直接覆盖 `quota_tokens` 后丢失调整原因。

降级：

- 下个周期生效。
- 当前周期仍保持原套餐。
- 已支付周期内不回收已授予额度，除非退款/风控明确触发补偿流程。

退款 / 取消：

- 取消订阅不等于退款；取消只改变下个周期续费行为。
- 退款必须由支付平台回调或服务端主动查询确认后生效，并通过 billing saga 调整 subscription 状态、quota 状态和成本/收入对账。
- 若退款发生在额度已使用之后，需按产品规则决定是否允许负额度、冻结云端 AI、或进入人工处理；该规则必须在 billing 与 quota 的 saga 中显式建模。

订阅表保留计划变更字段：

```sql
scheduled_plan_id,
scheduled_change_at
```

### 8.1 BFF / API 组合层

每个端有独立的 BFF（Backend for Frontend），不共享——这是 BFF 模式的核心约束。不同端的视图粒度、鉴权路径、数据量级、可用性要求不同，共用一个 BFF 会导致端差异渗透到聚合层，最终变成"万能胶水层"。

| BFF | 对应端 | 鉴权方式 | 定位 | 落地阶段 |
|-----|--------|---------|------|:---:|
| `bff/web/interface` | Web 官网 | C 端 JWT（Cookie/Header） | 官网、定价、账号中心、订阅购买 | 第二阶段 |
| `bff/desktop/interface` | 桌面端云端模式 | PKCE + JWT（Keychain 存储） | 云端 AI 调用、套餐查询、同步接口 | 第四阶段 |
| `bff/mobile/interface` | 移动端 | JWT（安全存储） | 灵感记录、轻量创作、余额查询 | 第五阶段 |
| `admin/interface` | 管理后台 | 独立管理员认证 + RBAC | 用户管理、订阅管理、运营报表、对账 | 第六阶段 |

契约放在 `services/api/bff/<端>/interface/v1/` 下，与实现路径镜像。各 BFF 的 proto 可以共享公共 message（如 TokenBalance、Subscription），但 service 定义独立——不同端需要的聚合视图不同，不应为了复用而把各端接口揉进同一个 service。

```http
# Web BFF 示例
GET /v1/me/dashboard            -- user + subscription + token-balance
GET /v1/me/usage-trend          -- 用量趋势 + 聚合统计

# Desktop BFF 示例（更重的上下文预检）
GET /v1/me/context-preflight    -- user + subscription + usage_trend + ai_gateway/model-list

# Mobile BFF 示例（精简视图）
GET /v1/me/brief                -- display_name + plan + remaining_tokens（三字段轻量视图）

# Admin BFF 示例（独立 /admin/ 路径前缀）
GET /v1/admin/users             -- 用户列表 + 订阅状态 + 本月用量（跨服务聚合）
GET /v1/admin/subscriptions     -- 订阅管理
```

约定：

- 每个 BFF 只做自己端的聚合、裁剪、视图编排，不写业务逻辑，不持有状态。
- SDK 只暴露面向自己端的聚合视图，不镜像内部服务拆分。服务边界变更不应传导到前端。
- 内部领域服务仍各自对外暴露 REST（供 CLI、内部工具、跨 BFF 调试等场景），BFF 是面向各端的优选路径。
- BFF 不直接读写领域 schema。通知、报表、运营聚合等不是 BFF 的私有状态：实时视图走下游服务编排，低实时性视图走 reporting/read-model，通知能力归 `notification` 领域服务。
- BFF 做端侧差异化视图（Web/Desktop/Mobile/Admin 返回字段不同），但业务规则必须归属到对应领域服务，不能沉到 BFF。
- Web 与 Desktop BFF **不共享**——桌面端的上下文预检、批量同步等需求与 Web 官网的账号中心差异显著，共享会导致两端互相拖慢迭代节奏。

### 8.2 HTTP API 版本化

对外 HTTP API 采用 URL 前缀版本化。Web / Mobile / Desktop / SDK / E2E 一律调用 `/v1/...`，禁止客户端调用无版本路径。BFF 内部可以选择原生挂载 `/v1`，也可以由 Kong 剥离版本前缀后转发，但该实现细节不得泄露给客户端。

外部路径：

```http
POST /v1/auth/register
POST /v1/auth/login
GET  /v1/me/dashboard
POST /v1/ai/chat
```

版本化约定：

- URL 前缀版本与 proto 目录 `v1` 保持语义一致（`/v1/...` 对应 `api/*/v1/` 下的契约定义）。
- 不兼容变更必须升主版本号（`/v2/...`），同时保留旧版本至设定的废弃窗口结束。
- 兼容新增字段（如返回体新增字段、新增可选 query 参数）不升版本号。
- Kong 路由按 `/v1/` 前缀匹配，支持 `/v1/` 与 `/v2/` 并存路由到不同 upstream 或同一 BFF（由 BFF 内部按版本分发）。
- 废弃窗口建议：旧版本标记为 deprecated 后，至少保留一个发布周期（如 30 天），在响应头中返回 `Deprecation: true` 和 `Sunset` 日期。

通用请求头：

- `Authorization: Bearer <access_token>`：用户身份。
- `X-Request-Id`：客户端生成或边缘生成的请求 ID，用于日志聚合。
- `traceparent / tracestate`：W3C Trace Context，客户端可透传，Kong 可补齐。
- `X-Idempotency-Key`：非幂等写接口建议支持；AI 调用、创建订单、支付确认等关键接口必须支持。

通用响应头：

- `X-Trace-Id`：服务端 trace 主键，错误排查时必须返回。
- `Retry-After`：限流或短暂不可用时返回，客户端据此退避。
- `Deprecation / Sunset`：API 废弃窗口内返回。

## 9. Kong 网关职责

Kong 负责外部入口层：

- 路由。
- HTTPS。
- 基础限流。
- 请求日志。
- CORS。
- 认证前置。
- 服务发现或 upstream 管理。

Kong 只做"对外入口"的职责：解析并校验外部 JWT、剥离不合法请求、基础限流。**业务鉴权与资源归属校验必须放在服务内**，不能只依赖网关——网关通过不代表该用户有权访问该资源。服务间内部调用不经 Kong，其鉴权见 §13。

支付 webhook 是例外入口：它来自微信支付 / 支付宝等第三方平台，不携带用户 JWT。Kong 应按独立 route 转发到 billing webhook ingress，并保留原始 body 给 billing 验签。webhook 的安全边界是平台签名、时间戳/nonce、防重放、幂等入库、来源限制和审计日志，不是 C 端登录态。

身份头传播规则：

- 客户端请求进入 Kong 前，任何 `X-User-* / X-Internal-* / X-Service-*` 头都视为不可信，必须被剥离。
- Kong 验证 JWT 后注入内部身份上下文，至少包含 `user_id / session_id / plan_code / trace_id`；敏感 claims 不透传给前端。
- BFF 将 HTTP 身份上下文转换为 gRPC metadata，下游服务仍需校验资源归属。
- 内部服务间调用使用 mTLS 或 service token 标识调用方服务，避免任意内部 Pod 冒充 BFF。

限流分层策略：Kong 负责网络层的粗粒度保护，业务级限流由各服务内部实现：

| 层级 | 位置 | 维度 | 示例 |
|------|------|------|------|
| 全局硬上限 | Kong | 全局 QPS | 1000 req/s（防 DDoS） |
| 单 IP 限制 | Kong | 单 IP QPS | 100 req/s（防单 IP 滥用） |
| 单用户差异化 | Kong（按 JWT claim 中的 plan 等级）| 单用户 QPS | Free 20 / Basic 60 / Pro 120 / Premium 300 req/s |
| 业务级速率 | ai-gateway（max_rpm） | 单用户每分钟 AI 请求数 | 由套餐 plan.max_rpm 控制 |
| 登录保护 | auth-service（Redis） | 单 IP/单邮箱 失败次数 | 5 次失败后锁定 15 分钟 |

Kong 的限流仅做粗粒度保护，不替代服务内的业务限流。Kong 限流超限返回 429，服务内限流超限也返回 429，客户端应根据 `Retry-After` 响应头退避。

## 10. Redis 职责

Redis 用于：

- 登录失败限流。
- 邮箱验证码发送频率计数；验证码哈希、有效期和消费状态保存在 auth PostgreSQL 表中。
- API 限流计数。
- 临时会话状态。
- 热点套餐和配置缓存。
- AI 请求短期幂等 key。
- user / plan 等只读热数据的短期缓存（结合 §13 身份传播）。

权威数据仍以 PostgreSQL 为准。Redis 只做缓存和计数，不作为可信源。

## 11. RabbitMQ 职责

RabbitMQ 用于削峰和异步解耦：

- 支付成功后的下游处理（通知、统计、对账）。额度账户创建走同步链路，不在此处。
- 订阅续期。
- 支付失败重试。
- token 用量聚合。
- 通知发送。
- 后台报表。
- 失败补偿任务。

同步链路只做必要的用户可见结果，耗时或可补偿动作进入队列。

事件契约版本化（与 API 契约同等管理）：

- 事件名带版本：`subscription.activated.v1`，不兼容变更必须升版本号。
- payload schema 放在 `services/events/<领域>/vN/`，用 protobuf 或显式 JSON Schema 管理；producer 改字段需向前兼容。
- consumer 按版本路由，旧版本消费者在新事件到来时不应崩溃。
- RabbitMQ 不自带 schema registry，需在 CI 校验事件 schema、示例 payload、producer/consumer 兼容性。
- 一个 topic exchange 可绑定多个领域专属 queue；不要让不同领域的消费者竞争同一 queue。

Outbox relay：

- 独立进程扫 `outbox_events`，未投递的记录投到 MQ，成功后回写 `published_at`。
- relay 崩溃重启后从 `published_at IS NULL` 继续，天然幂等。
- 配合消费端 inbox、领域唯一约束和 DLQ，整条链路是至少一次投递、效果幂等；不要宣称消息队列层提供恰好一次。

## 12. 可观测性

微服务的可观测性不是可选项。token 计量、支付、AI 调用这些链路横跨多个服务，没有跨服务追踪基本无法排障。落地组件栈在 `deploy/docker-drama/docker-compose.yaml`，下方按「排查优先级」组织——接到告警后的典型动线是：指标发现问题 → 链路定位服务 → 日志深挖到行。各 Go 微服务（auth / user / billing / quota / ai-gateway / notification / bff / job）是三支柱的共同数据源。

数据流总览：

```txt
Go 服务 ──traces/metrics(OTLP)──> otel-collector ──traces──> jaeger
Go 服务 ──stdout──> docker json-file ──> fluent-bit ──> opensearch ──> opensearch-dashboards
Go 服务 ──/metrics(pull)──> prometheus ──> grafana
opensearch ───────────────────────────────────────────────> grafana
```

指标（Prometheus）—— 告警/排障第一站：

- Prometheus 拉模型抓取各服务 `/metrics`，TSDB 存储周期由部署配置决定（本地建议 15 天）。
- 业务指标：支付确认结果、额度预扣拒绝数、outbox 堆积数、Provider 成本风控事件；指标仅使用枚举型结果和 Provider 名称，不能把订单号、用户 ID、错误文本、prompt 或正文放进 label。
- 系统指标：每服务 QPS、直方图延迟分位（p50/p95/p99）、错误率、RabbitMQ 队列堆积、DB 连接池和等待计数。告警阈值、面板和逐项处置手册见 [LM3-22 指标告警记录](./loop/LM3-22-指标告警与错误聚合.md)。

链路追踪（OpenTelemetry Collector → Jaeger）：

- 数据流：Go 服务经 `OTEL_EXPORTER_OTLP_ENDPOINT` 推到 otel-collector（OTLP gRPC :4317 / HTTP :4318），collector 再把 traces fan-out 到 jaeger。
- otel-collector 是三支柱的共同中转入口；metrics/logs 也可经它下发，视 `otel-collector/config.yaml` 配置。
- Jaeger 作为本地和测试环境的 trace 查询入口；生产可替换为托管 tracing 或更长期存储，组件版本由部署清单锁定。
- 一次 `/ai/chat` 请求要穿 `Kong → ai-gateway → quota → 模型 → 回 quota`，全链路一个 trace。
- `trace_id` 通过 W3C `traceparent` + HTTP header / gRPC metadata 透传；RabbitMQ 同时携带 `traceparent` 和兼容 `trace_id`。outbox relay 会从持久化 `trace_id` 恢复一个远程父上下文，再创建 publish/consume span，串联同步调用与异步事件（含 §5.8 的 saga 链路）。
- ai-gateway 的模型出站调用作为独立 span，能直接看到真实模型耗时与重试。

日志（Fluent Bit → OpenSearch → OpenSearch Dashboards）：

- 数据流：服务打结构化日志到 stdout → 宿主 docker json-file 落盘 → fluent-bit tail 后写入 opensearch → opensearch-dashboards / Grafana 检索。
- fluent-bit：`/fluent-bit/state` 持久化 tail DB 偏移，重启不重读、日志不重复。容器名、service 名等字段需通过日志驱动、processor 或 Lua 注入补齐。
- OpenSearch：本地可用 single-node，生产环境必须开启认证、TLS、索引生命周期和权限隔离。
- JSON 日志统一字段：`timestamp / level / service / trace_id / span_id / user_id / request_id`，按 service + trace_id 可串联检索。
- 敏感字段（API Key、token、手机号、密码哈希）以及正文、prompt、payload、provider 原始响应都不得落日志；结构化日志对嵌套字段、Bearer/DSN 片段和常见凭据键做二次脱敏。

可视化前端（Grafana + OpenSearch Dashboards 并存，分工不同）：

- Grafana 通过 provisioning 同时接 Prometheus（指标，默认数据源）和 OpenSearch（日志），做指标大盘和跨源统一视图；日常排障/看板的主入口。
- OpenSearch Dashboards 只连 OpenSearch，负责日志深挖（Discover）和未来 OpenSearch 集群运维（索引模板、ISM 生命周期、告警/anomaly 插件）。与 Grafana 在「日志可视化」上有重叠，两者按场景分工而非互替。

错误上报：

- 当前以 `dramaip_errors_total{service,operation,class}` 作为 Sentry 的同类聚合信号；`operation` 和 `class` 都在进程内归一化，绝不使用原始错误文本。Sentry 接入时必须沿用同样的脱敏约束。
- 指标不携带 `trace_id`，以免造成无限时间序列；告警先按 service/operation/class 收敛，再用同一时间窗在 OpenSearch 以 service 检索 `trace_id`，最后到 Jaeger 定位完整链路。

trace_id 必须从 Kong 入口生成或透传，贯穿 BFF、各服务、MQ、worker，是整套可观测性的主键。

## 13. 安全要求

必须实现：

- 密码 `bcrypt` 哈希。
- refresh token 服务端保存哈希。
- access token 使用短 TTL；生产环境优先采用非对称签名（RS256 / ES256）+ JWKS 发布公钥，支持 key rotation。禁止多个服务共享长期 HMAC 签名密钥作为生产默认方案。
- 登录失败限流。
- 支付回调验签。
- webhook 幂等处理。
- 订单号全局唯一。
- 后端查询支付平台确认状态。
- 不从客户端直接修改订阅状态。
- token 扣减原子化。
- 敏感操作审计日志。
- API Key 不下发给 Web/Mobile。
- 平台 API Key 不进入开源桌面仓库。

身份传播与服务间鉴权：

- 对外：客户端持短期 access token，Kong 通过 JWKS 校验签发、过期、issuer、audience 和 key id。
- 对内：生产环境服务间 gRPC 使用 TLS 1.3 mTLS；每个 workload 使用 CA 签发的独立证书，服务端只接受允许的客户端证书 CN。证书、私钥和 CA 仅以受控文件挂载提供，缺少 mTLS 配置时生产进程必须拒绝启动。**禁止"来自网关所以可信"的假设**；每个服务仍需校验调用方身份与权限。
- Kong 在转发前剥离客户端传入的 `X-User-*` 身份头。Web BFF 只在验证 JWT/Redis session 后才以内部 gRPC metadata 传播 user_id；user、subscription/order 和 AI 等用户资源服务必须将该身份与请求资源归属比对。
- 横向越权防护：所有按 `user_id / subscription_id / token_account_id` 查询或修改的接口，必须校验该资源归属于当前身份，不能只信任传入的 id 参数；账本内部编排仅允许经 mTLS 认证的指定领域服务调用。

客户端 token 存储：

- Web：Web BFF 使用 `HttpOnly + Secure + SameSite=Lax` access/refresh Cookie（生产强制 `Secure`，refresh Cookie 限定认证路径），由 BFF/Auth 设置和轮换；优先同源/host-only，跨受控子域时才显式配置共同父域。JavaScript 不读取长期或短期 token。所有 Cookie 会话的状态变更接口使用双提交 CSRF 防护。
- Desktop：refresh token 存系统 Keychain，access token 仅存内存，登录流程使用 Authorization Code + PKCE（见 §3.1）。
- Mobile：refresh token 存系统安全存储（iOS Keychain / Android Keystore），access token 仅存内存或短期安全存储。
- 所有端都不得把 refresh token 写入 localStorage、URL、日志、崩溃上报或普通业务数据库。

桌面端本地安全：

- 用户自填 API Key 优先存于**系统 Keychain**（macOS Keychain / Windows Credential Manager / libsecret）。
- 不在本地 DB 存明文 Key，也不用"DB 加密字段"——若加密 key 藏在 app 内部，那只是混淆不是安全。
- 实现上，SQLite 只保存不可用作认证的凭据引用；新建或更新必须先确认系统凭据库写入成功，再替换旧引用。旧版 SQLite 密文/明文迁移失败时保留原值并记录不含密钥的审计状态，数据库备份提供恢复边界。
- 返回 renderer 时显示掩码，不返回明文。
- 云端模式下桌面端不需要知道平台 API Key。

创作内容与隐私：

- 本地优先模式下，项目正文、人物设定、分镜、素材等创作资产默认只存本地，除用户显式发起云端 AI、云同步或分享外，不上传云端。
- 云端 AI 模式下，ai-gateway 只接收完成本次模型调用所需的最小上下文；长文本、素材和项目包不得无边界整包上传。
- 请求审计表默认记录 request_id、hash、模型、token usage、状态和错误摘要；原始 prompt / response 如需落库，必须有明确产品目的、保留周期、脱敏策略和用户可删除路径。
- 日志、trace、错误上报禁止包含正文内容、prompt 全文、access token、refresh token、API Key、支付敏感字段。
- 模型供应商的数据保留、训练使用和跨境传输策略必须在 provider 配置与用户协议中体现；企业/团队版本需支持更严格的 provider 白名单和数据不留存选项。

备份与恢复：

- PostgreSQL 是权威源（订单、支付、订阅、token 账本）。必须有定期全量 + 增量备份，以及经过演练的恢复流程。支付与账本数据丢失是事故级风险。

## 14. 演进路线

第一阶段：整理目录和文档

- 父级 `docs/` 保存通用文档。
- `dramaip-desktop` 保持桌面端项目。
- `dramaip-platform` 新增闭源平台项目。

第二阶段：官网与账号体系

- 建立 `clients/apps/web`。
- 建立 `auth-service`。
- 支持注册、登录、refresh token。
- Web 账号中心接入。
- 对外 API 统一到 `/v1/...`。
- 可观测性地基（日志、指标、trace-id 透传）在服务诞生第一天就接入。

第三阶段：订阅和额度

- 建立 `billing-service`。
- 建立 `quota-service`。
- 接入微信支付和支付宝。
- 支持套餐购买、支付回调、月度 token account。
- 支付 webhook 作为独立入口接入 billing，不经过 C 端 BFF。
- 订单、订阅、quota account 写入套餐快照，防止套餐变更后历史权益无法对账。
- outbox + saga + 同步激活随支付链路一起落地。

第四阶段：AI 网关

- 建立 `ai-gateway-service`。
- 用户无需填 API Key 即可使用平台模型能力。
- Web/Mobile/Desktop 都可调用云端 AI。
- 桌面端保留本地 API Key 模式作为可选路径。
- 建立 `bff/desktop/interface`：桌面端云端模式专用 BFF，提供上下文预检、模型列表等聚合接口，与 Web BFF 独立部署。
- AI 预扣、结算、request audit、成本账本和幂等重放规则全部落地后，才能开放平台 API Key 托管能力。

注意：若第三阶段先上线订阅、第四阶段再上线云端 AI，第三阶段的付费用户仍使用自己的 API Key 驱动桌面端，订阅价值来自桌面能力与未来云端额度。销售页面必须清楚说明云端 AI 的上线阶段，避免"付了费却没有云端 AI"的预期落差。

第五阶段：移动轻创作

- 建立 `clients/apps/mobile`。
- 建立 `bff/mobile/interface`：移动端专用 BFF，提供精简视图（三字段余额、草稿同步等）、离线同步支持。
- 支持灵感、草稿、AI 快速扩写。
- 支持同步到桌面端继续精修。

第六阶段：平台化能力

- 资源市场。
- 云同步：本地优先 + 云同步涉及冲突解决（CRDT / last-write-wins / 手动合并），是已知难点，需单独设计冲突策略，不在本架构展开。
- 私有知识库。
- 管理后台：建立 `admin/interface`，独立管理员认证 + RBAC + 审计日志 + 操作确认。管理员操作不经 C 端 BFF，不走 C 端 JWT 鉴权路径。
- 运营报表。
- 团队与企业账号：多租户不要用 `users.tenant_id` 表达，因为同一用户可能加入多个团队。目标模型应采用全局用户身份 + 租户成员关系 + 计费归属三层：

  ```sql
  tenants (
    id,
    name,
    status,
    created_at,
    updated_at
  );

  tenant_memberships (
    tenant_id,
    user_id,
    role,
    status,
    created_at,
    updated_at
  );
  ```

  个人账号可视为 `account_scope = personal`，团队账号可视为 `account_scope = tenant`。`subscriptions / token_accounts / orders / usage_logs` 等计费和额度表应预留 `account_scope` 与 `tenant_id`（nullable）或等价的 `account_id + account_type` 设计；`users` 仍保持全局身份表，不绑定单一租户。团队计费需单独设计分摊模型（按席位/按用量/混合），不在当前订阅模型中展开。

## 15. 架构验收门槛

后续代码向本文收敛时，每个阶段至少通过以下验收门槛：

**契约门槛**

- 外部 API 只暴露 `/v1/...` 路径，SDK、Web、Mobile、Desktop、E2E 使用同一版本化入口。
- 每个端有独立的 BFF proto 契约（`api/bff/<端>/interface/v1/`），不共享同一个 service 定义。公共 message 可跨 proto 复用，但 service 独立。
- proto / OpenAPI / events schema 在 CI 中做 lint、breaking-change 检查和 SDK 生成校验。
- 非幂等写接口必须支持 `X-Idempotency-Key`，重复请求不能造成重复扣费、重复订单或重复模型调用。

**数据门槛**

- 每个服务使用独立 DB role，只能访问自己的 schema；跨 schema 读取必须由 API、事件投影或 reporting/read-model 承接。
- BFF 不得直接 JOIN 领域 schema；跨域读模型必须由领域 API、事件投影或 reporting/read-model 承接。
- 订单、订阅、token account、AI request audit、provider 成本记录必须保留可对账快照，不能只引用后续可变的配置表。
- billing / quota / ai-gateway 的关键写路径必须有并发测试，覆盖重复 webhook、重复结算、额度不足、预扣过期和超额 usage。
- 所有账本类表只追加或保留可审计历史，不用覆盖写掩盖过去状态。

**安全门槛**

- 生产环境 access token 通过 JWKS 验签，支持 key rotation；refresh token 服务端只存哈希。
- Web / Desktop / Mobile 分别按 §13 的安全存储策略保存长期凭据。
- `admin/interface` 使用独立管理员认证体系（与 C 端 JWT 完全分离），强制 RBAC 和操作审计。
- secret scanning、依赖扫描和日志脱敏检查进入 CI；支付密钥、模型 API Key、JWT 私钥不得进入 Git、镜像层或客户端包。

**一致性门槛**

- 支付成功到订阅激活、额度账户创建、事件投递必须有 saga 状态机和补偿路径。
- outbox relay 支持重启续投；consumer 幂等；失败事件有重试、死信或人工处理入口。
- 对账任务能从支付平台、billing、quota 三方重建订单/订阅/额度状态。

**可观测性门槛**

- 每个外部请求返回 `X-Trace-Id`；trace 能跨 Kong、BFF、gRPC 服务、MQ、worker 串起来。
- 指标至少覆盖 QPS、错误率、延迟分位、支付成功率、quota 拒绝数、outbox 堆积、AI provider 延迟和成本。
- 结构化日志必须包含 `service / trace_id / request_id / user_id(可脱敏)`，并禁止输出 token、API Key、密码哈希和支付敏感字段。

**端到端门槛**

- 标准 E2E 必须覆盖：注册/登录 → 查看套餐 → 创建订单 → 模拟或沙箱支付 → 创建额度账户 → AI 预扣/结算 → 用量查询 → refresh/logout。
- 各 BFF 上线前需通过自己端的 E2E：Web BFF 覆盖账号中心全流程，Desktop BFF 覆盖云端模式预检 + AI 调用，Mobile BFF 覆盖精简视图 + 草稿同步，Admin BFF 覆盖管理员认证 + 跨服务查询。
- 生产前必须新增真实支付沙箱 webhook E2E、AI provider 失败/超时 E2E、并发额度扣减压测和恢复演练。
