# DramaIP 技术架构

本文记录 DramaIP 的整体技术设计。当前阶段采用一个父目录管理两个项目：

- `dramaip-desktop`：桌面端项目，未来可能开源。
- `dramaip-platform`：官网、移动端和云端服务，保持闭源。

通用产品、架构、路线与流程文档放在父级 `docs/` 下。

## 1. 架构目标

DramaIP 的产品形态分为三类入口：

1. 桌面端：专业创作工作台，本地优先，适合长文本、复杂项目、AI 工作流、导出交付。
2. Web 官网：产品官网、定价页、下载页、登录注册、订阅购买、账号中心。
3. 移动端：轻量创作入口，用于随手记录灵感、创建草稿、查看套餐和 token 余额。

云端服务负责：

1. 用户登录与账号体系。
2. 月费套餐订阅。
3. 每月 token 额度和用量账本。
4. 用户无需填写 API Key 的 AI 代理调用。
5. 支付回调、订阅续期、异步任务和运营后台能力。

核心原则：

- 登录只证明“用户是谁”。
- 订阅和额度决定“用户能用多少”。
- 桌面端保持本地优先，不把云端作为创作数据的唯一可信源。
- 支付状态以后端支付回调为准，不信任客户端支付成功提示。
- token 扣减必须可审计、可幂等、可追踪。
- 云端采用微服务架构。服务边界沿有界上下文和扩展性差异切分；切完之后的正确性靠数据自治、Saga、可观测性保证，而不是靠"多拆几个进程"。

### 2.1 dramaip-desktop

`dramaip-desktop` 是本地优先的 Electron 桌面端项目。

```txt
dramaip-desktop/
  apps/
    desktop/
      electron/         Electron main / preload / IPC / 本地运行时
      renderer/         React UI

  packages/
    core/               TS 类型、Zod schema、常量
    db/                 本地 SQLite + Drizzle + repositories
    ai/                 本地 AI workflow、provider、prompts、LangGraph 节点
    export/             Markdown / JSON / CSV / 项目包导出

  docs/                 桌面端专属开发、使用、发布文档
  scripts/
  tests/
```

注意：`apps/desktop` 不是纯前端。`renderer` 是前端 UI，`electron` 更像本地后端，负责 IPC、数据库、密钥、文件、安全策略和 AI 调用。

#### 目录约定（判断结构是否合理的五条标准）

1. **契约与实现分离，路径镜像**：`api/<领域>/<类型>/v1/*.proto` 与 `app/<领域>/<类型>/` 一一对应，改契约能立刻定位到服务。
2. **按 `<领域>/<类型>` 切，不是 `<类型>/<领域>`**：`billing/job` 正确，`job/billing` 错误。`service` / `job` / `interface` 是**类型**，按触发方式区分——`service` = 同步领域服务（被其它服务 gRPC 调用）、`job` = 异步任务（定时器 / MQ 触发）、`interface` = 面向前端的 BFF 聚合层；它们不是领域，提到顶层会造成 worker 大杂烩。
3. **每个 `app/<领域>/<类型>/` 内部遵循 kratos-layout**：`cmd/server/{main.go, wire.go}` + `configs/` + `internal/{conf, server, service, biz, data}` 五层。
4. **共享代码沉到 `pkg/`，但只沉项目特有的**：Kratos 自带的 `log / tracing / validator / middleware` 不在 `pkg/` 里重新包一层；`pkg/` 放 token 解析、业务中间件、outbox relay 等**加值**代码。
5. **基础设施与代码分离**：Kong、k8s、Docker 配置放 `deploy/`，不和服务源码混。

#### Kong 在结构中的位置

网关用 Kong，**不要再造一个 Kratos 的 gateway 服务**——Kong 就是网关。流量分工：

```txt
外部客户端（web / mobile / desktop）
    │  HTTPS
    ▼
Kong   ── TLS / 路由 / JWT 校验 / 限流 / CORS      ← 外部入口，配置在 deploy/kong/
    │  HTTP
    ▼
bff/interface（聚合多服务，按需）                  ← 普通 Kratos 服务，不是网关
    │  gRPC（内部直连，不经 Kong）
    ▼
auth / user / billing / quota / ai-gateway
```

- 外部流量过 Kong，Kong 负责鉴权前置和限流。
- 内部服务间 gRPC **直连，不走 Kong**（Kong 是外部入口，不是内部总线）；内部靠 K8s DNS / 服务发现 + mTLS。
- BFF 只做聚合，鉴权 / 限流交给 Kong，不在 BFF 里重写。
- Kong 配置（路由、插件、consumer）放 `deploy/kong/`，用 decK 或 `kong.yml` 声明式管理。

### 2.3 开源与闭源边界

推荐以仓库边界控制开源风险：

```txt
public:
  dramaip-desktop

private:
  dramaip-platform

optional:
  API contracts / SDK，可公开也可随 desktop 发布
```

桌面端可开源的内容：

- Electron + React 桌面应用。
- 本地 SQLite 数据层。
- 基础 AI provider 接口和本地工作流。
- 导出能力。
- 桌面端文档、测试和脚本。

不建议开源的内容：

- 用户、订阅、支付、token 账本服务实现。
- 微信支付、支付宝的商户配置和回调处理。
- 平台级模型代理、风控、成本控制。
- 商业 prompt、资源市场审核规则、运营后台。
- 生产环境部署、Kong、数据库、队列和密钥配置。

桌面端如需使用云端套餐，通过公开 API 调用闭源服务，不直接包含服务端实现。

契约（proto / OpenAPI / 事件 schema）建议作为**独立版本化产物**管理，跨 `dramaip-desktop` 与 `dramaip-platform` 两个仓库引用同一版本，避免契约漂移。SDK 版本与契约版本绑定。

## 4. 云端服务技术栈

服务端选择：

```txt
语言：Go
框架：Kratos
数据库：PostgreSQL
缓存：Redis
ORM：GORM
认证：JWT + Refresh Token
密码哈希：bcrypt
支付：微信支付 + 支付宝
任务队列：RabbitMQ
网关：Kong
部署：Docker
可观测性：OpenTelemetry + Prometheus + 结构化日志
```

服务调用关系：

```txt
Client Apps（web / mobile / desktop）
  |
  v
Kong Gateway                 外部入口：TLS / 路由 / JWT 校验 / 限流 / CORS
  |
  v
bff/interface（按需聚合）      普通 Kratos 服务，不是网关
  |   gRPC（内部直连，不经 Kong）
  v
Kratos Services：auth / user / billing / quota / ai-gateway
  |
  +-- PostgreSQL   +-- Redis   +-- RabbitMQ
```

通信方式：

- 外部客户端到服务端：HTTP API，经 Kong 入口。
- 内部服务间：gRPC 优先。
- 异步事件：RabbitMQ。
- 缓存和限流辅助：Redis。
- 权威数据：PostgreSQL。

## 5. 服务拆分

### 5.0 数据自治与服务边界原则

微服务的正确性建立在数据自治上，不是建立在"拆了多少个进程"上。所有服务拆分遵循以下硬约束：

- **数据自治**：每个服务独占自己的数据。当前阶段采用**每服务独立 schema、共享同一 PostgreSQL 实例**；后续按负载再独立 DB。任何服务不得直连、JOIN 别服务的表，跨服务数据需求只走 API 或事件。一旦出现跨服务表 JOIN，服务边界即名存实亡，未来拆库、换库、重构都会被锁死。
- **边界沿有界上下文 + 扩展性差异切分**：`quota` 和 `ai-gateway` 单独拆出来是因为它们在 AI 热路径、扩缩容节奏、出站调用特征上与其它服务不同，这是正确的拆分理由。
- **服务内部状态可独立演进**：服务的表结构、缓存策略、内部实现变更不应对其它服务可见。
- **跨服务一致性见 §5.7**，不依赖分布式事务（无 2PC）。
- **每个 `app/<领域>/<类型>/` 内部遵循 kratos-layout**：`cmd/server/{main.go, wire.go}` + `configs/` + `internal/{conf, server, service, biz, data}` 五层（目录约定详见 §2.2）。

### 5.1 auth-service

职责：

- 注册。
- 登录。
- 密码校验。
- JWT access token 签发。
- refresh token 签发、轮换、撤销。
- 登出。
- 设备会话管理。
- 登录失败限流。

核心表：

```sql
users (
  id,
  email,
  phone,
  password_hash,
  status,
  email_verified_at,
  phone_verified_at,
  created_at,
  updated_at
);

user_identities (
  id,
  user_id,
  provider,
  provider_user_id,
  created_at
);

refresh_tokens (
  id,
  user_id,
  token_hash,
  device_id,
  expires_at,
  revoked_at,
  created_at
);
```

认证策略：

- `access_token`：短期有效，用于 API 请求。
- `refresh_token`：长期有效，用于换取新 token。
- 服务端只保存 refresh token 哈希。
- 支持主动登出、踢设备、异常会话撤销。
- 密码使用 `bcrypt`。

### 5.2 user-service

职责：

- 用户资料。
- 账号状态。
- 用户偏好。
- 与订阅、额度、设备绑定的基础信息。

`user` 与 `auth` 分开的原因：身份凭证（密码、token、会话）变更频率和安全等级，与资料/偏好不同，分属不同有界上下文。`user` 的资料会被多个服务读取，应通过 JWT claims + 短期缓存满足，避免每次请求都同步回查 user-service（详见 §13 身份传播）。

### 5.3 billing-service

职责：

- 套餐定义。
- 创建订单。
- 微信支付。
- 支付宝。
- 支付回调验签。
- 订阅创建、续期、取消。
- 退款和账单记录。
- 幂等处理。

核心表：

```sql
plans (
  id,
  code,
  name,
  billing_period,
  price,
  currency,
  monthly_token_quota,
  max_rpm,
  max_context_tokens,
  model_level,
  is_active,
  created_at,
  updated_at
);

subscriptions (
  id,
  user_id,
  plan_id,
  provider,
  provider_subscription_id,
  status,
  current_period_start,
  current_period_end,
  cancel_at_period_end,
  canceled_at,
  scheduled_plan_id,
  scheduled_change_at,
  created_at,
  updated_at
);

orders (
  id,
  user_id,
  plan_id,
  subscription_id,
  amount,
  currency,
  status,
  provider,
  provider_order_id,
  created_at,
  paid_at
);

payments (
  id,
  user_id,
  order_id,
  provider,
  provider_payment_id,
  amount,
  currency,
  status,
  raw_payload,
  created_at
);

webhook_events (         -- inbox：支付回调幂等去重
  id,
  provider,
  provider_event_id,
  processed_at,
  raw_payload,
  created_at
);

outbox_events (          -- outbox：DB 提交即事件最终发出（见 §5.7）
  id,
  aggregate_type,        -- subscription / order / payment
  aggregate_id,
  event_type,            -- subscription.activated.v1
  payload,               -- JSON / protobuf bytes
  created_at,
  published_at
);
```

支付原则：

- 不相信客户端支付成功回调。
- 订阅状态只能由服务端支付回调或服务端主动查询确认后更新。
- 支付平台 webhook 必须验签。
- webhook 必须幂等，重复事件直接忽略。
- 写库与发事件通过 outbox 原子化，禁止 dual-write（见 §5.7）。
- 支付成功后，billing 在回调中**同步、幂等地**触发当期 token_account 创建（直连 quota gRPC），用户付完钱立即可用；同时写 outbox 供下游异步消费。

### 5.4 quota-service

职责：

- 管理用户每月 token 额度。
- 创建周期额度账户。
- 检查余额。
- 扣减 token。
- 记录用量。
- 支持套餐升级、降级后的额度调整。

核心表：

```sql
token_accounts (
  id,
  user_id,
  subscription_id,
  period_start,
  period_end,
  quota_tokens,
  used_tokens,
  status,
  created_at,
  updated_at
);

token_usage_logs (
  id,
  user_id,
  subscription_id,
  token_account_id,
  request_id,
  model,
  prompt_tokens,
  completion_tokens,
  total_tokens,
  cost_amount,
  created_at
);
```

并发扣减必须使用原子更新：

```sql
UPDATE token_accounts
SET used_tokens = used_tokens + ?
WHERE id = ?
  AND used_tokens + ? <= quota_tokens;
```

如果更新行数为 0，说明额度不足。

后续可增加预扣表：

```sql
token_reservations (
  id,
  user_id,
  token_account_id,
  request_id,
  reserved_tokens,
  actual_tokens,
  status,
  created_at,
  updated_at
);
```

扣减策略演进：

1. 早期"后扣费"：请求前检查余额大于 0，模型调用完成后按真实 usage 扣费。注意并发窗口——多个请求同时通过"余额>0"检查会形成超扣，早期可接受，需配合 max_rpm 限流收敛风险。
2. "预扣 + 结算"：请求开始按估算上限预扣到 `token_reservations`，调用完成后用真实 usage 结算差额。ai-gateway 热路径采用此模式（见 §5.5）。

usage 未知的处理：流式响应的 usage 在末尾才到，个别 provider 可能不返回或返回估算值。必须约定 fallback——按输入 token 估算上限预扣，usage 回填后多退少补；不得因为"usage 未知"而放行不计量。

周期账户创建：当期 `token_account` 由 billing 在支付回调中**同步、幂等**创建（自然键 `subscription_id + period_start`，唯一约束兜底重投递），不放入异步队列。月度重置同理：worker 创建新周期账户，旧账户保留供对账（见 §5.6、§5.7）。

### 5.5 ai-gateway-service

职责：

- 替用户调用模型。
- 统一保管平台 API Key。
- 用户无需自己填写 API Key。
- 模型路由。
- 请求限流。
- token 用量计量。
- 失败重试和审计。
- 对接 quota-service 扣减额度。

请求流程（预扣 + 结算，避免热路径两次同步 RPC）：

```txt
用户请求 AI 接口
  |
  v
Kong 鉴权 / 限流
  |
  v
ai-gateway-service
  |
  +-- 校验用户身份
  +-- 调 quota-service 申请一次"预扣租约"（按估算上限，单次 RPC）
  +-- 调 OpenAI-compatible / 其他模型 API
  +-- 获取真实 usage
  +-- 异步结算：调 quota-service 用真实 usage 多退少补
  +-- 返回结果给用户
```

把"检查 + 扣减"从两次同步 RPC 压到一次预扣，既保护热路径延迟，又对短时间突发并发有额度保护。租约必须有超时回收机制，防止调用失败后额度长期占用。

桌面端未来有两种模型模式：

1. 本地自带模式：用户自己配置 API Key，所有调用在桌面本地完成。
2. 云端套餐模式：用户登录后走 `ai-gateway-service`，使用平台 API Key 和套餐额度。

成本风控：平台 API Key 托管意味着账号被盗会直接烧平台预算。除 max_rpm 外，ai-gateway 还需单用户/单 IP 的短窗口成本上限和异常突增告警，超限直接熔断。

### 5.6 worker

worker 不是"按消费 MQ 切出来的单一服务"，而是**按领域组织消费者**的统称。每个领域服务自带属于自己的异步消费者，或按领域独立队列、独立部署：

- `app/billing/job/`：订阅续期检查、退款补偿、账单报表。
- `app/quota/job/`：新周期 token_account 维护、用量聚合、对账。
- 通知、报表等可按领域归位为 `app/<领域>/job/`，或作为独立领域（如 `app/notification/job/`）；不单列全局 worker。

不把所有领域的异步逻辑塞进同一个可部署单元——否则它会成为耦合磁铁（billing 改续期逻辑要重启整个 worker，连带 quota 聚合一起受影响）和部署瓶颈。

职责（按领域分布）：

- RabbitMQ 消费。
- 支付成功后的下游异步处理（通知、统计、对账）。注意：额度账户创建走同步链路，不在此处。
- 订阅续期检查。
- 失败补偿。
- 用量统计聚合。
- 邮件、站内通知、运营报表。

典型事件（schema 见 §11 版本化约定）：

```txt
subscription.activated.v1
subscription.renewed.v1
subscription.canceled.v1
payment.succeeded.v1
payment.failed.v1
token.usage.recorded.v1
quota.exhausted.v1
```

### 5.7 跨服务一致性与 Saga

支付 → 订阅 → 额度 是跨三个服务的链路，是本系统最关键的分布式事务场景。必须按 saga 设计，不能靠"发一次事件就完事"。

原则：

- 不依赖跨服务事务（无 2PC）。
- 写库与发事件通过 **outbox 原子化**。
- 消费端必须幂等。
- 失败要有补偿或可兜底的兜底路径。
- 用户可见结果走同步链路，副作用走异步链路。

Outbox 模式（避免 dual-write）：

billing-service 在更新 `orders / payments / subscriptions` 的**同一 DB 事务**里写 `outbox_events`，由独立 relay 进程投递到 RabbitMQ。这样保证"DB 提交即事件最终发出"，不会出现"付了钱但事件丢失"或"DB 回滚但幽灵事件已发出"。

幂等消费：

每个事件带全局唯一 `event_id` + 领域自然键（如 `subscription_id + period_start`）。消费端用去重表或唯一约束保证重投递只生效一次。`webhook_events` 是同一思路在入口侧的应用，内部事件消费同样要求。

补偿：

若额度账户创建最终失败（例如长时间不可达），saga 不能"乐观成功"了事：标记订阅异常 → 通知运营 → 进入退款或人工处理流程。每一步都要可追溯，不留脏状态。

同步与异步的边界：

- 同步：支付回调成功 → 同步、幂等创建当期 token_account（billing 直连 quota gRPC）。用户付完钱立即可用。
- 异步：通知发送、统计聚合、续期、报表。
- 判断准则见 §11：同步链路只做必要的用户可见结果，耗时或可补偿动作进队列。

最终一致性窗口：

同步激活后用户立即可用；但前端展示的"用量趋势/历史"如果来自异步聚合，可能有短暂延迟。前端对"刚付完是否能用"应查询权威接口（quota-service），不查异步聚合表。

trace 上下文：

saga 链路横跨同步 RPC 与异步事件，必须全程透传 `trace_id`（见 §12），否则链路失败时无法定位是哪一跳。

## 6. 套餐与 token 额度模型

套餐不是简单的会员状态，而是“月费订阅 + 每月 token 额度”。

示例套餐：

```txt
Free       每月 10,000 tokens
Basic      每月 500,000 tokens
Pro        每月 2,000,000 tokens
Premium    每月 10,000,000 tokens
```

额度校准（重要）：token 额度必须按真实单次上下文规模校准，不能拍脑袋。长篇小说生成单次即可达数十万 token，Free 档 10,000 tokens 实际上**一次请求就会用尽甚至不足**，名义存在却不可用。各档 `monthly_token_quota` 必须与 `max_context_tokens`、`max_rpm`、典型工作流步数联合对账后再定。示例数字仅作量级参考，上线前需用真实 prompt 链路重算。

套餐维度：

- 月度 token 额度。
- 每分钟请求限制。
- 单次最大上下文。
- 可用模型等级。
- 是否支持高级工作流。
- 是否支持视频相关能力。

订阅周期：

```txt
用户购买套餐
  |
  v
billing-service 创建订单
  |
  v
微信支付 / 支付宝完成扣款
  |
  v
billing-service 接收并验证支付回调
  |
  v
更新 order / payment / subscription   （同一事务写 outbox）
  |
  v
同步、幂等创建当期 token_account        （billing 直连 quota gRPC）
  |
  v
relay 投递 subscription.activated.v1   （outbox → MQ，供下游异步消费）
  |
  v
worker 消费：通知 / 统计 / 聚合
```

月度重置不应清空旧账户，而是创建新的周期账户：

```txt
subscription: Basic
period: 2026-07-01 ~ 2026-08-01
quota_tokens: 500000
used_tokens: 0
```

这样便于查账、统计、排错和对账。

## 7. 套餐升级与降级

建议规则：

升级：

- 立即生效。
- 可补差价。
- 当前周期额度按新套餐补齐或按比例增加。

降级：

- 下个周期生效。
- 当前周期仍保持原套餐。

订阅表保留计划变更字段：

```sql

```

### 8.1 BFF / API 组合层

Web / Mobile / Desktop 三端取一个"账号首页"通常要同时拿到用户资料、订阅、额度——如果前端分别打 `/me`、`/me/subscription`、`/me/token-balance`，就是客户端编排 + N 次往返，且把服务拓扑泄露给了前端。

`services/app/bff/interface/` 作为 BFF（Backend for Frontend）提供面向端的聚合接口（契约在 `services/api/bff/interface/v1/`）。注意 `services/api/` 只放 proto 契约，BFF 是独立的运行服务：

```http
GET /me/dashboard     -- 组合 user + subscription + token-balance
GET /me/usage-trend   -- 组合用量日志 + 聚合统计
```

约定：

- BFF 只做聚合、裁剪、视图编排，不写业务逻辑，不持有状态。
- SDK 只暴露面向端的聚合视图，不镜像内部服务拆分。服务边界变更不应传导到前端。
- 内部服务仍各自对外暴露 REST（供后台、CLI、桌面直连等场景），BFF 是面向 C 端的优选路径。

## 9. Kong 网关职责

Kong 负责外部入口层：

- 路由。
- HTTPS。
- 基础限流。
- 请求日志。
- CORS。
- 认证前置。
- 服务发现或 upstream 管理。

Kong 只做"对外入口"的职责：解析并校验外部 JWT、剥离不合法请求、基础限流。**业务鉴权与资源归属校验必须放在服务内**，不能只依赖网关——网关通过不代表该用户有权访问该资源。服务间内部调用不经 Kong，其鉴权见 §13。

## 10. Redis 职责

Redis 用于：

- 登录失败限流。
- 短期验证码。
- API 限流计数。
- 临时会话状态。
- 热点套餐和配置缓存。
- AI 请求短期幂等 key。
- user / plan 等只读热数据的短期缓存（结合 §13 身份传播）。

权威数据仍以 PostgreSQL 为准。Redis 只做缓存和计数，不作为可信源。

## 11. RabbitMQ 职责

RabbitMQ 用于削峰和异步解耦：

- 支付成功后的下游处理（通知、统计、对账）。额度账户创建走同步链路，不在此处。
- 订阅续期。
- 支付失败重试。
- token 用量聚合。
- 通知发送。
- 后台报表。
- 失败补偿任务。

同步链路只做必要的用户可见结果，耗时或可补偿动作进入队列。

事件契约版本化（与 API 契约同等管理）：

- 事件名带版本：`subscription.activated.v1`，不兼容变更必须升版本号。
- payload 用 protobuf 或显式 `version` 字段；producer 改字段需向前兼容。
- consumer 按版本路由，旧版本消费者在新事件到来时不应崩溃。
- RabbitMQ 不自带 schema registry，需团队约定上述规则并在 CI 校验。

Outbox relay：

- 独立进程扫 `outbox_events`，未投递的记录投到 MQ，成功后回写 `published_at`。
- relay 崩溃重启后从 `published_at IS NULL` 继续，天然幂等。
- 配合消费端幂等，整条链路至少一次投递 + 恰好一次生效。

## 12. 可观测性

微服务的可观测性不是可选项。token 计量、支付、AI 调用这些链路横跨多个服务，没有跨服务追踪基本无法排障。四根支柱：

日志（结构化）：

- JSON 日志，统一字段：`timestamp / level / service / trace_id / span_id / user_id / request_id`。
- 敏感字段（API Key、token、手机号、密码哈希）落日志前必须脱敏。
- 日志按 service + trace_id 可串联检索。

指标（Prometheus）：

- 业务指标：token 扣减次数、额度不足拒绝数、支付成功率、订阅活跃数、outbox 堆积数。
- 系统指标：每服务 QPS、延迟分位（p50/p95/p99）、错误率、RabbitMQ 队列堆积、DB 连接池、relay 投递延迟。

链路追踪（OpenTelemetry / Jaeger）：

- 一次 `/ai/chat` 请求要穿 `Kong → ai-gateway → quota → 模型 → 回 quota`。
- `trace_id` 通过 HTTP header / gRPC metadata 透传；RabbitMQ 消息也携带 `trace_id`，串联同步调用与异步事件（含 §5.7 的 saga 链路）。
- ai-gateway 的模型出站调用作为独立 span，能直接看到真实模型耗时与重试。

错误上报：

- 服务异常聚合到 Sentry 或同类系统，按 service 分流，关联 trace_id。

trace_id 必须从 Kong 入口生成或透传，贯穿 BFF、各服务、MQ、worker，是整套可观测性的主键。

## 13. 安全要求

必须实现：

- 密码 `bcrypt` 哈希。
- refresh token 服务端保存哈希。
- 登录失败限流。
- 支付回调验签。
- webhook 幂等处理。
- 订单号全局唯一。
- 后端查询支付平台确认状态。
- 不从客户端直接修改订阅状态。
- token 扣减原子化。
- 敏感操作审计日志。
- API Key 不下发给 Web/Mobile。
- 平台 API Key 不进入开源桌面仓库。

身份传播与服务间鉴权：

- 对外：客户端持 JWT，Kong 校验签发与过期。
- 对内：服务间 gRPC 调用使用 mTLS 或短期内部 service token，**禁止"来自网关所以可信"的假设**；每个服务仍需校验调用方身份与权限。
- user 上下文通过 JWT claims / gRPC metadata 透传，服务内基于 claims 做授权。
- 横向越权防护：所有按 `user_id / subscription_id / token_account_id` 查询或修改的接口，必须校验该资源归属于当前身份，不能只信任传入的 id 参数。

桌面端本地安全：

- 用户自填 API Key 优先存于**系统 Keychain**（macOS Keychain / Windows Credential Manager / libsecret）。
- 不在本地 DB 存明文 Key，也不用"DB 加密字段"——若加密 key 藏在 app 内部，那只是混淆不是安全。
- 返回 renderer 时显示掩码，不返回明文。
- 云端模式下桌面端不需要知道平台 API Key。

备份与恢复：

- PostgreSQL 是权威源（订单、支付、订阅、token 账本）。必须有定期全量 + 增量备份，以及经过演练的恢复流程。支付与账本数据丢失是事故级风险。

## 14. 演进路线

第一阶段：整理目录和文档

- 父级 `docs/` 保存通用文档。
- `dramaip-desktop` 保持桌面端项目。
- `dramaip-platform` 新增闭源平台项目。

第二阶段：官网与账号体系

- 建立 `clients/apps/web`。
- 建立 `auth-service`。
- 支持注册、登录、refresh token。
- Web 账号中心接入。
- 可观测性地基（日志、指标、trace-id 透传）在服务诞生第一天就接入。

第三阶段：订阅和额度

- 建立 `billing-service`。
- 建立 `quota-service`。
- 接入微信支付和支付宝。
- 支持套餐购买、支付回调、月度 token account。
- outbox + saga + 同步激活随支付链路一起落地。

第四阶段：AI 网关

- 建立 `ai-gateway-service`。
- 用户无需填 API Key 即可使用平台模型能力。
- Web/Mobile/Desktop 都可调用云端 AI。
- 桌面端保留本地 API Key 模式作为可选路径。

注意：第三阶段已开始卖订阅，但云端 AI 在第四阶段才上线。第三阶段的付费用户实际仍用自己的 API Key 用桌面端，订阅价值来自桌面能力与未来云端额度。此为有意的产品节奏，需在销售页面向用户说清楚，避免"付了费却没有云端 AI"的预期落差。

第五阶段：移动轻创作

- 建立 `clients/apps/mobile`。
- 支持灵感、草稿、AI 快速扩写。
- 支持同步到桌面端继续精修。

第六阶段：平台化能力

- 资源市场。
- 云同步：本地优先 + 云同步涉及冲突解决（CRDT / last-write-wins / 手动合并），是已知难点，需单独设计冲突策略，不在本架构展开。
- 私有知识库。
- 管理后台。
- 运营报表。
- 团队与企业账号：现有 schema 暂无 `tenant_id` 多租户概念，引入时需前瞻设计数据隔离与计费分摊。
