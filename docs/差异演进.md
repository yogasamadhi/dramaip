# DramaIP 差异演进

本文记录 DramaIP 当前实现与 `docs/技术架构.md` 目标架构之间的差异、风险、迁移动作和退出条件。目标架构只写在 `docs/技术架构.md`；任何阶段性实现、兼容路径、临时简化和迁移计划都放在本文，避免污染目标设计。

更新时间：2026-07-13

> 文档路径已统一迁移到 `docs/loop/`。本文件中的差异状态仍以代码、测试和部署配置为准；路径迁移本身不代表任一 D 项完成。

## 1. 总体判断

当前实现已经具备可运行的云端平台骨架：auth / user / billing / quota / ai-gateway / billing-job / quota-job / migration-job 基本按 Kratos layout 拆开，Web BFF、HTTP 路由和 SDK 已经使用目标路径与 `/v1/...` 契约，Compose、Kong、可观测性目录也已成形。主要差异集中在四类：

- **路径与契约**：Web BFF 已完成端标识拆分；RabbitMQ 事件契约已版本化并纳入生成与兼容性检查。
- **安全与权限**：生产 JWKS 签名和 Web Cookie 会话已落地；可信服务间身份、资源归属校验与服务级 DB role 仍待收敛。
- **领域边界**：BFF 仍直接读写 `notification` schema，notification 只有迁移表，还没有独立 service/job。
- **账本与对账**：套餐快照、AI provider 成本快照、DB 权限隔离仍需补齐。

## 2. 差异清单

### D-001 BFF 路径按端拆分（已完成 Web 阶段）

**完成状态**：LM3-02 已将现有通用 BFF 迁移为 `services/api/bff/web/interface/v1` 与 `services/app/bff/web/interface`，并同步更新 Go import、生成代码、Docker/Compose、Kong、Helm、Kubernetes 脚本和运行文档。旧通用路径已删除；未创建的 Desktop/Mobile/Admin 能力仍必须仅在其各自端专属 BFF 下新增。

**验证**：`buf generate`、`GOCACHE=/tmp/dramaip-go-build go test ./...`、Compose 配置渲染、Helm 模板渲染通过；仓库扫描未发现旧通用 BFF 路径或旧服务标识的活动引用。

**后续约束**：LM3-25、LM3-27、LM3-29 创建新端 BFF 时，必须沿用 `api/bff/<端>/interface/v1` 对应 `app/bff/<端>/interface` 的镜像结构，不得重新引入通用入口。

### D-002 BFF 仍直接访问 notification schema

**当前实现**：`app/bff/web/interface/internal/data/downstream_clients.go` 持有 `*gorm.DB`，直接查询和写入 `notification.notifications`。

**目标态**：BFF 只做端侧聚合与视图裁剪。通知查询、已读状态、通知写入由 `notification/service` 承接；事件消费与通知生成由 `notification/job` 承接。

**风险**：BFF 绕过 notification 领域边界，后续 DB role 隔离后会直接失效；通知逻辑也会和 Web BFF 绑死。

**迁移动作**：补 `notification/service` gRPC/HTTP 契约；BFF 改为调用 notification-service；支付成功、订阅取消等通知通过事件或领域 API 生成，不再由 BFF 直接写表。

**退出条件**：BFF 不再持有跨领域 DB 写权限；通知读写全部通过 notification-service；`notification` schema 只有 notification 服务和 migration/job 可写。

### D-003 事件契约目录与兼容性 Gate（已完成）

**完成状态**：LM3-04 新增 `services/events/<领域>/v1` protobuf 契约及统一
`EventEnvelope`，覆盖 checkout、支付成功、订阅激活、token 用量和通知请求。每类事件都有
可解析示例；现有 billing outbox 和 RabbitMQ relay 已改用生成类型与 protobuf JSON
envelope，不再发布自由 `map[string]any` payload。

**验证**：`make event-contracts` 执行 protobuf 格式、`buf lint`、相对 `origin/main` 的
`buf breaking` 和生成物一致性检查；`go test ./...` 覆盖示例解析、未知兼容字段忽略和
路由/载荷一致性。billing 迁移 `015_billing_event_contract_envelope` 已在临时 PostgreSQL
数据库中验证，可将未投递的旧 checkout/payment outbox 行转为 envelope，已发布行保持不变。
根级平台 CI 定义会执行同一 gate；仓库所有者选择普通 Gitee 流程，未启用 Gitee Go 托管流水线。

**后续约束**：新增 producer/consumer 前必须先增加对应版本目录、schema、示例和生成物；
已发布字段只允许兼容性新增，删除、重编号、改类型或语义变化必须新建 `vN` 事件名和
目录。consumer 必须通过 `pkg/events.ParseEnvelope` 解析，以忽略未知兼容字段。

### D-004 BFF 单元测试使用无版本路径（已完成）

**完成状态**：LM3-01 已将 Web BFF HTTP 单元测试统一为 `/v1/...`，并新增无版本业务路径返回 `404` 的负向覆盖；LM3-02 随 BFF 迁移将该测试移动到 `services/app/bff/web/interface/internal/service/`。

**验证**：Go 全量测试、客户端 `pnpm typecheck` 与 Web 路由 smoke 均通过；无版本 `/plans`、`/me/dashboard`、`/auth/login`、`/billing/checkout`、`/ai/chat`、`/metrics` 均有明确的不暴露验证。

**后续约束**：所有新增外部 API、SDK、E2E 与单元测试必须使用 `/v1/...`；兼容路径如确有必要，必须单独命名并声明删除窗口。

### D-005 billing 缺少完整套餐快照

**当前实现**：`billing.orders` / `billing.subscriptions` 主要引用 `plan_id`，缺少目标架构要求的 plan code、价格、额度、RPM、上下文上限等完整快照字段。

**目标态**：订单、订阅周期、续期账单保存购买当时的套餐快照；quota 创建账户只接收快照额度，不依赖当前 `plans` 反推历史权益。

**风险**：套餐改价或改额度后，历史权益、收入和 quota 对账无法还原。

**迁移动作**：为 orders/subscriptions 增加 plan 快照字段；创建订单和续期时写入快照；quota account 创建使用快照数据。

**退出条件**：历史订单/订阅不依赖当前 `plans` 重建权益；对账可复现购买时套餐。

### D-006 AI provider 成本快照不完整

**当前实现**：`ai_gateway.request_audits` 已记录 request、provider、model、usage 和状态，但缺少输入/输出单价、币种、汇率、成本等 provider 计价快照。

**目标态**：AI 成本账本记录 provider、model、输入/输出 tokens、单价、币种、汇率、成本、计价时间，并与 request_id / reservation_id 关联。

**风险**：只能做用户 quota 账，无法分析毛利、异常成本和 provider 对账。

**迁移动作**：增加 provider cost log 或扩展 audit 表；把模型价格快照与每次请求绑定。

**退出条件**：可按 request_id 同时追踪用户额度扣减和平台真实成本。

### D-007 DB role / schema 权限尚未强制隔离

**当前实现**：各服务通过统一 PostgreSQL 连接工具打开数据库，目标中的“每服务独立 DB role”尚未从配置和权限上强制落地。

**目标态**：每个服务使用独立 DB role，只能访问自己的 schema；migration/job 使用单独 DDL 角色；BFF 不持有跨领域写权限。

**风险**：服务边界只停留在代码约定，实际仍可跨 schema 读取或修改。

**迁移动作**：新增服务专用连接配置和数据库 role；迁移权限授予；CI 或启动检查验证 role 权限。

**退出条件**：普通运行服务无法访问其他领域 schema；BFF 无跨领域写权限。

### D-008 认证签名仍是开发态 HS256（已完成）

**完成状态**：auth-service 已改为 RS256，使用 `kid` 签发并发布 `/.well-known/jwks.json`；生产 profile（`prod`/`production`）强制挂载 RSA 私钥与包含当前、保留公钥的 JWKS，且不再读取共享 `JWT_ACCESS_SECRET`。refresh token 采用家族轮换、旧 token 重放检测、可审计撤销原因和按设备撤销。

**Kong 边界**：仓库保留无私钥的开发模板；发布前由 `cmd/kong-jwt-config` 将受控 JWKS 渲染为 Kong 的 RS256 公钥 credentials。Kong 校验 `kid`、`exp`、`nbf`，Auth/BFF 继续强制校验 issuer、audience 和 Redis 会话，以覆盖 Kong OSS JWT 插件不验证 issuer/audience 的边界。

**轮换与回滚**：先发布包含新旧公钥的 JWKS 与 Kong 配置，再切换 `JWT_ACTIVE_KID` 和私钥；旧 access token 过期后才移除旧公钥。不得以生产共享 HS256 回退。

**验证**：JWKS 新旧 key、错误 audience、错误算法和生产缺少 key material 均有 auth 单测；refresh rotation/reuse/device revoke 已在临时 PostgreSQL 实例验证；Kong 渲染器测试覆盖多 key 与安全 `kid`。

### D-009 Web refresh token 存储不符合目标安全策略（已完成）

**完成状态**：LM3-06 的 Web BFF 在登录、注册和刷新时设置 Cookie：短期 access 与长期 refresh 均为 `HttpOnly + SameSite=Lax`，生产 profile 额外强制 `Secure`；refresh Cookie 的路径收窄为 `/v1/auth`。同源部署默认使用 host-only Cookie；若 Web/API 必须分属受控子域，可显式设置受控共同父域。响应 JSON 只包含用户信息，不再返回任何 access/refresh token。登出会撤销服务端 refresh 会话并按相同 domain/path 清除三类 Cookie。

**CSRF 与跨域边界**：BFF 对携带 Cookie 且未使用 `Authorization` header 的所有非安全方法实施双提交 CSRF 校验（可读 CSRF Cookie 与 `X-CSRF-Token` 常量时间比较）。Kong 的凭据型 CORS 仅允许开发精确 origin；生产部署必须替换为实际 HTTPS Web origin，禁止通配 origin 与 credentials 组合。分属子域时，Cookie domain 只能覆盖完全受控的同站点子域，不能把 token 扩散到不受信任子域。

**客户端迁移**：Web 不再读写长期 token；旧的 `localStorage` token 在首次加载时一次性删除，而不是不安全地换取 Cookie。Axios 启用 `withCredentials`，自动携带 CSRF header；多标签刷新使用 `navigator.locks` 串行化，并在取得锁后先复查新 Cookie access session，避免将 refresh rotation 误判为重放。

**验证**：Web BFF 单测覆盖 JSON 不泄漏 token、Cookie 属性、生产 `Secure`、Cookie 刷新/登出清除和 CSRF 拒绝；平台 E2E 改用 Cookie jar + CSRF；Web lint、typecheck 与生产构建通过。auth-service 的 refresh rotation/reuse 检测由 LM3-05 的数据库集成测试覆盖。

### D-010 notification 只有 schema，没有独立服务

**当前实现**：存在 `services/migrations/notification/014_notification_init.up.sql`，但没有 `app/notification/service` 和 `app/notification/job`。

**目标态**：notification 作为独立领域服务，负责通知查询、已读状态、事件 inbox、通知生成和投递重试。

**风险**：通知能力被 BFF 或其它领域直接写表，无法复用到 Mobile/Admin，也不利于 MQ 重试和幂等治理。

**迁移动作**：新增 notification proto、service、job；BFF 迁移到调用 notification-service；领域事件进入 notification-job 的 inbox。

**退出条件**：通知读写和事件消费都归 notification 领域；其它服务不直接写 `notification.notifications`。

### D-011 管理后台前端尚未独立

**当前实现**：`clients/apps/` 下只有 `web` 和 `mobile`，没有 `admin`；目标文档已将管理后台前端拆为 `clients/apps/admin`。

**目标态**：管理后台使用 React + Vite 体系独立部署，走 `admin/interface` 和管理员认证体系，不复用 C 端 Web BFF。

**风险**：若继续把后台功能塞进 Web 官网，会混用 C 端 JWT、路由、权限和审计边界。

**迁移动作**：创建 `clients/apps/admin`（React + Vite）；建立管理员登录、RBAC、审计日志基础页面；仅调用 `admin/interface`。

**退出条件**：管理后台页面不在 C 端 Web 路由下暴露；管理员操作全部走 admin BFF 并有审计。

## 3. 迁移优先级

1. **收紧服务身份底座**：D-007 与可信边缘/服务间身份，优先封住伪造内部身份和跨 schema 访问。
2. **拆出 notification 边界**：D-002、D-010，解除 Web BFF 对 notification schema 的直接写入。
3. **补齐账本和权限**：D-005、D-006、D-007，保证支付、quota、AI 成本链路可审计、可幂等、可对账。
4. **后台独立化**：D-011，随运营能力上线前完成。

已完成并保留记录：D-001（LM3-02，Web BFF 路径迁移）、D-004（LM3-01，版本化路由测试）、D-008（LM3-05，JWKS 生产认证）和 D-009（LM3-06，Web Cookie 会话与 CSRF）。
