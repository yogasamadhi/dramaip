# DramaIP 差异演进

本文记录 DramaIP 当前实现与 `docs/技术架构.md` 目标架构之间的差异、风险、迁移动作和退出条件。目标架构只写在 `docs/技术架构.md`；任何阶段性实现、兼容路径、临时简化和迁移计划都放在本文，避免污染目标设计。

更新时间：2026-07-07

## 1. 总体判断

当前实现已经具备可运行的云端平台骨架：auth / user / billing / quota / ai-gateway / billing-job / quota-job / migration-job 基本按 Kratos layout 拆开，BFF HTTP 路由和 SDK 已经主要使用 `/v1/...`，Compose、Kong、可观测性目录也已成形。主要差异集中在四类：

- **路径与契约**：BFF 仍是无端标识的 `bff/interface`，事件契约目录尚未落地。
- **安全与权限**：生产目标要求 JWKS / 非对称签名、Cookie 安全存储、服务级 DB role，目前仍有开发态实现。
- **领域边界**：BFF 仍直接读写 `notification` schema，notification 只有迁移表，还没有独立 service/job。
- **账本与对账**：套餐快照、AI provider 成本快照、DB 权限隔离仍需补齐。

## 2. 差异清单

### D-001 BFF 路径仍未按端拆分

**当前实现**：代码仍使用 `services/api/bff/interface/v1` 与 `services/app/bff/interface`，没有 `bff/web/interface`、`bff/desktop/interface`、`bff/mobile/interface`、`admin/interface` 运行目录。

**目标态**：Web/Desktop/Mobile/Admin 分端独立，契约路径与实现路径镜像：`api/bff/<端>/interface/v1` 对应 `app/bff/<端>/interface`。

**风险**：Desktop、Mobile、Admin 能力继续进入同一个 BFF，BFF 变成万能聚合层，端侧节奏互相拖累。

**迁移动作**：先把现有 BFF 迁移为 Web BFF；旧路径只保留短期兼容壳或删除。新端能力只允许进入端专属 BFF。

**退出条件**：不再新增 `api/bff/interface/v1` / `app/bff/interface` 能力；Web BFF 使用目标路径；新端只在端专属 BFF 下开发。

### D-002 BFF 仍直接访问 notification schema

**当前实现**：`app/bff/interface/internal/data/downstream_clients.go` 持有 `*gorm.DB`，直接查询和写入 `notification.notifications`。

**目标态**：BFF 只做端侧聚合与视图裁剪。通知查询、已读状态、通知写入由 `notification/service` 承接；事件消费与通知生成由 `notification/job` 承接。

**风险**：BFF 绕过 notification 领域边界，后续 DB role 隔离后会直接失效；通知逻辑也会和 Web BFF 绑死。

**迁移动作**：补 `notification/service` gRPC/HTTP 契约；BFF 改为调用 notification-service；支付成功、订阅取消等通知通过事件或领域 API 生成，不再由 BFF 直接写表。

**退出条件**：BFF 不再持有跨领域 DB 写权限；通知读写全部通过 notification-service；`notification` schema 只有 notification 服务和 migration/job 可写。

### D-003 事件契约目录尚未落地

**当前实现**：`services/events/` 目录不存在，RabbitMQ payload 还没有独立 schema 约束。

**目标态**：RabbitMQ 事件 schema 放在 `services/events/<领域>/vN/`，与 HTTP/gRPC 契约同等版本化。

**风险**：producer/consumer 对 payload 理解漂移，字段变更只能靠人工约定，升级时容易产生隐性破坏。

**迁移动作**：新增事件 proto 或 JSON Schema、示例 payload、兼容性测试；CI 校验事件 schema 和 consumer 兼容性。

**退出条件**：新增 MQ producer/consumer 前必须先有事件 schema；CI 能阻止不兼容事件变更。

### D-004 BFF 单元测试仍使用无版本路径

**当前实现**：BFF HTTP router 和 SDK 已主要使用 `/v1/...`，但 `app/bff/interface/internal/service/http_test.go` 仍请求 `/plans`、`/me/dashboard`、`/auth/login` 等无版本路径。

**目标态**：外部 API、SDK、E2E、单元测试全部使用 `/v1/...`。

**风险**：测试与真实 router 契约不一致，可能掩盖路由回归；后续维护者误以为无版本路径仍受支持。

**迁移动作**：把 BFF HTTP 单元测试路径统一改为 `/v1/...`；若需要兼容测试，单独命名并标注兼容窗口。

**退出条件**：`services/app/bff/interface/internal/service/*_test.go` 不再出现无版本业务路径。

### D-005 billing 缺少完整套餐快照

**当前实现**：`billing.orders` / `billing.subscriptions` 主要引用 `plan_id`，缺少目标架构要求的 plan code、价格、额度、RPM、上下文上限等完整快照字段。

**目标态**：订单、订阅周期、续期账单保存购买当时的套餐快照；quota 创建账户只接收快照额度，不依赖当前 `plans` 反推历史权益。

**风险**：套餐改价或改额度后，历史权益、收入和 quota 对账无法还原。

**迁移动作**：为 orders/subscriptions 增加 plan 快照字段；创建订单和续期时写入快照；quota account 创建使用快照数据。

**退出条件**：历史订单/订阅不依赖当前 `plans` 重建权益；对账可复现购买时套餐。

### D-006 AI provider 成本快照不完整

**当前实现**：`ai_gateway.request_audits` 已记录 request、provider、model、usage 和状态，但缺少输入/输出单价、币种、汇率、成本等 provider 计价快照。

**目标态**：AI 成本账本记录 provider、model、输入/输出 tokens、单价、币种、汇率、成本、计价时间，并与 request_id / reservation_id 关联。

**风险**：只能做用户 quota 账，无法分析毛利、异常成本和 provider 对账。

**迁移动作**：增加 provider cost log 或扩展 audit 表；把模型价格快照与每次请求绑定。

**退出条件**：可按 request_id 同时追踪用户额度扣减和平台真实成本。

### D-007 DB role / schema 权限尚未强制隔离

**当前实现**：各服务通过统一 PostgreSQL 连接工具打开数据库，目标中的“每服务独立 DB role”尚未从配置和权限上强制落地。

**目标态**：每个服务使用独立 DB role，只能访问自己的 schema；migration/job 使用单独 DDL 角色；BFF 不持有跨领域写权限。

**风险**：服务边界只停留在代码约定，实际仍可跨 schema 读取或修改。

**迁移动作**：新增服务专用连接配置和数据库 role；迁移权限授予；CI 或启动检查验证 role 权限。

**退出条件**：普通运行服务无法访问其他领域 schema；BFF 无跨领域写权限。

### D-008 认证签名仍是开发态 HS256

**当前实现**：auth-service 使用 HS256 `JWT_ACCESS_SECRET` 签发 access token，Kong `kong.yml` 也配置 HS256 consumer secret。

**目标态**：生产 access token 使用 RS256 / ES256 等非对称签名，通过 JWKS 发布公钥，支持 key rotation。

**风险**：多个组件共享 HMAC 密钥，密钥扩散后难以轮换；也不符合多服务本地验签和边缘验签的目标安全边界。

**迁移动作**：引入签名 key set、`kid`、JWKS endpoint、key rotation 策略；Kong 改为 JWKS / OIDC 验签模式；保留 HS256 仅作为 dev/test profile。

**退出条件**：生产配置不再使用共享 `JWT_ACCESS_SECRET`；Kong 和服务端均通过 JWKS 验签。

### D-009 Web refresh token 存储不符合目标安全策略

**当前实现**：`clients/apps/web/lib/api-client.ts` 将 access token 和 refresh token 写入 `window.localStorage`。

**目标态**：Web refresh token 使用 `HttpOnly + Secure + SameSite` Cookie，由 BFF/Auth 设置和轮换；状态变更接口具备 CSRF 防护。

**风险**：XSS 可直接窃取长期 refresh token，账号恢复成本高。

**迁移动作**：改造登录/刷新/登出为 Cookie 模式；access token 改为内存态或 BFF session 换取；新增 CSRF token 或 SameSite 策略验证。

**退出条件**：Web 不再把 refresh token 写入 localStorage；状态变更接口有 CSRF 防护。

### D-010 notification 只有 schema，没有独立服务

**当前实现**：存在 `services/migrations/notification/014_notification_init.up.sql`，但没有 `app/notification/service` 和 `app/notification/job`。

**目标态**：notification 作为独立领域服务，负责通知查询、已读状态、事件 inbox、通知生成和投递重试。

**风险**：通知能力被 BFF 或其它领域直接写表，无法复用到 Mobile/Admin，也不利于 MQ 重试和幂等治理。

**迁移动作**：新增 notification proto、service、job；BFF 迁移到调用 notification-service；领域事件进入 notification-job 的 inbox。

**退出条件**：通知读写和事件消费都归 notification 领域；其它服务不直接写 `notification.notifications`。

### D-011 管理后台前端尚未独立

**当前实现**：`clients/apps/` 下只有 `web` 和 `mobile`，没有 `admin`；目标文档已将管理后台前端拆为 `clients/apps/admin`。

**目标态**：管理后台使用 React + Vite 体系独立部署，走 `admin/interface` 和管理员认证体系，不复用 C 端 Web BFF。

**风险**：若继续把后台功能塞进 Web 官网，会混用 C 端 JWT、路由、权限和审计边界。

**迁移动作**：创建 `clients/apps/admin`（React + Vite）；建立管理员登录、RBAC、审计日志基础页面；仅调用 `admin/interface`。

**退出条件**：管理后台页面不在 C 端 Web 路由下暴露；管理员操作全部走 admin BFF 并有审计。

## 3. 迁移优先级

1. **先修契约和测试一致性**：D-001、D-004，避免新端和测试继续依赖错误路径。
2. **收紧安全底座**：D-008、D-009，优先处理长期凭据和生产验签策略。
3. **拆出 notification 边界**：D-002、D-010，解除 BFF 对 notification schema 的直接写入。
4. **补齐账本和权限**：D-005、D-006、D-007，保证支付、quota、AI 成本链路可审计、可幂等、可对账。
5. **后台独立化**：D-011，随运营能力上线前完成。

## 4. 维护规则

- 本文只记录差异和迁移，不定义目标架构；目标架构以 `docs/技术架构.md` 为准。
- 每条差异必须有明确退出条件。没有退出条件的“临时实现”等同于目标漂移。
- 当差异完成收敛后，保留一条完成记录或在变更日志中说明删除原因，不把已完成差异重新写回目标架构文档。
