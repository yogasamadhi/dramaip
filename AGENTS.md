# AGENTS.md

DramaIP contains two independent products: `desktop/` (Apache-2.0 Electron/local Runtime) and `platform/` (proprietary Java cloud platform and clients). They own separate dependencies, data, builds, tests, and releases; never add a build or runtime dependency across them. Root files only coordinate launchers, tests, docs, and CI; there is no root JS workspace.

## Sources of truth

- Product positioning: `docs/product/POSITIONING.md`; brand copy: `docs/product/BRAND.md`; proposed work: `docs/PLAN.md`. Story/IP development and authoritative content are the overall core. Novel writing is an independent first-class upstream capability with manuscript/submission outcomes; adaptation/screenplays are the transformation core; author intent, narrative quality, continuity, versions, and lineage span both. Media is an optional production output. Do not force novel writing, adaptation, or video into every project, and do not turn planned workflows, simulated scores, or historical release records into shipped-quality or GA claims.
- Desktop design: `docs/architecture/desktop/DRAMAIP_CLIENT_PLUGIN_RUNTIME_ARCHITECTURE.md`; implemented facts: `desktop/docs/engineering/ARCHITECTURE.md` and code. Do not present roadmap items as implemented.
- Platform design and ownership: `docs/后端技术架构.md`. Prefer current launchers and `platform/README.md` over stale `run-platform.py` references in `platform/docs/LOCAL_DEVELOPMENT.md`.
- Commands/workspaces come from `desktop/package.json`, `platform/clients/package.json`, `platform/Makefile`, and `.gitlab-ci.yml`.
- Loop mode is opt-in. Do not read/apply `docs/loop/LOOPRULE.md`, create `loop/*`, or create Loop records unless the maintainer explicitly enables it.

## Toolchains and setup

- Both JS workspaces require Bun **1.4.0 exactly**. Both disable Bun auto-install; install explicitly or let the root launchers do so. Keep Desktop's `linker = "isolated"`; keep Platform clients' `linker = "hoisted"` because Metro/Babel requires hoisting.
- Desktop uses Bun 1.4.0 for dependency management/builds and Node **24.18.0 exactly** for standalone Core Runtime, migration workers and Runtime tests; desktop Core uses Electron's embedded Node. Invoke standalone Node through `scripts/run-node.mjs`. Development HMR requires `--expose-internals`; Bun Core Runtime is unsupported. Platform clients separately require Node >=20 (CI pins 24.18.0), including the Expo toolchain.
- Platform server requires JDK 21 only and Maven 3.9+; Spring Boot 4.0.6 is managed by `platform/server/pom.xml`, not child modules.
- Fresh clones need `git submodule update --init` before `check:engine-locks`; `run-desktop.ts` initializes active Codex/Pi/DSH sources. Treat all `vendor/*` as read-only. `desktop/legacy/` and non-workspace `desktop/packages/schema/` are references/leftovers, never dependencies or implementation targets.

## Desktop

- From repo root, `bun run-desktop.ts` verifies Bun and the locked DSH snapshot, prepares the nine framework workspaces, installs dependencies, builds the framework, prepares Codex/Pi, repairs Electron, removes `ELECTRON_RUN_AS_NODE`, and starts dev. Useful modes: `--check`, `--install`, `--rebuild-engines`; pass Electron/Vite args after `--`.
- From a clean Desktop checkout: `git submodule update --init`, `bun run prepare:framework`, `bun ci`, `bun run build:framework`, `bun run check:framework`. `build/dsh-framework/` is ignored, reproducible output; never edit vendor or resolve the nine framework packages from registry copies.
- Development uses native Loader/Include/Group patches under `bundles/` and `profiles/`, with DSH Timer/HMR. `test:runtime:hmr` and `test:runtime:hmr:electron` test detached artifacts, all five Profiles and graph recovery. Production has no file watchers.
- From `desktop/`: `bun run test` already runs typecheck, unit/Runtime, and conformance suites. Focus Bun-only suites with `bun test <path>`; run Runtime suites with `bun run test:runtime:node` or `bun scripts/run-node.mjs --expose-internals node_modules/vitest/vitest.mjs run <path>`.
- Electron E2E is serial and needs built output: `bun run test:e2e`; focus with `bun run build && bun scripts/run-electron-playwright.ts test tests/electron/<file>.spec.ts --reporter=list`. Linux needs a display (`xvfb-run -a ...`). Engine tests also need prepared `build/codex` and `build/pi` resources.
- Maintainer preference: all agent debugging must stay in the background without stealing desktop focus. Isolated Electron E2E automatically keeps main/credential windows hidden; manual development/debug launches must use `DRAMAIP_DEBUG_BACKGROUND=1`. Uncontrolled native dialogs/external apps are blocked in this mode. Use logs, screenshots and controlled selectors; ask before any foreground/native interaction. Do not hide, focus or close the maintainer's ordinary app instances.
- Broad local verification: `bun run lint`, `bun run format:check`, `bun run test`, all relevant `check:*`, then `bun run build && bun run check:renderer-chunks`; the chunk check reads the build manifest. Packaging additionally needs `DRAMAIP_UPDATE_URL`, prepares Codex and Pi, and must precede `release:metadata`.
- Contract/route changes: `bun run --filter @dramaip/client generate`, then `bun run check:generated`. Ownership/event/service/built-in UI changes: `bun run architecture:generate`, then `bun run check:architecture`. Functional migration evidence: `bun run migration:generate`, then `bun run check:migration:complete`; `db:generate`/`db:push` are intentional no-ops. Do not hand-edit generated catalogs, manifests, OpenAPI, or the migration matrix.

Desktop architecture red lines:

- Flow is `Client -> ServerConnectionManager -> HTTP /api/v2 -> independent Core Runtime -> HTTP /host/v1 -> Desktop Host`. Renderer business code uses only `@dramaip/client`: no direct `fetch`, business IPC, Host/Runtime implementation imports, or direct `ServerConnectionManager` imports outside `runtime-connection`. Preload exposes only the one-shot Runtime bootstrap exchange; Electron Main supervises rather than owning business routes/workflow.
- Composition is `Plugin -> Bundle -> Product Profile -> Core Graph Revision`; profiles reference bundles, not plugin lists. Installed extensions use a separate Extension Graph revision and never mutate the official Profile/Core Graph. The registry owns exactly 14 first-party plugins; do not recreate `legacy-bridge`.
- First-party plugins use native DSH Cordis `Context / Service / inject / effect / Fiber` and import `@dramaip/plugin-api/internal`; Cordis imports are allowed internally and forbidden in public Plugin API, Renderer and Agent Runtime. Signed isolated extensions use the public root API. Third-party code runs only in Extension Host QuickJS/WASM processes, never Core or the main Renderer, and cannot supply React/HTML, Node APIs, raw SQLite, unrestricted files/network, paths, or credentials.
- Each table, route, event, migration, service, and UI contribution has one owner. Plugins cannot import peer implementations or write peer tables. Register every long-lived route/handler/timer/watcher/process through tracked `ctx.effect()` or a supervisor so activation failure/disposal unwinds it. Use native `ctx.effect(acquire, label)`; independent effects use DSH concurrent cleanup. Put resources requiring ordered disposal in one effect and await each step. Durable business events use `ctx.domainEvents`, leaving Cordis `ctx.events` untouched.
- Routes are declarative contributions and preserve `/api/v2`, RFC 7807, operation IDs, ETag/If-Match, Idempotency-Key, cursor pagination, and replayable SSE. Business writes and persistent Domain Events share a transaction; applied plugin migration owner/version/checksum is immutable and migrations are forward-only.
- Public contracts expose opaque grants/artifact refs/`credentialRef`, never credential plaintext or unnecessary absolute paths. `@dramaip/agent-runtime` stays vendor/framework-neutral; Runtime owns Session/Run/Item, workflow, Preview/Commit, retry, and recovery. Pi, Codex, and LangGraph.js are the only active engines; unsupported operations return structured errors, never silent fallback.

## Platform

- From `platform/`, `make test` runs Maven verify, client typecheck/tests, contract checks, and web-route smoke; it does not install dependencies, run client lint, or build Web/Admin. Java-only: `mvn -B -ntp verify` in `platform/server/`. Focus Java with `mvn -B -ntp -pl services/<name> -am -Dtest=<Class> -Dsurefire.failIfNoSpecifiedTests=false test`; focus clients from `platform/clients/` with `bun test <path>`.
- Client CI parity from `platform/clients/`: `bun ci`, then `bun run lint`, `typecheck`, `contracts:check`, `test`, `build:web`, and `build:admin`; run `make web-route-smoke` from `platform/`. `typecheck`/`test` already include root launcher checks. Public schema changes require a contract-version bump when `origin/main` is available.
- Local Compose E2E is ordered and stateful: `make platform-up`, then `make platform-e2e`, then `make platform-down`. E2E writes local data; normal down preserves bind-mounted data. CI-only `platform-ci-e2e` reuses packaged JARs/random ports and must be paired with `platform-ci-down`.
- Root launchers are separate: `bun run run-platform-dev.ts` runs migration, Gateway `8080`, and host JVM services `8081-8087` while infra stays in Docker; it stops Compose Java containers and may terminate occupants of those ports. `bun run run-platform-clients.ts` may install dependencies and terminates occupants of `3009-3011` by default; use `--no-install`/`--no-kill-ports` when needed. Consult each `--help` before partial startup.

Platform architecture red lines:

- Gateway is the only public entry. Business APIs use `/api/v1/**` plus `X-DramaIP-Contract-Version: 2`; JSON APIs use `Result<T>` with request/trace IDs, except protocol-specific streams/downloads/health. Gateway routes/authenticates but does not own business orchestration or database access.
- Services do not depend on peer implementations; `common` is technical infrastructure only. Each business table has one authoritative service writer, reporting owns projections rather than master data, and cross-service access uses APIs/events/read models instead of a central all-domain DTO module.
- Only the `migration` executable uses Flyway. Historical SQL is 001-049 with baseline 49; new immutable forward-only migrations start at `V050`, and production keeps `baselineOnMigrate=false`. Prefer local transactions plus outbox/idempotent consumers; Seata is explicit/limited, never the default for payment, AI-provider, or RabbitMQ boundaries.
- `platform/deploy/release/images.tsv` is the authoritative inventory: migration, Gateway, seven services, and Web (9 Java + 1 Web). `check-manifest.sh` is shared by CI/build/scan/push/Helm; reactor support modules do not map to images.
- Releases are operator-run: `preflight.sh` requires clean `main`; build images, refresh Trivy vulnerability/Java databases, scan, then push; invoke `DRAMAIP_RELEASE_AUTHORIZED=1 helm-release.sh <staging|production> <apply|rollback> [revision]` only after approval. GitLab validates merge requests/default branch on private Docker runners but does not deploy.

## Root checks

- Run root launcher/release tests with `python3 -m unittest discover -s tests`; focus with `-p 'test_run_platform_dev.py'` or `-p 'test_platform_release.py'`. The launcher suite rejects every Bun version except 1.4.0.
- The remote is Gitee, while CI is GitLab (`.gitlab-ci.yml`, private runners, `harbor.home.arpa`); do not assume GitHub workflows or URLs.
